# 开发日志与 Qoder 使用记录规范

> 比赛硬性要求：提交每日开发流程 + Qoder 使用方式说明，并附截图证据。
> 本目录是**过程证据的唯一归档处**，代码提交信息不替代它。

## 目录约定

```
devlog/
  README.md              本规范（含每日模板）
  YYYY-MM-DD.md          每日一条，当天写，不攒到周末
  assets/YYYY-MM-DD/     当日截图与附件
    01-说明.png
    02-说明.png
```

命名只用日期和两位序号，便于日志内相对引用：`![说明](assets/2026-11-17/01-xxx.png)`。

## 每日必填六项

1. **今日目标**：开工前写下打算完成什么（不是事后追认）。
2. **实际完成**：对照目标逐条写结果，未完成的写「未完成 + 原因」。
3. **Qoder 使用记录**：见下表，逐条列。这是比赛评分的重点，不能只写「用了 Qoder」。
4. **决策与变更**：当天拍板的技术/范围决策，以及与 PRD 草案不一致的地方。
5. **截图证据**：至少 2 张，覆盖「Qoder 侧」和「产物侧」。
6. **明日计划**：下一步具体动作 + 阻塞项。

## Qoder 使用记录表（第 3 项的格式）

| # | 能力类型 | 具体名称 | 目标 / 关键 prompt 原文 | 产出物（可点击路径） | 人工修正 | 效果判断 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | Skill | `qoder-canvas:canvas` | 「制作架构与领域模型可视化，用于 3 人评审」 | `...canvas.tsx` | 无 / 改了 X | 有效 / 部分有效 / 无效 |

**能力类型**取值固定为：`Skill`、`Agent`（子代理）、`MCP`（工具）、`内置工具`（Read/Edit/Grep/Bash 等）、`记忆`、`人工`。

填写要求：

- **prompt 写原文或贴近原文的摘要**，不要事后美化成「让 AI 生成架构图」。评委会看你怎么提问。
- **人工修正必须写**，包括「AI 输出错了什么、我怎么发现的、怎么改的」。这部分比成功记录更有说服力。
- **效果判断要诚实**，无效就写无效并说明为什么放弃。
- 一次对话里调用了很多工具时，按「阶段」归并成 3–8 行，不要逐次刷屏。

## 截图规范

| 来源 | 谁截 | 方式 |
| --- | --- | --- |
| 应用界面（跑起来之后） | agent 自动 | `browser-use` MCP `take_screenshot`，存到当日 assets 目录 |
| Qoder 界面（Skill 调用、Canvas 预览、Agent 面板、对话） | 本人手动 | `Win + Shift + S`，粘贴后另存为当日 assets 目录 |
| 代码 / 文件树 / 测试结果 | 本人手动或 agent | 终端截图，或用文本块代替（注明是文本摘录） |

agent **无法截取 Qoder 桌面界面本身**，这部分必须人工补。每天日志末尾会留「待补截图」清单，没补齐就标 `待补`，不要留空假装已完成。

截图内容要求：能看到上下文（界面标题、文件名、时间），能对应到日志里的某一条记录；涉及真实姓名/学校/账号的画面先打码。

## 诚实性要求

- 不补造未发生的操作，不把「计划做」写成「已完成」。
- AI 生成的素材（示例截图、演示数据）在日志中明确标注为生成内容，与真实运行结果区分——这与 PRD F12 第 385-387 行的规则一致。
- 当天没进展也写一条，说明卡在哪。空白日期比负面记录更糟。

## 阶段汇总

每个阶段末（PRD 第 8 章的 4 个阶段）把当阶段日志汇总成一页：做了什么、Qoder 承担了哪部分、哪些是人工判断、返工了几次。最终路演材料用 `Presentations:pptx` skill 从这些汇总生成，避免临赛补写。
