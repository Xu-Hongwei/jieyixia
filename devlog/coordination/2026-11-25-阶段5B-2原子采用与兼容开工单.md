## 1. 本阶段要交付什么

用户核对一份草案后，点击一次明确的“采用这份计划”，将它变成真实任务、行动和每日安排；保存结果可核实，重复点击不会重复创建，中途失败不会留下半份计划。

主链路：**已保存草案 → 影响预览 → 核对重要字段与缺口 → 明确采用 → 整批保存 → 展示真实结果 → 打开现有任务/日程继续执行。**

本阶段采用隔离验收入口验证真实服务与现有产品页面，不提前开发完整助手页面。5B-3 再接真实建议接口，5B-4 再交付完整助手交互。不得把固定输入演示说成截图识别或真实模型规划已经完成。

### 当前代码依据

- 正式契约为 0.5.0，数据库 v4，备份 v2；三个助手 store 已存在。
- `frontend/src/services/assistant/drafts.js` 已负责草案保存、确认、重算、刷新结算，没有正式采用能力。
- `frontend/src/services/storage/db.js` 的 `transformAssistantAtomic` 只写线程/草案；不能将它直接包装成“已实现整批采用”。

- 现有 Task/Action/PlanItem、专注与日程规则继续使用；不创建第二套执行数据。

## 3. 产品规则一次性确定

### 3.1 采用范围

1. 一次采用当前草案的一个明确版本。取消预览、继续编辑、仅保存草案都不写正式业务。
2. 首版新增安排，不替换、删除、移动或取消既有安排；`replacement_ids` 必须为空。
3. Task 支持 create/link/update；update 仅限已批准的标题、描述、完成标准、截止四类字段，逐字段核对旧值与新值。不能修改状态、当前行动、分组、空间或执行历史。
4. Action 支持 create/reuse。复用只关联既有行动，不修改其正文/估时/完成状态，也不重复创建。新增行动默认未完成。
5. 新 Task 为 todo、current_action_id=null；无分组依据则 matter_id=null。关联已有 Task 不自动开启任务或专注。
6. 整体采用已确认的有效范围。明确排除的工作项不生成安排，也不因仍残留 proposal 就创建其独占新行动/新任务。被其他纳入项引用的共享对象按引用闭包保留一次。存在非排程用途的孤立新对象时，不静默决定保留或丢弃：2A 返回“先明确采用范围”的阻断。
7. 已知但未排下的纳入行动仍创建一次、保持未完成；结果必须单列未排工作及分钟。未知估时必须补充或明确排除。
8. 有缺口与有既有过载分别确认，不能用一个总确认替代。已有安排对应的“额外尚未安排工作”确认继续沿用 D12。
9. 不提供整批撤销采用。事务失败回滚、重复提交去重与用户事后撤销是不同能力；采用后修改走现有对象操作或新草案。

### 3.2 每日安排与截止

- 一个 Task 可以对应多个日期上的 PlanItem；一段安排一条 PlanItem，不能按段复制 Task 或 Action。
- 日程上方展示每天安排的工作，下方展示 Task 的真实截止；安排日期不写回截止，窗口末不自动成为截止。
- 正式 PlanItem 不新增 action_id；建议行动引用留在草案，开始工作沿用现有行动选择与开始确认流程。
- 新安排固定为 planned，actual_minutes=null、focus_session_id=null、task_ref_state=active。
- 新安排同日 order 接在当前最大 order 后，保留本次分段顺序，不重排原记录。安全整数溢出时拒绝。
- 按北京时间自然日处理。预览到提交期间跨北京午夜必须重新核对，不把已过去的日期静默改成今天。

### 3.3 截止、出处与确认

- 采用时保存的是用户确认的截止决定，必须与最后有效排程采用的截止一致；存在差异时要求重算。
- 保留既有截止时保持原字符串与精度，兼容无秒等已支持写法；不因采用改写事实。
- 无截止使用正式 Deadline 的空值形状；不能将缺失确认解释为明确无截止。
- Note 字段确认仍保留 origin/derived/quote 等来源信息；单纯确认不伪装为用户重新输入。
- 有合法已确认 Note 字段依据时，Task 截止可使用 source=note，并保证 from_note_id 在 note_ids 中。
- 只有图文 Source/助手建议、没有匹配 Note 的截止，不能伪造 Note 或偷标 manual：2A 将其列为需要补充“用户明确录入/修改为此值”或先走既有核对路径的阻断。纯用户值可按既有 manual 语义保存，草案仍保留原始证据与用户决定。不在本阶段临时增加 Note 自动生成流程。
- Task 更新的未提供字段表示不改。标题不允许清空，描述允许明确空字符串；完成标准首版不扩展清空能力（null 仍为不改），有值更新须确认。清除截止必须通过显式 null 截止确认及重新排程，不凭空候选数组单独授权。

## 4. 预览必须说明什么

预览来自实际准备写集，不另拼一套与保存无关的展示数据：

- 新建哪些任务、关联哪些既有任务、哪些任务字段从何值改为何值。
- 新建哪些行动、复用哪些行动；行动估时与本次剩余工作量分开显示，二者不能互相覆盖。
- 各日新增安排、已有占用、预算和缓冲；总截止另列。
- 已排与未排分钟、未排原因、排除范围、既有过载及相应确认。
- 来源字段确认清单；任务/行动/安排的预计创建数量及任务更新数量。

采用按钮绑定 workspace、draft、revision、完整预览身份。内容、确认、范围或事实改变后原预览失效，不能只凭 revision 相同继续提交。

**看预览本身无持久化副作用。只有用户明确采用后，才生成/落盘 pending 协调信封与 applying 状态。** 可在内存预分配 ID，但不得把“已准备”显示成“已保存”。

- 仅增加本地采用类型且不改变已有持久 payload 时，维持 schema 0.5.0 / DB v4 / backup v2；不改 HTTP API，不新增后端端点。
- 生成 schema/typedefs 等，禁止手改生成物。为新增类型补正式校验入口及负例。
- 来源确认必须补足“当前字段完整基线 → 明确决定 → 正式字段”的映射，不能仅校验 value 而漏 status/origin/derived/quote/precision。

### 5.2 纯函数与适配层

建议增加 `frontend/src/domains/assistant/application.js`（可按职责拆分），提供以下等价能力：

1. 从合法草案及固定快照导出采用范围与引用闭包。
2. 生成预览、正式字段补丁、新对象与确定性计数。
3. 生成 ID 映射与可签名的不可变准备数据；时间/ID/北京时间今天由外部注入，纯函数内部不读系统时钟、不随机取 ID、不写库。
4. 比较准备基线与最新事实，返回所有可安全报告的相关差异及可定位路径。
5. 将成功写集转换为 ApplicationReceipt 与 AppliedSummary；这里只计算候选值，成功回执须由 2B 提交完成后对外返回。

复用现有 planning、assistant/draft、refs 和业务域校验规则；避免复制出第二个排程器或第二套专注保护规则。旧工厂若内置随机 ID/独立落库，抽取必要纯构造能力后复用，不按顺序调用 app store 的多个保存方法。

### 5.4 摘要与不可变性

签名覆盖：空间、草案身份/版本、当前完整内容与确认、规划输入/结果、完整相关基线、采用范围、实际写集、ID 映射，以及会影响提交语义的日期边界。稳定序列化并写清每个排除字段的理由。

事务外完成 Blob 读取、摘要计算和深拷贝；输入对象事后突变不改变已冻结准备数据。同 application_id 的重试不得重新生成 ID、时间戳或写集再冒充同一意图。正式写入必须比对本地持久 pending 信封，不信调用者重新提交的任意写集。

### 5.5 2A 验收与交回

至少覆盖：新建/关联/更新/复用、同任务多天、多工作项共享行动、全部/部分排不下、未知与排除、依赖缺口、缺口与过载独立确认、多截止候选、截止清除/保留、缺 Note 来源、重复目标、ID/key 冲突、字段无变化、空写集、签名字段变化、输入突变、无副作用。

空业务写集返回“没有需要采用的变更”，不创建 pending 或 applied 历史。只新增已知未排行动属于非空写集，可在缺口确认后采用。

交回：契约精确差异、正式对象映射表、准备结构/签名字段表、纯函数代码、正反例、门禁结果、未覆盖清单。文档必须写明“2A 未实现真实事务采用”，不能提前标 5B-2 完成。

## 6. 2B 保存协议与失败处理

### 6.1 协调预写

用户明确采用后，在一个小事务内核对当前准备身份并写 pending＋草案 applying。预写失败不进入业务提交。同一草案版本最多一份生效信封，双标签必须依靠数据库事务串行判定，不能只靠页面内 Promise 队列。

协调字段足够定位原信封；applying/result_unknown 状态不开放普通编辑绕过待核实结果。旧 pending 失败后保留用于核实，不自动清理。经过已知拒绝并进入新版本后，旧信封不再有执行权；重试必须同时匹配当前草案版本、内容与允许状态，不能仅凭 pending 存在就重放。

### 6.2 一个业务事务

增加专用存储原语，单个 readwrite 事务覆盖 docs、sources、assistant_drafts、assistant_ops、focus_runtime；只有采用时确实追加线程结果才包含 assistant_threads。首版建议结果通过 applied_summary 展示，暂不自动追加消息，避免线程消息上限造成旁路或静默删历史。

IndexedDB 模式属于整个事务：sources/focus_runtime 在该事务里仅用于读取，靠封闭写集限制禁止写入，不能声称同一事务存在 store 级 readonly 模式。

事务内重读并同步比较：

1. 原 application_id 的台账与回执；已 committed 且身份一致直接返回原结果，零写入。身份不一致拒绝。
2. 当前空间、草案、版本、准备身份与采用状态；被其他 application 采用时返回可核实冲突。
3. 全部相关 Task/Action/Note/Source 与当前确认；完整字段比较，不能只看 updated_at。
4. 七日窗口全部占用，含未选中任务的新插入；被修改对象的专注/历史保护、当天 order、跨午夜边界。
5. 冻结写集对应的来源内容版本与元数据；内容摘要在事务外完成，事务内复查绑定。禁止 await Blob/WebCrypto/网络等非 IDB 异步。

全部通过才写：Note 确认、Task 新建/更新、Action 新建、PlanItem 新建、草案 applied+summary、ops committed+receipt。新 ID 用 add 或等价存在性保护，不用 put 静默覆盖。任何业务写失败，全部业务与成功回执回滚；先前 pending 可以保留，不把它当成功结果。

成功只在事务 oncomplete 后报告。缺口采用不改变未排工作为完成；现有日程缓存通过提交后刷新更新，刷新失败不能重做业务提交。

### 6.3 结果分类

| 结果 | 对外说明与后续 |
| --- | --- |
| 校验/事实冲突 | 未写正式业务，进入待核对并列差异；重新预览和确认，不自动修正后代用户提交 |
| 明确事务中止 | 未写正式业务；保留原信封供显式重试，重试前重新核对；不生成第二套 ID |
| 可能提交但回执读取失败 | “保存结果待核实”；按原 application_id 核实，禁止显示没有写入或直接再建一批 |
| 已提交 | 返回原回执与实际数量；重复请求、刷新与双标签均返回同一结果 |
| 已采用但回执异常缺失 | 保持只读并报告异常；不把草案改回 ready |

核实应与可能在途的提交覆盖相同相关 stores，等待事务顺序后读取权威台账与草案。一次普通查询查不到回执不等于未执行。没有证实未提交前，不允许放弃/编辑后绕开原意图重新采用。

切空间：提交前发现世代改变则拒绝；若已经完成提交，结果带原空间身份，不能导航新空间、清空新输入或在新空间冒出“本页采用成功”。切回后仍能核实原结果。
