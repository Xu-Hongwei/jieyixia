## 2 [P2] structuredClone不能直接复制Vue响应式确认快照

定位：frontend/src/services/focus/service.js:156。

当前入口使用`const input = structuredClone(rawInput)`。这能隔离普通对象，却不能复制Vue的Proxy。命令顶层是普通对象也不够：只要expected、facts或historyConfirm任一嵌套值来自ref/reactive，就会在进入业务校验和服务try/catch之前抛出DataCloneError。

独立复现：

```js
const expected = ref(planSnapshot(planItem))
await service.begin({ ...validInput, expected: expected.value })
```

真实Chromium结果：`Failed to execute 'structuredClone' on 'Window': #<Object> could not be cloned.` 同内容普通对象对照组可正常得到PLAN_SESSION_EXISTS与既有会话ID；响应式版本直接Promise拒绝，连回到已有工作的业务结果也拿不到。

这不是外部库猜测：项目现有PlanEditor正是以ref(planSnapshot(...))保存确认基线，并将frozenExpected.value作为expected提交；PlanDetail也使用ref保存确认事实。当前focus store透传输入，没有递归去除代理。

范围说明：2A没有开放计划UI，不宣称当前普通任务开始按钮已经失效。本缺陷是本轮入口修改引入的Vue集成兼容问题，按已有表单模式接2B会触发；需要在服务边界解决，不能要求每个页面各写一套转换。

## 3 最小修复

项目`frontend/src/services/storage/db.js`已经提供`deepRaw`和`snapshot`：逐层去除Vue代理后structuredClone。复用现有snapshot或等价统一实现，让服务独占快照在排队前生成。

要求：

1. 支持普通对象、顶层reactive对象、普通对象内嵌ref.value，以及historyConfirm中的响应式数组。
2. 不能仅toRaw(rawInput)处理根层，也不能只做浅拷贝；嵌套代理仍会失败。
3. 不冻结或改写调用方对象。深拷贝后仍保持R4“原始输入、指纹、事务与回执同版”。
4. 对协议外、确实无法复制的值，可返回明确输入错误；不能把无法创建快照描述成“数据库保存结果未知”。
5. 补service和真实Vue/Pinia入口测试：响应式确认事实可进入正常业务逻辑；提交后修改原ref/数组不影响实际写入；同输入回放一致，换输入同ID仍被拒。

不需要改契约、DB版本或后端，也不要求扩大本批页面范围。
