# 阶段 5B-1B 草案存储与备份恢复开工单

日期：2026-11-24（北京时间）。承接 [5B-1A 最终人工验收](./2026-11-24-阶段5B-1A最终人工验收.md)、[5B-1 总开工单](./2026-11-24-阶段5B-1本地草案与规则排程开工单.md)、[最新契约差异包](./2026-11-24-阶段5B-1A-契约差异包.md)（含 §11、§12）。

## 1 本批完成后应具备什么能力

**一份七天草案可以可靠保存、继续编辑、查看旧版本，并随完整备份恢复到新空间。刷新、断网、切换空间和两个标签同时编辑，都不会让资料丢失或悄悄覆盖。**

典型验收链路：虚构目标和约束→调用已验收的排程器→保存草案第 1 版→修改预算形成第 2 版→刷新仍能读取两版→导出含原始资料和草案的 ZIP→恢复到新空间→内容和引用正确、状态待核对、原空间不变。

这一步仍然只保存助手线程与草案。正式 Task、Action、PlanItem、FocusSession 的批量采用属于 5B-2；模型接口属于 5B-3；完整助手页面属于 5B-4。当前不开放“采用草案”按钮，不把预览段放入正式日程，不通过新增 UI 掩盖数据层缺口。

## 3 实施顺序与交回点

这是一个完整批次，内部按以下顺序实施，不把中间状态当作可交付版本：

1. **契约与类型归位**：正式 0.5.0、旧 schema 选择、生成类型/限额、版本影响回归。
2. **草案纯规则与引用遍历**：修订、确认、状态、限额、失效检查及类型化访问器。
3. **存储实现**：v4 新 store、原子保存、并发比较、一致快照、清空。
4. **完整备份恢复**：v2 导出/校验/重映射/恢复，与 v1 分支并存。
5. **集成与真实浏览器验证**：隔离 origin 下迁移、并发、离线、恢复失败及重试。

全部完成后提交一次 5B-1B 交回，暂停人工验收。1C 仍负责后续综合验收；本批基础迁移和恢复不能只靠 fake-indexeddb，必须先拿到真实浏览器证据。

## 4 正式契约归位

### 4.1 类型与生成物

以契约差异包的持久化/备份闭包为准，纳入 AssistantThread、AssistantDraft、修订快照、确认、规划输入输出、展示结果摘要及依赖类型。共享已有枚举与基础模型，不复制出两套不一致的同名定义。生产代码不得 import contract/proposals。

保留单一手写来源，正式 schema、typedefs、limits 均可重复生成；迁入后提案可作为历史/协议测试入口，但不能形成两份需要人工同步的运行时定义。新增 oneOf 联合生成与类型收窄回归不能丢失。

task/deadline 确认必须保留 1A 最终规则：id_scope 条件必填；old_value/new_value 显式在场；缺失/undefined 不等于 null；同名 draft/formal 分别绑定。正式 JS 校验、Python 校验与生成 schema 的职责要明确，不能误以为生成 JSON Schema 自动携带所有跨字段业务检查。

### 4.2 版本影响

- contract/frozen/0.4.0 保持原字节和摘要，生成器不覆盖。旧包使用冻结 schema；新包使用正式 0.5.0。
- 所有旧定义逐字段比较；只放行差异包已列出的 AnalyzeResponse/HealthResponse.schema_version 默认值 0.4.0→0.5.0，其余旧业务语义不变。
- healthz/analyze 与包装版本按已批准统一版本路线调整必要声明和断言，API_VERSION、路径、鉴权、重试、模型行为不变。不能以“主要写前端”免除共享契约影响的后端测试。
- 旧 PlanDraft 仍按旧语义处理，不自动转成 AssistantDraft；助手对象独立存放，不伪装 docs 的新 kind。

## 5 草案和线程的服务设计

建议新增 `frontend/src/domains/assistant/{draft,refs}.js` 与 `frontend/src/services/assistant/{context,drafts}.js`，适配既有代码风格。模块命名可小幅调整。

| 服务能力 | 输入与边界 | 结果 |
| --- | --- | --- |
| 创建线程/草案 | 捕获空间；本地 ID；合法建议与规划快照 | 必要关联记录同事务保存 |
| 读取列表与详情 | 显式空间及 ID；验证真实归属 | 当前记录、历史、引用解析状态、读取基线 |
| 修改草案内容 | 当前记录基线、明确编辑命令 | 新 revision 与旧版本快照 |
| 确认字段或变更状态 | 当前记录基线、当前 revision、完整确认 | 只修改该版本合法确认/状态，不创建业务对象 |
| 重新排程 | 当前草案及当前空间事实 | 真实 normalize/schedule/validate 结果，不另写简化算法 |
| 保存/重试 | 冻结目标记录、原读取基线 | 已保存事实或明确冲突/失败 |
| 放弃草案 | 当前基线、显式操作 | discarded，保留内容可读 |

不提供任意 `putAssistantObject` 给上层绕过规则；底层原语仍需检查空间、形状和关键不变量。自动生成的记录由本地服务赋 ID/时间，不信模型提供的持久化身份。

### 5.1 修订与确认

- 目标、需求、范围、估时、依赖、规划窗口或事实基线的实质修改产生新 revision；旧版本保存为只读快照。
- 保存同一内容、重复读取、同输入重新计算不凭空增加 revision。
- 同一版本的确认与状态更新可不增加 revision，但仍必须经过完整并发基线校验。
- 新 revision 不自动继承旧版授权。用户可见历史内容保留，旧确认不能成为新版本的 ready 依据。
- 草案的 planning_input 与 planning_result 必须属于同一次计算/同一版本。计算后有人编辑、切空间或改变相关事实，旧结果不再覆盖新记录。
- revision 最多 20，history 最多 19，草案 JSON UTF-8 总体积≤1MiB；线程最多 200 消息、每条≤16000 字符。越界原记录不变，不静默剪历史。用户显式新建草案可复制可读内容，但重建身份并清除原采用授权。

### 5.2 状态规则

按照冻结状态机持久化 editing/needs_clarification/needs_review/ready/discarded 等合法状态。ready 必须由服务核对估时、事实、引用、确认、硬约束、缺口与过载独立确认后推导，不能仅凭 result.complete 或页面传值。

不为保存草案写 applying、pending 信封或 adopted 成功；本批没有采用能力。备份中的 applied 作为历史只读兼容记录处理，不允许转回可采用状态。

本库刷新时 generating 按中断规则处理；遇到 applying/result_unknown 只保留待核实表达，不能因为本批没实现采用就称“没有写入”。恢复到新空间是另一条路径，见第 9 节。

## 6 并发与事务规则

### 6.1 不能只比较 revision

另一标签可能在同一 revision 内修改确认或将草案标为 discarded。单看 revision 会把这些变化覆盖掉。每次写入必须同时验证**完整的已读取记录基线**，至少覆盖内容、状态、确认、历史及所关联的线程变化。

推荐沿用不可变快照和同步规范化内容比较：调用时冻结 expected record；事务中读最新，再比较完整持久形状。也可使用由完整内容派生的比较标识，但不能仅用 updated_at 时间戳充当版本锁；同毫秒更新也要检出。所有摘要计算在事务外，事务内只同步比较。

| 场景 | 必须行为 |
| --- | --- |
| 两标签从相同基线同时修改 | 第一份成功，第二份返回冲突，不覆盖；保留第二份未保存输入 |
| 内容未变但另一页改变确认/状态 | 同样冲突，不能把 discarded 覆盖回 ready |
| 重复保存同一冻结目标 | 若库中已是同一目标且身份/空间一致，返回已保存，不重复历史和消息；否则重新核对 |
| 事务提交前切空间 | 拒绝或 abort；不能写入新的当前空间 |
| 已提交后切空间 | 返回捕获空间的真实保存结果，不虚称回滚；当前页面不把旧空间结果渲染成新空间内容 |
| 输入对象在等待期间被修改 | 写入仍依据调用时冻结快照，不能被后续突变污染 |

线程与草案都参与一次命令时，两者在同一事务比较并写入。仅保存一个草案时，不写回陈旧的整份线程对象。消息追加也要基于事务内最新记录，不能丢掉其它草案刚追加的消息。

### 6.2 事务纪律

IndexedDB 的 mode 属于整个事务，不能给同一个事务的每个 store 分配不同模式。事务内部不 await Blob、WebCrypto、网络、压缩或定时器；这些操作在准备阶段完成。事务完成事件后才返回“保存成功”。错误/配额/中止时相关写入全部回滚。

本批草案写事务只改变助手对象；需要联合读取业务事实时可把相关 store 纳入同一事务，代码约束业务 store 只读用途。禁止为了得到“原子”效果拆成先存线程再存草案两个独立事务。

## 7 数据库 v4 与生命周期

| store | keyPath | 索引 | 本批用途 |
| --- | --- | --- | --- |
| assistant_threads | id | by_workspace(workspace_id) | 对话与已确认要求 |
| assistant_drafts | id | by_workspace(workspace_id)、by_thread(thread_id) | 当前草案及版本历史 |
| assistant_ops | application_id | by_workspace(workspace_id) | 只建空 store，为 5B-2 留正确主键 |

只新增 store 和其索引，不重写 sources/docs/workspaces/focus_runtime，不批量修补旧 Focus。索引查询后仍验证 workspace_id，不能因为 thread_id 命中就信任跨空间结果。

保留 onversionchange 关闭连接和 onblocked 可重试错误。迁移失败不能显示升级成功；旧 v3 前端打不开已升级 v4 是已知边界，回退依靠升级前留存 v1 备份，不提供静默降库工具。

`clearWorkspace` 必须在同一事务清目标空间的 sources/docs/focus_runtime 及三个助手 store。**assistant_ops 删除键是 application_id，不能继续复用 store.delete(rec.id)。** 清空只作用于指定空间，不动个人空间，不遗留演示空间旧对话、草案或台账。

本批放弃草案采用软状态 discarded，不新增通用硬删除线程功能。资料/任务/行动按既有删除入口处理，助手历史不级联消失；下次读取/继续编辑/重算/ready 判定前重查引用。撤销删除后重新核对，不自动恢复旧授权。

## 8 引用规则落为代码

建立类型化访问器注册表供校验、失效检查和重映射共用；返回实际路径、目标类型、命名空间、引用用途。不能用 JSON 全文替换或仅按字符串命中映射表判断。

除差异包完整表外，本批明确补查以下容易漏掉的路径：

- `task_proposals[op=update].changes.deadline_candidates[].evidence_refs`，不能只遍历 create 和顶层证据。
- `UserConfirmation.object_id_or_key`：task 根据 id_scope；其它类型按固定命名空间。正式 ID 重映射，draft key 不动。
- 当前 proposal/planning_input/planning_result/requirements 与 revision_history 中同类字段全覆盖。
- typed requirement.value 内的任务引用/工作项 key，不能把开放 JSON 当普通正文全部跳过。
- applied_summary.id_map 的 formal_id 为历史对象关联；application_id 只是原采用事件追溯标识，不查找或重建新空间 ops，不赋予执行权。
- turn_id 与线程内消息身份按已冻结局部命名空间保留；正文、quote、标题里出现相同 ID 字符串仍为原文。

**助手快照中的引用与当前正式业务活引用要分开校验。** 例如旧草案 planning_input.occupancy 引用的 PlanItem 后来被删，这是历史快照失效，可保留内容、隔离映射并 needs_review；不能仅因快照 state=planned 就拒绝整个备份。相反，当前正式 docs 中 planned PlanItem 的活 Task 引用损坏，仍按既有业务规则拒绝，不能用助手历史宽容规则放行。

draft.thread_id 必须指向同包同空间线程；这类容器归属损坏拒绝整包，不能静默丢草案。历史缺失对象不伪造实体、不关联到原空间，引用状态在读取时计算；不私加未注册 deleted 字段。以上分类需给出逐路径机器测试。

## 9 备份 v2 与恢复

### 9.1 导出一致快照

扩展现有 readWorkspaceSnapshot，在**一个 readonly 事务**读取 workspaces/sources/docs/assistant_threads/assistant_drafts。用户切空间也按捕获 wsId 导出，不串空间；之后的 Blob/JSON/摘要/压缩均在事务外。

v2 必需 payload：原 sources/docs 与新增 data/assistant_threads.json、data/assistant_drafts.json；空数组也写入。计数、字节数、SHA-256、schema 版本一致。ZIP/解压/单 JSON/图片/条目限额不放宽。

不导出 assistant_ops、信封、可执行写集、在途请求、租约或所有权。按正式类型白名单验证，不把未认识字段悄悄剪掉后宣称完整备份。无需为本批增加导出旧格式按钮。

### 9.2 分版本校验

| 输入 | 行为 |
| --- | --- |
| v1 + schema 0.4.0 | 用冻结 schema 和既有业务规则，助手为空；旧记录不被追溯收紧 |
| v2 + schema 0.5.0 | 校验两助手 payload、计数/摘要、版本、状态、引用、大小及记录归属 |
| 错误组合/未知版本 | 明确拒绝，不能忽略助手部分后继续恢复 |

单草案 1MiB、20 版本、线程/消息上限导入同样执行。校验必须覆盖 JSON 安全性和类型业务守卫，不能仅用生成 schema 代替全部规则。

### 9.3 准备、映射与去授权

prepareRestore 冻结本次新空间 ID、对象 ID 映射、线程/草案 ID、原 ZIP 摘要及作业身份；重试复用同一份 prepared，不重新随机分配。

活对象全量新 ID，历史缺失引用使用稳定的隔离映射。正式 ID 与局部 key 恰好同名也分别处理；助手映射纳入现有 idMapSignature。检查冲突范围包括新增 store，不允许恢复目标与已有助手对象撞 ID。

未应用草案恢复为 needs_review，清除当前事实基线和可执行确认，保留建议、规划与历史供阅读。恢复预览说明原状态，恢复后的文案统一说明“旧保存结果不能由本次备份恢复推定，须重新核对”，不把原 applying/result_unknown 宣称为未提交。

applied 保持只读历史，discarded 保持放弃。历史里的确认/已确认要求即使保留用于解释，也不能作为当前草案授权输入；`extra_work_acknowledged` 等旧计算输入仅作旧预览，不直接拿来重新排程。不得为了展示保留原授权对象在可执行字段中；不得添加未登记的恢复字段。恢复后 0 个新采用操作、0 个自动生成 PlanItem。

### 9.4 原子提交与回执

现有 commitRestore 事务扩展 assistant_threads、assistant_drafts；目录、资料、docs、focus_runtime、助手记录全部 add，任一步失败全回滚。assistant_ops 不导入，也不根据 applied_summary 重建。

继承 operation_id、原始 ZIP 指纹、backup_id、目标名、ID 映射签名的幂等绑定，扩展助手计数与映射。相同意图已提交返回原结果；不同意图占用/绑定不一致拒绝，禁止自动换新 ID 重做。

verifyCommittedRestore 必须实际重读目标空间，核对助手记录数量、身份、内容转换、引用、状态及无 ops；不能只校验两项计数。旧 v1 恢复回执无新助手计数字段时按 0 解释，不改写旧回执。

## 10 前端接入范围

本批不新增正式助手路由，不重排页面导航。现有备份预览/结果页可做必要的小幅适配：显示线程数、草案数，以及恢复后需核对的提示；原 v1 包仍正常展示。

开发验收入口只在隔离环境调用真实服务，不写第二套模拟保存逻辑，不进入生产构建或正式导航。使用虚构数据和独立浏览器配置/origin，禁止把用户个人空间作为故障注入对象。
