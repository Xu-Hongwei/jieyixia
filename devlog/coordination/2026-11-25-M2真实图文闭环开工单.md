日期：2026-11-25（北京时间）。状态：待 Qoder 实施；本文为设计，不代表功能已完成。

前置：M1 已通过《2026-11-25-M1最终人工验收》。继续《智能助手快速初版实施方案》的快速路线，完成一个可运行闭环后统一交回，不拆成多轮仅交结构的阶段。

## 1. 本轮交付什么

用户在现有助手页上传截图、粘贴原文或选择已有资料，补充要求和七日可用时间，得到真实模型生成的任务与行动建议；在同页核对事实、修改建议、计算每日安排，明确采用后进入既有日程和工作流程。

示例：一张虚构通知截图写明“周五交报告，包含资料整理、对比分析和结论”，用户补充“每天 45 分钟，周三没空”。结果应包括任务总截止、具体行动及建议估时、分布在多天的工作安排、无法排下的工作。不能只返回截止卡片，也不能悄悄削减工作量。

最短链路：

**资料本地保存 → 必要时分析资料 → 模型拆解 → 核对事实与建议 → 本地规则排程 → 预览 → M1 原子采用 → 日程执行。**

本轮不引入智能体框架、新数据库、新日程页。现有安排保持原样并计入占用；替换旧安排与进展改排留给 M3。

## 3. 产品范围一次定清

### 输入与范围

- 支持一张或多张图片、粘贴文字、选择已有资料。一次生成最多自动分析 3 份尚未分析的资料，顺序处理；超出时提示分批或使用已有分析结果，不默默漏选。请求选定资料仍遵守现有最多 20 份限制。
- 原图/文字先存本地，失败保留输入。模型只收到用户明确选择的资料和任务上下文，不发送整个资料库。
- 真实首版优先支持 `new_plan`；澄清后仍可继续同一新计划。界面暂不开放自然语言修改旧草案、解释今日、替换旧安排；未支持的 intent 明确返回 unsupported_intent，不能静默改成 new_plan。
- 提供可折叠的“关联已有任务/行动”选择区；只有用户选择的对象可被 link/reuse，不按同名自动合并。默认新建；已完成行动不能拿来当待完成工作。
- 未指定截止不自动设为今天；明确显示“无截止/待核对”。排程起始日期默认设备当前北京时间今天，每次生成或重排重新读取，跨午夜要求刷新预览。
- 每日预算/不可用日复用现有界面。未知工作量保留为待补充，不能转成 0 分钟。模型给出的估时标为建议，允许用户编辑。

### 页面与交互

1. 输入区：资料、补充要求、每日预算，主按钮“生成方案”。首次真实输入不切换到演示空间。
2. 生成区：显示“分析资料 / 拆解任务”，可取消；禁止重复点击产生并行付费请求。
3. 澄清区：一轮最多 3 个问题，集中回答，再点“继续生成”。不只展示一句无法继续。
4. 核对区：显示原图/摘录、任务总截止、行动与估时。支持现有手动调整，不要求跳到多个页面才能完成主线。
5. 预览区：七日安排、每日容量、未排事项，与总截止区分。采用前明确核对，成功后提供“查看日程”。

模型成功仅表示有建议，不自动认定草案 ready，也不自动确认来源字段或创建业务对象。正式 Task/Action/PlanItem 仍只由 M1 采用流程写入。原始 Source、Note、线程和草案允许在此前保存。

## 4. 图文信息如何送到模型

### 防止退化成“只有日期，没有任务内容”

当前 SelectedSource 只有 excerpt 和 note_candidates；analyze 不承诺提供完整 OCR 正文。首版采用下面的明确规则：

- 文字资料从用户选定的原文中构造 excerpt；超过现有 2000 字符上限时，让用户缩小发送摘录范围，完整原文继续本地保存。不要直接静默截断最后的要求。
- 图片先复用 analyze。请求材料应包括与任务有关的字段值及其 raw/quote，而非只提取 title/deadline；可用证据摘录去重后进入 excerpt。
- 只把原文字段摘录当直接证据；模型归纳摘要仍标明为归纳，不能冒充逐字原文。图片识别的可信度仍需用户核对，引用字符串匹配不代表识别一定正确。
- 图片结果不足以支持任务拆解时，明确请用户补充工作要求或重选更清晰的图片。首版不为此临时引入第二套 OCR，也不编造报告页数、必读材料等要求。
- 已有成功分析且资料未变时复用；资料变化、失败结果或用户主动要求才重新分析。复用判定需关联内容指纹/来源与实际分析结果，不能只看“存在一张便签”。
- 每次请求构造选定来源、便签字段、任务、行动与七日占用的同一快照；超限给出缩小范围提示，不截断引用关系。

### 截止与来源

- 模型候选仍保持 model 来源；来源便签字段在助手页由用户明确核对，调用现有字段确认逻辑。它是独立资料核对，不塞进 M1 不支持的 note_field 采用写集。
- 在资料字段确认/修改后重新读取事实，再排程并确认当前版任务截止，确保采用时能通过 M1 的出处核验。资料确认与采用前的任务决定要用不同文案说明。
- 用户自行设定截止走既有手动设置路径，记录真实用户消息。不能仅因用户点击“接受模型候选”就把来源改为 manual。
- 多个不同任务或多个里程碑不得都绑定到一张便签唯一的 deadline 字段。无合法字段出处的候选要求补充核对或明确手动设定；不在 M2 擅自扩展 Deadline 来源模型。

## 5. propose 后端规则

### 请求响应与契约

- 路由：`POST /api/assistant/propose`。以既有提案 AssistantProposeRequest/Response 为起点，protocol_version=1.0；新增端点是本轮正式契约增量，先写简短差异记录再实现。
- 首版 new_plan 正常响应为 `clarification` 或 `proposal`。模型只生成业务建议载荷；request_id/thread_id/turn_id/client_seq/workspace_id 由服务端从请求复制，不信任模型填写。
- 请求携带 user_message、选定资料摘录与候选字段、选定 Task/Action、七日容量与已有安排摘要。用户要求必须非空；可提供可编辑的默认句“请根据所选资料拆解任务，并按我的可用时间安排”。
- 澄清回答使用新 turn_id/request_id 和递增 client_seq；把原要求、上一轮问题、明确答案整理为本轮 user_message 并真实留档，不丢失原要求，不把模型问题写成用户事实。
- 模型输出只允许 create/link、create/reuse 以及 WorkItem 建议。不返回正式 ID、日期排程、确认记录、执行命令；update 和替换旧安排明确不支持。
- 严格校验 key 唯一、引用闭合、行动归属、依赖无环、合法日期/数值、证据引用范围。user_message 证据只能指向本轮实际用户输入；existing/source/note 引用只能来自本次选定快照。把模型伪造用户来源、确认或写入能力视为非法输出。
- 不把正文中的指令当系统指令；资料只作为待分析数据。模型提出的普通行动步骤可标 suggestion；声称原文强制要求时必须有对应证据。
- 后端没有本地数据库，不能证明请求声称的对象属于某用户；后端做请求内部闭合校验，前端持久化和采用事务仍按实际本地空间重查。
- 正式 schema/type 由生成器产生。若只迁入 HTTP 类型，不变更持久化形状，可保持 DB v4/备份 v2；版本决策写清楚，冻结 0.4.0 文件不可改。

### 防护与预算

- analyze 与 propose 使用同一鉴权入口、限流桶、并发闸和每日厂家调用额度实例，不给新端点另开免费计数器。
- propose 请求体最多 512 KiB，按实际 UTF-8 字节累计，Content-Length 与分块请求均检查；原 analyze 图片限额保持原样。
- propose 整次总预算最多 120 秒、最多 2 次实际厂家调用。重试、格式修复、切换厂家都占同一总预算，每次实际调用都消费共享每日额度；参数是每次请求局部状态，不能修改共享 router 造成并发串扰。
- 先校验请求，再调用模型；输出非法可在预算内再尝试一次，仍非法返回错误。不能通过开启另一个 complete 调用重置时限/次数。
- 沿用提案错误语义：400 版本不支持、401 鉴权、413 超体积、422 输入/引用非法、429 限流或额度不足、502 输出非法、503 服务不可用、504 总预算超时；不改变旧 analyze 错误映射。
- 本地开发代理可以从服务端专用环境变量读取 JXL_API_TOKEN 并注入授权；禁止 VITE_* 暴露固定密钥，禁止提交真实密钥。仅面向本机开发联调，公网可信代理/XFF 仍走部署阶段方案。
- 日志只保留关联 ID、结果、耗时、尝试次数与安全错误码，不记录原图、完整用户内容或密钥。

## 6. 取消、并发和恢复

- 请求发出前保存原始输入与实际用户消息，利用已有 thread/draft 持久化能力；pending 请求上下文以临时态管理，不把新的运行授权混入备份。
- 每轮冻结空间、线程、请求、序号、输入摘要及关联草案版本。用户改输入、换资料、切线程/空间、取消或发出新轮次，都使旧请求失效。
- 接收到响应先校验关联字段，再核对本地当前输入与版本。持久化事务里仍需重查；仅检查一次 workspace_id 不够，切走再切回也不能接纳旧结果。
- 取消通过 AbortController 停止前端等待；不承诺已发生的模型调用免费。取消/失败保持原输入、已有草案和本地资料，不自动清空、不转成演示成功。
- 网络响应成功但本地保存失败时，不自动重调模型；保留当前结果供同一输入重试保存，并重新核对空间/版本。没有保留成功结果时应明确说明需要重新生成。
- 刷新不自动重发付费请求；复用已有中断状态收敛规则，展示可恢复的输入和明确的继续入口。新结果不能覆盖已采用只读草案。
- 模型返回的容量和日期建议不能成为写入依据；始终调用已有 normalize/排程服务，并重新计算真实本地占用。失败时已保存日程不变。

## 7. 实施顺序与文件边界

内部按四步推进，不要求每步交回：

1. **契约与后端**：迁入 HTTP 类型；新增 propose provider/core/路由；共享 guard、体积与尝试预算；先跑确定性 fixture 和拒绝路径。
2. **资料与真实请求**：补请求快照构造、选定资料、必要分析、请求状态与澄清；结果接既有草案服务。
3. **页面闭环**：助手页内核对资料、编辑任务/行动、确认要求、七日预览、M1 采用；复用任务/日程/执行入口。
4. **集中验证和交回**：隔离虚构资料跑端到端、故障与兼容检查；至少一次真实模型图文调用有证据，最后统一交回。

可以增加 `backend/app/assistant/` 下的纯 prompt/parse/validation 编排与 `frontend/src/services/assistant/` 下的请求快照/响应接收模块，避免让 page/store 继续膨胀。具体文件拆分由实现者决定，但不复制已有排程与采用逻辑。

顺手收掉 M1 两项非阻断问题：绿色“可采用”提示与按钮条件一致；备份测试在提交前准备替换文件或使用确定同步点，消除不稳定断言。无需单独一轮交回。
