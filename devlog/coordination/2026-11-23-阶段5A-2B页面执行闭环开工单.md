## 1 交付目标和边界

让用户通过真实页面完成：

**日程找到某天的安排 → 确认要做的行动 → 开始工作并写成果 → 分别确认行动结果、安排进度 → 回原日程看见结果 → 必要时另安排一天。**

例：任务“周五交报告”，周一安排“整理资料”。本次执行行动“阅读三篇参考文献”。结束时可以选择“行动尚未完成，但周一安排已完成”。任务的周五截止不变；继续阅读时可以另建周二安排，也可以从任务直接开始独立工作。

| 对象 | 用户理解 | 本批不改变的规则 |
| --- | --- | --- |
| Task任务 | 最终要交付的目标 | 总截止独立，任务完成仍由任务详情负责 |
| Action行动 | 实际执行的步骤 | 按ID选择，只有明确选“行动完成”才完成它 |
| PlanItem安排 | 某天准备做的工作 | 日期属于安排；说明不是Action绑定；可跨多天建立多项安排 |
| FocusSession工作记录 | 某一次真实投入和成果 | 关联安排可为空；开始后不能通过URL改挂安排 |

沿用统一日程的“上方每日安排、下方每日截止”，不新增一套日程或执行页面。沿用现有样式，只增加必要上下文和操作，不做整体视觉改版。

不改后端/API/契约0.4.0，不升级DB v3；不新增PlanItem.action_id、doing状态或历史快照字段。不做自动拆解、自动排程、拖拽、提醒推送、自动顺延及多截止模型。

2A已经具备事务级开始校验、结束原子保存、累计摘要和请求绑定。本批消费这些能力，不另写页面版业务规则，不以第二次confirmProgress补写结束结果。若接入发现底层缺陷，记录可复现问题和必要修复范围，不能以页面绕过校验代替修复。

## 2 页面分工：各页只承担明确的职责

| 页面/组件 | 本批职责 | 主操作 |
| --- | --- | --- |
| 日程与PlanDetail | 找到哪天做什么、看安排进度和实际投入 | 开始这项安排 / 回到工作 |
| 共享开始确认面板 | 核对安排和实际Action，确认执行风险 | 确认并开始 |
| TaskDetailPage | 维护任务、选择或新增具体行动 | 在明确安排上下文中开始；普通入口保持独立工作 |
| WorkPage | 计时、成果编辑、暂停和恢复 | 结束本次工作 |
| EndSessionForm | 一次确认两种结果 | 结束并保存 |
| WorkRecordDetailPage | 查看已保存的实际记录和出处 | 返回安排 / 返回来源 |

安排卡继续承担摘要和进入详情的职责，卡上不堆开始、暂停、完成、删除等一排按钮。任务详情的“查看所属任务”和“去任务选择行动”是不同入口：前者仅浏览，后者才带显式执行安排上下文。

## 3 从安排开始：先决定身份，再真正开始

### 3.1 安排详情入口优先级

页面预检查用于解释，最终资格仍由focus.begin事务决定。

1. **同空间同安排已有未结束会话（运行或暂停）**：主按钮“回到工作”，导航到该真实会话。优先于当前行动和旧历史检查；即使Task.current_action已变，也不能错失这个入口。绝不新建、自动续计时或接管。
2. **没有该安排未结束会话，但本空间另有未结束工作**：显示“先处理已有工作”，提供查看入口；不能因为Task/Action相同就误认为同一安排。
3. **其它空间有运行会话**：复用现有冲突说明和显式切换入口；取消不改变任何会话。不因点击本安排自动切空间、暂停别人或抢占。
4. **安排/任务不具备开始资格**：终态、断引用、任务已完成等显示原因；不提供可提交的新开始操作。合法历史仍可查看。
5. **旧planned有已结束历史**：先提示“核对已有进度”，复用原进度核对入口；异常历史显示待核对原因和已有记录，不当作无投入的新安排。
6. **planned/partial且资格满足**：主按钮“开始这项安排”，打开共享确认面板。

task/action相同但plan不同，或者一个plan为空，均不是同一安排工作。普通任务入口若遇到已有计划会话，可提示并查看已有工作，但不能冒称这是新开始的独立工作。

### 3.2 确认面板内容

建议纵向紧凑呈现，360px手机可滚动：

```text
开始这项安排
所属任务：周五交报告
安排日期：11月23日 · 今天
安排说明：整理资料          安排预计：30分钟
将执行的行动：阅读三篇参考文献    行动估时：45分钟
任务总截止：11月27日（按原精度显示）

去任务选择行动        取消        确认并开始
```

- 有有效当前Action时展示名称和估时，用户仍需明确点击开始。无有效Action时禁用开始，提供“去任务选择行动”。不自动选第一条，不按相同文字匹配，不自动创建Action。
- 用户去任务页选择/新增Action后，在该页通过同一确认流程开始；不要求先回日程再点一次。安排日期、说明、预计分钟不能覆盖Action内容。
- Task为blocked时，同一面板展示“开始后任务将转为进行中”的明确确认；未确认不提交confirmBlocked=true。
- 安排日不等于北京时间今天时，明确提示提前/延后执行，点击开始确认这个事实；原安排日不改，实际开始时刻按真实时钟记录。
- 任务截止是独立信息，过期仅提示风险，不禁止真实记录、不自动改期。无时间的日期不伪装成23:59。
- 日程“今天”和无日期初值继续以北京时间为准。确认跨北京午夜，要求重新核对日期关系。

### 3.3 冻结与重确认

打开面板时捕获：workspace、taskId、actionId、planItemId、planSnapshot六字段，以及beginFactsOf得到的行动/任务/截止/北京时间日期事实。面板显示值与提交值必须来自同一个快照。

事实变化时保留选择，显示完整差异，允许取消或核对后重新确认；第二次变化仍再次核对。禁止弹窗里显示旧行动、提交时却读取新的currentAction。

任务页存在未保存编辑时，沿用既有离开/放弃确认：取消后保留编辑，不创建会话；明确保存或放弃后，才基于已持久化记录打开开始确认。不能把未保存的Task/Action草稿塞给begin。

计划上下文失效时停住并提示，给“返回日程”或用户明确选择的“按独立工作继续”；**不能移除plan参数后直接执行原来的开始点击**。

## 4 路由与上下文规范

复用现有hash路由，不加新顶级页面。建议统一以下参数，抽一个纯路由helper解析和生成，避免各页手拼嵌套URL。

| 场景 | 路由语义 |
| --- | --- |
| 日程安排详情 | `/today?date=YYYY-MM-DD&view=list或week&plan=安排ID`；沿用现有默认值省略规则 |
| 为安排选行动 | `/tasks/任务ID?plan=安排ID&return=规范化日程地址` |
| 从安排进入工作 | `/work/会话ID?return=规范化日程地址`；实际plan身份读取session |
| 普通任务进入工作 | `/work/会话ID?return=规范化任务详情地址`；保留既有返回列表上下文 |
| 从安排看记录 | `/work-records/会话ID?return=规范化日程地址` |

规则：

1. 只有Task详情的**显式plan参数**可以表达“为该安排选行动”。不能从return字符串内碰巧出现的plan推断绑定。
2. 校验当前空间、PlanItem.task_id和当前Task一致、引用有效。跨空间目标只提示无效，不自动切空间。URL不是授权或业务事实。
3. return只接受精确匹配的已支持站内路径及已知查询参数；拒绝外站、协议相对地址、未匹配路径和对象不属于当前空间的地址。不要只用startsWith('/tasks')判定合法。
4. 返回上下文按“工作→任务→日程/资料库”或“工作→日程”有限结构生成，禁止把当前fullPath反复包成新的return。保留现有合法筛选/视图字段，丢弃与本次导航无关的临时操作参数。
5. session存在真实plan关联而return丢失/非法时，根据当前空间中的真实PlanItem构造安全日程目标。普通独立会话退回所属Task；对象不存在则回当前空间安全列表。
6. 返回日程恢复来源日期和视图，定位目标安排，必要时展开完成历史；若来源日期无法包含目标，使用目标安排日使它可见，并说明已定位。手机也要选中对应日。
7. 前进/后退、刷新深链接、同组件参数变化只加载和校验，不自动begin/end/恢复计时。切目标或空间时，旧确认、错误、请求、结果选择不得串到新对象。
8. 所有返回入口必须经过现有草稿/运行中离开保护，不用直接跳转或全局bypass绕开。提交真正成功后的程序化导航可按原成功路径处理。

## 5 工作页：补充上下文，成果仍是中心

计划会话在现有任务/行动信息旁增加紧凑块：

```text
正在做：阅读三篇参考文献
所属安排：整理资料 · 11月23日
安排预计30分钟 · 已结束工作累计1分20秒
任务总截止：11月27日                 返回安排
```

本段计时继续单独显示，不把它混进“已结束工作累计”。不按视觉计时反复写PlanItem.actual_minutes；摘要异常显示待核对，不能显示成0。

真实行动名称/任务名称优先沿用会话已有快照及现有信息变化提示。安排说明读取当前PlanItem，要标明是当前安排信息，不冒称为开始时历史快照。没有计划的工作页不显示空安排块。

“返回安排”走原有离开保护：运行中明确保存并暂停后离开，取消则留页；暂停会话也先处理草稿。再次回到工作必须主动继续，不因导航续计时。

正常v1关联损坏时保留正文和可定位原因，不能自动解绑或降级legacyEnd；现有暂停、草稿保存、恢复核对等仍在各自资格允许时可用，不能把整页做成无法取回内容的死路。

## 6 结束表单：两个独立结果，一次保存

### 6.1 可见内容和默认值

| 分组 | 选项 | 新会话首次打开初值 |
| --- | --- | --- |
| 这次行动的结果 | 行动完成 / 部分完成 / 被阻塞 | 部分完成 |
| 这项安排的进度 | 还需要继续 / 这项安排已完成 | 还需要继续 |

两组同时展示，不能折叠成一个“完成”开关，不能根据一组自动代选另一组。blocked必须填写卡点，三乘二的六种组合全部允许；blocked+done也保留卡点，不新增安排blocked状态。

显示安排日期、说明、已结束历史累计，并说明“本段有效用时将在保存时结算”。初次打开时冻结expected及historyConfirm：后者只含已有已结束会话，无历史为null，不含当前未结束段。

取消仅关表单，不结束、不暂停、不写安排进度。同一workspace+session内重新打开保留已选结果和卡点；因恢复核对关闭后也保留。重新打开需重新检查当前事实；有变化则显示差异再确认，不把旧选择误认为对新事实的授权。切会话/空间使用独立状态，不串值。

独立会话不显示第二组，提交时完全省略计划专属参数。不能用空对象或自动partial伪装“无安排”。

### 6.2 本次提交与重试必须同版

按以下顺序接入已有focus.end：

1. 校验表单，锁定本次目标workspace/session，冻结编辑输入并等待已有草稿保存队列结算。
2. 结算后若出现正文冲突、目标切换或失去操作资格，停止本次结束并保留输入；不能继续使用提交前的修订号。
3. 捕获不可变提交对象：sessionId、outcome、blocker、最终draftMd、**expectedRevision**；关联安排时再含planProgress、expected、historyConfirm。end不传planItemId。
4. 首次提交签发请求信封；同输入重试复用信封、正文、修订前提和所有确认事实。expectedRevision已进入服务输入指纹，不能在重试时从live状态取新值却沿用旧ID。
5. 成功后核实持久记录，清理已完成会话草稿和本次表单，再导航。所有异步返回先核对当前workspace、session/入口目标和页面意图是否仍一致；晚到成功不能抢走新页面或清空别的草稿。
6. 结果未知时保留原请求及输入，先以原请求核实/重试，不重新签发请求盲目再开始或再结束。若允许用户继续编辑，要将新草稿和待核实旧提交区分；本批优先采用“待核实期间锁定提交输入，提供重试/核实”的简单路径。
7. 明确未提交后，用户修改结果、正文或重新确认事实属于新意图，签发新信封。单纯重试不得悄悄刷新expected/historyConfirm。恢复/冲突处理改变了修订或事实时，同样需要新确认。

复用服务层对响应式对象的深快照支持；页面不要另造JSON序列化协议，也不能把“服务已拷贝”当成页面可以丢失重试输入的理由。

提交期间锁定两组结果、卡点和正文，防重复点击/Enter；也要约束Esc、遮罩关闭、同组件换目标等路径。保存失败保留内容和可恢复状态，不误显示“已经保存”。浏览器刷新前有未解决输入时给现有离开提示；不新增刷新后自动重放，不宣称关闭浏览器后的未提交表单已持久保存。

### 6.3 遗留会话适配

保留单独的遗留结束语义：

- v0无安排：原显式结束流程，不新增自动Action完成。
- v0有效活安排：在遗留表单明确增加安排结果与确认快照，通过legacyEnd同事务保存；不能套用正常v1的“完成Action”承诺。
- v0引用缺失/安排终态等既有例外：明确提示“可结束遗留记录，但本次无法更新安排”，沿用已验收释放占用路径，不修造关联。
- 正常v1不得借此例外绕过安排校验。

本批需验证上述页面入口确实可操作；2C再做更广的旧数据、删除和恢复组合。

## 7 成功返回、记录与另安排一天

开始成功/已有同安排会话返回时使用稳定`session_id`，兼容结果仅有该字段；重新读取并验证实际会话后导航，不能假定`r.session.id`总存在。刷新失败只重试读取，不能再次创建。

关联安排结束成功：

1. 原子保存由服务完成，页面不再调用planStore.confirmProgress。
2. 等待当前空间资料与会话刷新，回原日程并定位安排；done已折叠也能看见目标。partial/blocked必须即时更新，不依赖Action/Task变化触发刷新。
3. 提示真实保存结果，例如“本次工作已保存 · 行动部分完成 · 安排已完成”。“行动部分完成”不表示Task状态已自动改变。
4. 提供“查看工作记录”；原安排仍partial时提供“另安排一天”。已完成安排的继续工作入口保留在已有详情操作内，避免成功提示堆按钮。

结果提示可以复用recorded会话ID，但必须在当前空间读到匹配的已结束记录才展示。旧URL刷新或之后进度变化时，仅说明“这次记录已保存”，不得从当前PlanItem状态伪造当时的安排结果；现有契约没有每段planProgress历史快照，本批不新增该字段。

另安排一天复用PlanEditor.another：日期初值max(原日+1,北京时间今天)，说明/预计分钟可编辑；新ID、新累计空值，不复制会话或历史，不自动扣减预计分钟。原partial仍partial，并提示“新建不会结束原安排”；需要取消旧安排时走原确认流程。Action已完成则明确选择/新增下一行动，不能自动复活。

记录详情如补“所属安排”入口，按当前空间真实关联提供；关联缺失显示事实，不把当前安排说明说成历史快照。保留现有任务/行动快照与返回来源能力。

## 8 错误与恢复的页面处理表

| 服务事实/错误 | 用户看到什么 | 处理要求 |
| --- | --- | --- |
| PLAN_SESSION_EXISTS | 已有这项安排的工作 | 核实稳定ID后回到工作；不是重新开始成功，不续计时 |
| ALREADY_ACTIVE、跨空间运行冲突 | 已有其它工作需要处理 | 查看/明确切空间；不结束、不改挂 |
| PLAN_CONFIRM_REQUIRED | 需要核对安排与执行信息 | 返回完整确认，不补默认事实偷偷提交 |
| STALE_PLAN、BEGIN_FACTS_CHANGED | 安排/行动/任务信息已变化 | 列完整差异，重新确认；第二次变化再次核对 |
| PLAN_REVIEW_REQUIRED | 这项旧安排已有工作记录，请先核对进度 | 回已有进度核对入口，不自动改partial |
| HISTORY_UNCONFIRMED、HISTORY_CHANGED | 已有投入记录需要核对/发生变化 | 展示冻结的待确认摘要，确认新意图；不混入当前段 |
| HISTORY_UNRESOLVED | 历史记录异常，暂不能联动 | 展示问题及可定位记录，保留正文，不自动修数据 |
| TASK_DONE、ACTION_DONE、PLAN_NOT_EXECUTABLE、关联无效 | 明确哪个对象失效 | 返回处理，不能静默独立开始或解绑结束 |
| RECOVERY_REQUIRED、OWNER_CONFLICT、正文修订冲突 | 需要先恢复/核对/处理占用 | 沿用现有流程；保留两组选项、卡点和正文，处理后重新核对 |
| SAVE_FAILED/结果未知 | 未能确认保存结果 | 保留完整原提交，核实/原信封重试，不谎称已失败且零写入 |
| STALE_REQUEST、REQUEST_ENVELOPE_REQUIRED | 原请求已不能直接重试 | 读取当前事实判断是否已完成；核对后才能形成新意图，不自动换ID重提 |
| INVALID_FIELD | 输入无法提交 | 如实显示输入问题，不描述成“数据库结果未知” |
| 空间/目标已切换 | 当前页不显示旧目标成功或错误 | 按作用域丢弃UI回调，后续读取真实记录 |

错误文案可以面向用户简化；交回文档需列真实错误码和对应入口。不能只依靠按钮disabled证明这些分支安全。
