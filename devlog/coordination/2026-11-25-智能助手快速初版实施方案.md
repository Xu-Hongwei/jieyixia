# 智能助手快速初版：合并推进 5B-2 至 5B-5

日期：2026-11-25（北京时间）。当前状态：M1 已通过最终人工验收；M2 开工方案已整理，待实施；M3 未实施。

本文件为当前后续计划入口。按用户要求结合现有框架推进，不重做 5B-1，不引入平行架构。§9 保留 M1 的开工范围作为历史基线；当前下一步以同目录《2026-11-25-M2真实图文闭环开工单.md》为执行入口。M1 结论见《2026-11-25-M1最终人工验收.md》。下文原始顺序和范围保留，实施进度以此处及对应验收报告为准。

用户本轮明确要求“先实现功能，有一个初步版本”。因此暂停独立细化 5B-2A，改按下面三个可见里程碑推进。此前 5B-2 开工单的逐小批人工验收流程不再作为本初版的前置门槛；原文保留历史记录。已验证的数据规则、备份兼容和执行保护仍复用。

## 1. 初版目标

用户上传截图或粘贴文字，补充“每天能做多久、哪些天没空、希望怎么做”，得到任务拆解与七日安排；核对后一次加入现有日程，开始工作并记录成果；之后告诉助手还有多少工作没做完，调整尚未开始的安排。

第一版完成以下一条主线就算具备试用价值：

**输入资料 → 核对关键事实 → 拆解行动 → 规则排程 → 预览并采用 → 日程执行 → 反馈剩余工作 → 预览并调整。**

技术结构继续是 Vue/Pinia/IndexedDB + FastAPI + 现有模型 adapter，不引入智能体框架、工作流引擎或新数据库。模型理解和建议，本地规则算日期，本地事务保存。

## 2. 用三个里程碑代替四个串行大阶段

| 里程碑 | 合并内容 | 用户能直接看到什么 |
| --- | --- | --- |
| M1 看得见、存得下 | 5B-2 最小采用 + 5B-4 页面骨架 | 在助手页使用标明“演示”的固定案例，生成草案、一次采用、打开日程、开始已有工作流程 |
| M2 真实图文闭环 | 5B-3 + 5B-4 核心交互 | 真正上传图文并提出要求，生成可编辑的任务和每日安排，确认后执行 |

每个里程碑保留一个可运行版本、简短交回和真实截图。不再要求为每个纯函数/数据结构单独停一次审查；发现数据丢失、重复写入、越权修改历史或契约不兼容时仍须先修复。是否继续下一里程碑由实际交付指令确定，设计稿本身不等于已开始实施。

## 3. M1：助手页面和最小批量采用

### 页面先做成什么样

新增一个“助手”入口，复用现有导航和视觉组件。桌面左右两区，手机上下切换：

- 左侧：资料、文字要求、每日可用时间、不可用日期，以及本轮反馈输入。
- 右侧：任务与截止、行动清单、七日安排预览、未排工作和一个主按钮。
- 页面流程只有“生成方案 → 核对/调整 → 采用计划 → 查看日程”。采用后草案只读。
- 不堆功能卡片，不做独立多智能体入口。日程与任务页继续负责执行，助手负责生成和调整。

必要可编辑项：任务标题、明确截止或无截止、行动说明/建议估时、此次剩余工作量、每天预算、不可用日。编辑后重算并重新核对；不能在旧预览上直接保存新内容。任务截止和日程工作量分开显示。

### 采用首版范围

- 支持新建 Task/Action，以及明确关联既有 Task、复用既有 Action；不按名称自动合并。
- 为加快交付，暂不开放助手批量修改既有 Task 字段。用户修改既有截止走现有任务页，再回助手重新规划。模型返回 update 时明确提示调整范围或手动修改，不能静默当 link。
- 每个任务、行动只创建一次；每个工作段创建一条 PlanItem。PlanItem 不新增 action_id，执行仍使用已有选择行动流程。
- 只在用户明确采用后写业务。准备 ID 和一次操作 ID 在本地生成，重试沿用同一身份。
- 单事务写正式对象、applied 草案与成功回执；保留最小 pending/结果核实能力。双击、双标签、刷新不重复创建。
- 提交前重查草案身份、完整相关对象和全窗口占用；有变化则停止并要求重新预览，不自动换一份方案提交。
- 无法确定是否保存成功时显示“结果待核实”，按原操作 ID 查询；不得直接再创建一批。
- 未排下的已知行动保留，必须明确显示缺口并取得确认。未知估时不能当零。

### 来源兼容捷径

尽量复用现有“资料分析 → Note → 字段核对”的路径，助手页把核对内嵌呈现，避免用户在多个页面来回跳。来源字段确认与所依赖的任务创建保持一致，不虚构便签出处。

本版不为支持直接模型截止而新造一种正式 Deadline 来源。来自 Note 的截止须有合法确认；用户自行录入/修改可沿用 manual；原图建议但没有可追溯 Note 的值先要求核对，不偷换为用户原始输入。

### 备份不后补

继续用已有 v2 导出恢复：正式对象和助手草案可恢复；已采用摘要重映射后保持历史只读；assistant_ops 永不导入。M1 至少用真实采用结果做一次真实 ZIP 往返，不能只测手工伪造的 applied 对象。

## 4. M2：真实智能理解与任务拆解

### 最短调用链

1. 原图/文字先在本地收集保存。
2. 新截图复用现有 `/api/analyze` 提取候选信息，生成可核对资料；已有有效分析可复用，不能无条件每轮重新分析。
3. 新增 `/api/assistant/propose`：接收选定资料内容/摘录、候选字段、用户要求、选定既有任务与行动、七日容量和已有安排摘要；返回结构化任务/行动建议或最多三个澄清问题。
4. 前端核对关键事实，调用已有本地排程器，显示每天的工作和未排原因。
5. 用户采用后走 M1 同一个服务，再进入现有日程/工作页。

只有截止字段不足以拆解工作：请求必须带用户选定资料中的任务正文/要求与证据，受现有限额约束，不把整个本地资料库自动发送给模型。截图分析不能支撑的细节要问用户，不能用编造的课程要求填满行动清单。

### 后端首版边界

- 复用现有模型适配与配置，先保证一个配置好的模型能完成结构化输出；不新增复杂厂家自动选择。
- 普通请求响应即可，不做流式、工具自动循环或后台运行。
- 迁入需要的正式请求响应类型；结构与引用校验失败明确报错，不把自然语言猜成写库命令。
- 建议默认走 create/link、create/reuse；不输出已保存、已确认或任意工具调用。
- 新付费端点必须接入现有鉴权、限流、并发和共享每日模型额度；密钥留在服务端。
- 保留既定 propose 总预算和尝试上限：整体最多 120 秒、最多 2 次实际厂家尝试，包含格式修复/重试；不顺手改变 analyze 预算策略。
- 浏览器接口调用复用当前可用的本地开发访问方式，不把固定服务密钥写进前端。若采用真实模式需要代理注入授权，在本地服务端配置；公开托管与可信代理仍是后续部署工作，不以裸露密钥换进度。
- 失败保留资料、输入和已有草案。演示数据须明确标记，不能在真实请求失败后假装 AI 成功。

### 页面状态

仅需清楚呈现：理解资料、需要补充、方案可核对、正在保存、已采用、失败可重试、保存结果待核实。生成期间仍可取消，晚到结果不得覆盖用户的新输入、新版本或新空间。

## 5. M3：进展反馈与最小改排

2026-11-25 执行更新：M1、M2 已完成人工验收，下一步按 [M3进展反馈与最小改排开工单](2026-11-25-M3进展反馈与最小改排开工单.md) 实施。本节为总体边界，具体工作量口径、受限替换写集、版本兼容及验收以该开工单为准；后文 §8/§9 保留 M1 的历史执行记录，不代表重新从 M1 开始。

### 输入保持简单

从任务页或助手页选择已有任务，填写：

- 已完成/尚未完成的行动（完成状态仍走既有确认流程）。
- 各项还需要多少分钟，可附一句进展说明。
- 新的每天预算、不可用日和希望调整的时间范围。

例如：“资料已读完，报告还需 90 分钟，周四没空，请把还没开始的安排挪开。”模型可建议剩余拆解，用户核对剩余量。专注投入 30 分钟不等于工作量减少 30 分钟，不能自动相减。

### 仅调整一小块明确范围

首版一次选择一个任务，在七日窗口中明确勾选允许替换的旧安排，默认不选；候选只包含今天及以后、planned、任务活引用、无任何 FocusSession 引用且没有投入记录的安排。选择后仍须在预览与提交时重查。

- 已完成、partial、有投入历史、正在专注的安排只展示并保护。
- 没选中的安排保持原样并继续占用容量。
- 过去的未做安排不自动滚到今天，也不偷偷取消；用户可走原页面处理。
- 结果预览列出“保留 / 取消旧安排 / 新增安排”，明确总截止不变。
- 确认后，一个事务将选中旧安排标 cancelled，并新增安排、记录草案与回执；中途失败整体回滚。
- 同一既有 Task 和可复用 Action 不重复创建；默认先复用行动，新增行动必须在差异中单独显示。

**容量规则：** 被明确选入替换集且已验证可替换的旧安排，在这份改排模拟里扣除占用；未选和受保护安排仍计占用。未采用前真实日程不变。不能先取消旧安排再请求模型，也不能把旧安排继续算占用导致新方案虚假无容量。

### 这是一个明确的协议增量

当前首版协议限制 replacement_ids 为空。M3 必须交付一个单独的改排协议增量：定义允许的替换集、完整旧安排基线、模拟容量与原子取消写集，并配套生成类型和回归。不能直接删掉 maxItems=0 就宣称支持改排，也不能让 M1 的普通新增采用偷偷获得取消权限。

优先保持普通新增路径不变，将改排作为明确模式/独立准备类型实现。具体版本是否需要升级，以持久化与请求形状差异确定并记录；历史备份必须继续可读，执行授权不进入备份。采用后的旧草案保持只读，每次调整新建草案。

## 6. 先不做的功能

- 任意多任务全局最优重排、小时级时间槽、自动识别外部日历空闲。
- 自动后台改计划、跨设备同步、周期任务、批量删除、整批撤销。
- 任意既有任务字段批改、多智能体协作、工具插件市场、无限长聊天记忆。
- 复杂拖拽、视觉大改、全新工作页面、完整历史版本对比界面。
- 多厂家效果评测、复杂模型路由、公开部署优化；但真实模型闭环必须至少实测一次。

## 7. 最小验收，不重复堆流程

既有全量检查继续跑；新增测试围绕关键风险，避免只给实现函数套同形测试。

| 里程碑 | 必验路径 |
| --- | --- |
| M1 | 预览不写业务；一次采用数量与内容正确；双击/双标签不重复；中段失败零半份；事实变动拒绝；真实 ZIP 恢复后不重放；日程进入现有执行页 |
| M2 | 一张真实虚构通知截图＋文字要求→建议→每日安排→正式采用；一条澄清；模型失败保留输入；晚到响应被丢弃；请求鉴权/共享额度有效 |
| M3 | 已完成一项、另一项剩余 90 分钟、一天不可用→预览替换→保存；历史不变；未选安排不变；容量不双计；并发开始执行导致替换拒绝；失败不提前取消旧安排 |

每次提交前跑相关契约检查、前端 test/check/build；后端变更时跑后端测试。最终将三段主线各录一段短视频或截图序列，用虚构资料，注明真实模型与演示模式。用户真实资料不用于测试播种或故障注入。

## 8. 开工顺序

现在优先做 M1：助手页最小布局与输入/预览 → 接现有草案服务和固定演示输入 → 最小原子采用 → 日程/执行/备份验证。完成后用户已经能实际点通产品。

再做 M2，把固定建议替换成真实请求，并把原有资料核对嵌入同一流程；最后做 M3 的有限改排。过程中以能运行的代码和实际体验推进，必要协议差异写短文档，不再先扩展成多轮完整设计项目。

本初版完成后可以说明“图文到每日安排、确认采用、执行与有限反馈改排已打通”，不能说明原完整版 5B-2～5B-5 的全部能力均已完成。

### 9.2 只补四个职责

建议文件落点如下；已有等价模块则复用，避免为了文件名重复实现。

1. `pages/AssistantPage.vue`：当前草案选择、表单、预览、采用结果。
2. `stores/assistant.js`：连接页面和已有草案服务，管理当前请求/空间/准备状态；不复制正式业务 docs，不保存第二套计算结果。
3. `domains/assistant/application.js`：无 IO 的采用范围、正式对象写集、影响预览、最新事实复核和计数。
4. `services/assistant/applications.js`：调用存储原语完成 prepare/apply/resolve；只向页面返回真实结果。

前端组件先复用现有 Button/Input/DateInput/ConfirmDialog 等；可以把表单与预览拆成两个助手组件，但不新建组件库、主题或通用工作流框架。

### 9.3 M1 页面实际交付

页面顶部显示“本地规划初版 · 未接入智能理解”，与全局既有“模型就绪”明确区分；全局模型可用于旧 analyze，不代表助手已经能理解任意要求。

桌面为输入/预览两区；手机用“编辑 / 预览”切换，不硬挤七列。预览先按日期纵向列出工作段，正式周日程继续交给现有 TodayPage，避免再造一个完整可编辑周历。

输入区提供：

- “载入演示案例”与“继续已有草案”。案例由明确点击创建，不因进入页面或刷新自动播种。
- 任务标题、截止（DateInput 或明确无截止）、行动说明与估时、本次剩余分钟、开始日期、每日预算和不可用日。
- 一个折叠的“补充要求”文本框；M1 只保存文字并说明尚未自动解析。实际生效的结构化条件显示在表单里，不能假装任意自然语言已被执行。
- 图片上传、图文理解在 M2 接入；M1 不做可点击却没有效果的上传按钮。

初版不做拖拽、聊天气泡历史墙、复杂约束编辑器。已有复杂草案允许查看；若含本版不支持的操作，明确指出原因并阻止采用，不自动裁掉内容。

预览区显示任务截止、每天的工作段与分钟、容量/未排工作。采用前用一个确认面板汇总真实写集：“新增 X 个任务、Y 个行动、Z 条安排”，缺口与既有过载分别确认。只有一个“采用计划”主按钮；成功后改为“查看日程”和“查看任务”，保留草案查看入口。

修改表单后先标记“更改尚未重新排程”，禁用采用；保存修改与重算通过既有服务执行，旧确认按原规则失效。M1 不改变已批准的版本与确认绑定语义，也不由页面直接赋值 status=ready。

### 9.4 演示与真实工作区隔离

- “载入演示案例”在既有 demo 空间运行；从个人空间点击时明确说明并通过 `app.switchWorkspace('demo')` 切换，不向个人空间插入虚构任务。
- 演示模板只提供建议输入，日期根据点击时的北京时间今天生成；不是预存的成功结果。预算、截止、行动与不可用日调整后必须调用真实排程服务。
- 一个最小案例：一项报告任务、两条行动、跨多天安排。再备一个容量不足案例验证缺口确认。初始截止使用用户核对的明确值/无截止，不伪造模型或便签来源。
- 采用服务不是 demo 专用：对当前空间合法已保存草案同样执行归属、来源和并发校验。真实空间不自动生成样例对象。
- 刷新读回既有 thread/draft，不重新载入模板。重复打开已采用草案只能查看；用户明确新建另一份草案才形成新的意图。

### 9.5 最小采用服务边界

M1 支持 Task create/link、Action create/reuse、新 PlanItem；暂不支持 Task update、取消/替换旧安排。未支持的 op 必须返回明确错误。关联已有任务沿用其正式截止，不能通过草案中的不同截止决定绕过“不更新 Task”的范围限制。

prepare 读取固定空间快照，校验当前草案、完整输入/结果、确认与来源，冻结 ID 映射和写集并生成预览；这一阶段不写正式业务，也不把草案改为 applying。

用户点击采用后才持久化 pending 与 applying。后续单事务重新核对最新草案、对象、来源绑定、全窗口占用、日期与执行保护，再写全部正式对象＋applied 摘要＋成功回执。来源/运行状态只读用途由写集限制保证；事务内部不进行网络、Blob 读取或异步摘要计算。

同一意图只用同一个 application_id 与冻结 ID 映射；同 ID 不同内容拒绝。并发去重由真实数据库事务保证，不能只禁用按钮。若新建对象 ID 已存在，整体拒绝，不能覆盖。最终成功以事务完成为准。

返回至少区分：成功/已成功、需重新核对、确定未提交、结果待核实。结果待核实只查询原意图，不能生成新 ID 重来。保留旧采用协议中必要的完整基线与状态恢复规则，但不实现通用命令系统、自动重试队列或后台任务。

新增类型按实际依赖进入正式契约；M1 不改变已有业务字段、DB v4 和备份 v2 语义。提案中 TaskUpdate 等非本版消费能力不要求为了“凑全类型”一并实现；差异表写清已支持与暂缓部分。

### 9.6 必须一起接好的现有边界

- **状态锁定：** 当前草案服务原本没有真实采用。本批补齐 applying/result_unknown 时 edit、reschedule、discard 等入口的限制；线程需求变更也不能将未核实意图绕回可采用。先核实原结果再按允许状态操作。
- **刷新：** 复用 settleRefresh 的状态结算，并接原回执核实；刷新不能把 applied 改成可采用，也不能把 applying 简单当未保存。
- **导航：** 用现有 `domains/workNavigation.js` 的日程/任务链接生成规则。M1 不扩展复杂返回链，先进入原任务/日程，再沿原路径开始工作；不能从助手自动开计时。
- **空间：** 助手当前草案按空间隔离，切换后清理旧详情参数和瞬态输入归属；晚到结果不覆盖新空间。已提交结果始终带原空间身份。
- **列表刷新：** 采用成功后调用 app.reloadDocs 等现有刷新入口；刷新失败显示“已保存，列表刷新失败”，不能再次采用。
- **恢复：** DataPage 原流程继续使用。恢复新空间中的 applied 只读，未采用草案重新核对；不导出/导入 ops，原空间不变。
