# 阶段 6 部署前确认清单

## 推荐结论

MVP 推荐采用：

```text
浏览器
  ↓
Qoder Sites 前端
  ↓ 同源 /api 代理或边缘网关，服务端注入 token
后端 FastAPI（独立常驻服务，外网尽量不可直达）
  ↓
真实模型厂家
```

前端继续使用 Qoder Sites；FastAPI 单独部署到能运行常驻进程的服务。模型 token 只放在网关或后端服务端环境变量，不进入浏览器构建产物。

## 决策一：后端部署形态

### 推荐：Sites 前端 + 独立 FastAPI 后端

- Sites 只负责前端构建产物和 `/api` 代理。
- FastAPI 继续由 uvicorn 运行。
- 后端使用现有 `guard.py`、模型预算、并发闸和每日额度。
- 后端只允许网关访问，或至少限制来源。
- 后端的内存态限制适用于单实例比赛部署。

### 暂不推荐：把 FastAPI 重写成 Sites Function

这会改变运行模型，重新处理：

- 请求体和图片大小限制。
- 模型请求总预算。
- 并发控制。
- 每日调用额度。
- 日志和 request_id。
- 多实例状态持久化。

除非 Qoder Sites 已明确提供兼容 Python 常驻服务的能力，否则不要为 MVP 重写后端。

### 必须验证

- Sites 是否支持同源 `/api` 反向代理或 rewrite。
- 代理是否能转发 POST body、`Authorization`、CORS 和 `X-Request-ID`。
- 后端是否能被配置为只接受网关来源。
- 真实模型失败时，前端是否仍能进入“仅保存”模式。

## 决策二：token 放在哪里

### 推荐：服务端注入

- 浏览器只请求同源 `/api/analyze`。
- 网关在服务端添加 `Authorization: Bearer <JXL_API_TOKEN>`。
- 后端保留 `JXL_API_TOKEN` 校验。
- token 不放入 `VITE_*`、HTML、JS、localStorage 或截图。

### 当前风险

`frontend/src/services/api/client.js` 当前没有发送 `Authorization`。如果直接打开后端 token 校验，前端会收到 401；如果把 token 编译进前端，任何访客都能从开发者工具读出并盗用。

### Fixture 模式例外

比赛前端演示如果只使用 fixture，可以关闭 token，保持无登录体验；这不等于真实模型接口可以无保护公开。

## 决策三：网关后的客户端 IP

### 先明确当前代码语义

- `TokenBucket` 按 IP 限流。
- `ConcurrencyGate` 是进程级全局并发上限，不按 IP 分桶。
- `DailyQuota` 是进程级全局厂家尝试额度，不按 IP 分桶。

因此经过网关后，首先受影响的是 IP 限流；并发和每日额度仍然会工作，但多实例时每个实例各自计数。

### 推荐做法

增加可信代理配置，例如：

- `JXL_TRUSTED_PROXY_CIDRS`：明确列出网关出口 IP 或网段。
- `JXL_TRUST_X_FORWARDED_FOR=false`：默认不信任转发头。
- 只有当 TCP 对端属于可信代理网段时，才解析 `X-Forwarded-For`。
- 对解析出的地址做 IP 格式校验。
- 未来自可信代理的请求，忽略客户端自行发送的 `X-Forwarded-For`。

不能无条件采用 `X-Forwarded-For`，否则浏览器可以伪造请求头，轮换假 IP 绕过限流。

### 部署安全前提

后端必须不能被用户绕过网关直接访问。否则攻击者可以：

- 直接调用后端绕过网关 token。
- 伪造 `X-Forwarded-For`。
- 绕过网关层的集中限流。

## 团队拍板项

| 决策 | 推荐答案 | 未决定前的默认行为 |
| --- | --- | --- |
| 后端在哪里运行 | 独立 FastAPI 常驻服务 | 只发布 fixture 前端演示 |
| 浏览器是否直接访问真实模型后端 | 否 | 真实模型后端保持私有 |
| token 由谁注入 | 同源网关/反向代理 | `JXL_API_TOKEN` 不开启，避免前端 401 |
| 是否信任 X-Forwarded-For | 仅信任配置的代理网段 | 继续使用 TCP 对端 IP |
| 是否多副本部署 | MVP 单实例 | 不宣称额度是全局额度 |
| 是否做 Sites Function 重写 | MVP 不做 | 保持 FastAPI 代码不变 |

## 决策完成后的后端修改范围

只有团队确认采用网关后，才修改：

1. `backend/app/config.py`：增加可信代理网段配置。
2. `backend/app/guard.py`：仅对可信代理解析 `X-Forwarded-For`。
3. `backend/.env.example` 和 `backend/README.md`：补部署说明。
4. `backend/tests/test_guard.py`：覆盖可信代理、非可信代理、伪造头和 IPv4/IPv6。
5. `devlog/private-evidence/`：保存真实网关或本地反向代理验收结果。

在没有真实部署拓扑前，不要先改 guard 取信转发头。

## 阶段 6 通过条件

- 访客可以打开 Sites 前端并完成 fixture 黄金路径。
- 真实模型 token 不出现在前端构建产物。
- 直接访问后端会被网络层或鉴权拒绝。
- 网关转发请求后，后端仍能返回 `X-Request-ID`。
- 限流只按可信网关传递的真实客户端 IP 分桶。
- 多实例限制的边界已经在部署文档中写明。
- 真实模型失败、429、413、422、503 都能回到“仅保存”路径。
