## 2 FocusSession 字段差异（0.3.0 → 0.4.0）

保留全部现有字段与语义：id、workspace_id、task_id、action_id、plan_item_id、started_at、accumulated_ms、running、draft_md、outcome、blocker、ended_at、is_demo。

新增字段（全部可选，缺省即旧记录形态）：

| 字段 | 类型 | 缺省 | 语义 |
| --- | --- | --- | --- |
| record_version | 0 \| 1 | 0 | 0=旧记录（0.3.0 形态），1=3B 起新会话。分版本校验，不混用 |
| timer_anchor_at | str \| null | null | 运行中本段尚未计入 accumulated_ms 的起点（ISO 时间）。v1 运行中必填；暂停/结束必须为 null |
| task_snapshot | TaskSnapshot \| null | null | 开始时冻结的任务标题、事项名称、截止值及精度、捕获时刻 |
| action_snapshot | ActionSnapshot \| null | null | 开始时冻结的行动文本、预计分钟、捕获时刻 |
| task_ref_state | "active" \| "deleted" \| null | null | 任务活引用状态。v1 必填；v0 必须缺席（遗留缺失按展示层降级，不伪造 deleted 事件） |
| action_ref_state | "active" \| "deleted" \| null | null | 行动活引用状态，同上，与 task 独立 |

task_id/action_id 字符串保留。ref_state=deleted 后它们只是历史标识，禁止当活链接；active 必须在同一工作区解析到正确类型与所属关系（跨 fixture 校验 + 3B-1 运行时事务内校验）。

### 分版本校验规则

v0（record_version=0，含缺省）：
- 校验规则与 0.3.0 完全一致：accumulated_ms≥0；running 排除 outcome/ended_at；blocked 必须有 blocker。
- 五个新字段（anchor/两快照/两 ref_state）必须全部缺席，出现即拒绝——防止混版记录。
- 不新增 ended_at/outcome 成对约束：0.3.0 合法的旧记录不因新规则失效。旧 ended 缺 outcome 属遗留异常形态，可读，展示层按恢复/遗留处理。

v1（record_version=1）：
- 继承 v0 全部规则。
- task_snapshot、action_snapshot、task_ref_state、action_ref_state 必填。
- ended_at 与 outcome 成对：有其一必须有其二；结束后 running=false 且 anchor=null。
- running=true → timer_anchor_at 必填；running=false → anchor 必须为 null。
- ended_at 为空（运行或暂停）→ 两引用必须 active；deleted 引用只允许出现在已结束记录。
- 快照不随活对象改名重写、删除事务不临时伪造快照——模型层无法表达「不改写」，作为 3B-1/3 域规则写入 §7，测试在对应批次验证。

### 快照值对象（新增定义）

TaskSnapshot：title（必填）、matter_name（可空）、deadline_value（可空）、deadline_precision（none/date/datetime，缺省 none）、captured_at（必填）。校验镜像 Deadline：precision=none 时 value 必须空；有精度必须有值且格式匹配。不含 source/from_note_id/confirmed_at——快照是展示事实，不是新的截止确认。
ActionSnapshot：text（非空）、minutes（正整数）、captured_at（必填）。
快照不是原始资料备份：不复制原图、不复制便签字段进会话。

## 3 旧记录兼容策略

- v0 记录原样保留、可读，不重写为 v1，不从今天的任务内容补造过去快照。
- 历史无快照时展示「旧记录未保存当时信息」；如展示当前对象名称，明确标注是当前名称（3B-2 实现）。
- v0 引用对象已不存在：按遗留缺失展示，不自动补 ref_state=deleted（该字段 v0 禁止出现）。
- v0 未结束会话（如 fixture 05 的 focus-01）进入恢复确认流程，由用户处理后产生 v1 后续记录；本批不改写它。
- 兼容性精确陈述：**0.3.0 合法的 v0 记录在 0.4.0 下全部仍合法**（新字段可选且缺省即旧形态，v0 校验规则未变）；有效记录集合的变化只有两处——「v0 携带新字段」与「不满足 v1 不变量的 record_version=1 记录」被拒绝，这两类在 0.3.0 下本就不存在或无定义。不声称「新增可选字段所以完全兼容」：v1 校验确实收紧了新记录的有效集合。

## 4 计时语义（契约层）

started_at=首次成功开始，之后不变；accumulated_ms=最近成功提交的有效累计；timer_anchor_at=本段未计入起点。显示值：运行中 `accumulated_ms + max(0, now − anchor)`；暂停/结束只用 accumulated_ms。暂停/结束/检查点在同一事务累加本段并更新锚点；继续设新锚点不清零。检查点约 10 秒、写入串行/版本校验、恢复不自动计入离线间隔——均为 3B-1 运行时规则，契约只提供锚点字段与不变量。

## 5 PlanItem 兼容边界（本批只定契约，不实现计划功能）

- 新增 `task_ref_state`（active/deleted，缺省 active）。旧记录缺省 active，与既有语义一致，不失效。
- 校验：`state=planned` 且 `task_ref_state=deleted` 拒绝——未执行计划不得继续指向已删任务。done/partial/moved/cancelled 属历史形态，允许 deleted。
- Task 删除时的计划策略（提案，随本批审查）：删除事务内**删除 planned 条目**（计入撤销补丁），历史形态条目保留并置 task_ref_state=deleted。不做静默删除：进删除影响确认。
- `focus_session_id` 字段说明明确为：最近一次**已结束**会话的快捷引用；全部会话以 FocusSession.plan_item_id 反查；不保存第二份会话 ID 数组。跨 fixture 校验新增：focus_session_id 必须指向 ended_at 非空的会话。**复审整改后进一步要求双向闭合与归属一致，见 §11。**
- 本批新会话 plan_item_id 为空（从任务行动开始，fixture 06）；从计划条目开始的会话必须带 plan_item_id（fixture 07，复审整改后闭合）；已有计划记录不重算，汇总更新留阶段 5。

## 7 删除与撤销规则差异（契约支撑 + 3B-1/3 实施规则，本批不写运行时）

删除前：受影响对象存在任何 ended_at 为空的会话（含暂停）→「取消删除 / 先结束本次工作」；结束表单完成后**重新展示删除影响再确认**，不因之前点过删除就自动删。

删除事务（沿用便签联删、任务删行动、原始资料默认保留）：
- 单删 Action：同事务清 current_action_id；已结束历史 action_ref_state→deleted，task_ref_state 保持实际状态。
- 删 Task/便签联删：逐引用断开已结束历史；草稿、成果、用时、快照保留；planned 计划条目按 §5 策略删除。
- 不临时伪造快照；v0 记录按 §3 遗留策略，不写新字段。
- 历史展示「原任务/行动已删除」，不提供失效跳转；Task 仍在时仍可返回。

撤销：只逆转本次删除（恢复对象 + 本次被断开的引用 + 本次被删的 planned 条目）；不改写会话成果/累计/快照/新记录。删除记录携带**最小关系补丁**（被断引用的 id 列表、被清 current_action_id 的原值、被删计划条目原文）及提交后版本/状态；恢复事务逐条核对 ID/类型/归属/版本，被其他操作改过则明确拒绝冲突。单步 lastDeleted 边界不变，不做通用撤销栈。

## 8 transformDocsAtomic 工作区审计结论（§7 要求，3B-1 前必须补保护）

现状（frontend/src/services/storage/db.js）：`stamp()` 与 `inWorkspace()` 读取模块级可变 `workspaceId`；transformDocsAtomic 在 `req.onsuccess` 回调里才执行 plan 过滤与 stamp——若事务排队期间 `configureWorkspace()` 被调用，读取过滤与写入归属会按**切换后**的空间执行，可能把旧空间数据写进新空间或漏读。普通 putSource/putDoc 的 stamp 在 open() 解析后的微任务里执行，窗口小但同样依赖全局。

结论：本批（纯契约）不改运行逻辑；3B-1 接入会话前必须改为**调用时捕获 workspace_id**（transformDocsAtomic 在进入函数时快照当前 id，plan 过滤与 stamp 均用捕获值；异步提交中发现全局已切换则拒绝），并补「旧异步请求不写入新空间」的故障注入测试。已列入 3B-1 前置项。

### C2 事件时间真实性（models.py）

新增 `_check_real_datetime`：DATETIME_RE 形状 + **显式偏移范围检查**（时 00–23、分 00–59；实测 Python 3.12 `fromisoformat` 会静默接受 +08:75，与后端第六轮 time_rules 同一坑）+ fromisoformat 真实日历/时刻探针（Z→+00:00、HH:MM→HH:MM:00 归一后探测）。

适用范围（仅 v1 与新快照）：

- v1 FocusSession：started_at 恒校验；ended_at、timer_anchor_at 非空时校验。
- TaskSnapshot/ActionSnapshot：captured_at 恒校验。
- TaskSnapshot.deadline_value：date 精度走 DATE_RE + fromisoformat（复用 Deadline 的严格日历逻辑）；datetime 精度走 `_check_real_datetime`。

时区规则（明确，不依赖设备时区）：带偏移的值按绝对时刻保留、绝不替换偏移；naive 值按产品默认北京时间解释（与后端第六轮定案一致）。**v0 旧记录的 started_at/ended_at 不收紧**，保持 0.3.0 兼容边界，并有正向测试钉住（非 ISO 旧字符串仍合法）。

### 模型 / 机器 schema / 业务校验的边界（复审要求写清）

- **schema.json（机器可读）**：表达键集合、类型、枚举、必填性、if/then 结构关联。真实日历/偏移合法性与跨记录归属**无法**用 JSON Schema 表达，不在其中。
- **Pydantic validator（单记录）**：表达单记录不变量——分版本规则、快照精度、事件时间真实日历/时刻/偏移。消费 schema 的一方不能只跑 JSON Schema 校验就声称数据合法，必须执行同等 validator 逻辑（前端 3B-1 写入时须满足同一规则）。
- **check_fixtures（跨记录，需全量数据）**：表达归属/存在性/快捷闭合/运行与未结束配额。单条记录校验器无法表达，运行时由删除事务与写入路径保证（3B-1/3 实施）。
