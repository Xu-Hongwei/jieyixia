## 2 命令输入协议

### 2.1 begin（focus.begin / beginPlan）

无 planItemId：输入与行为完全不变（E01）。

planItemId != null 时新增必填：

| 输入 | 形状 | 说明 |
| --- | --- | --- |
| expected | planSnapshot 六字段 | 打开确认面板时冻结的安排快照；唯一构造口 planSnapshot() |
| facts | beginFacts 八字段（§3） | 面板冻结的行动/任务/日期事实；唯一构造口 beginFactsOf() |

confirmBlocked 沿用现有语义（blocked 任务必须显式 true）。

计划分支事务内检查次序：

1. **同安排未结束会话先查**（existingUnfinishedSessionForPlan，事务内最新 docs）：命中 → `info.code=PLAN_SESSION_EXISTS`，附稳定 session，零创建、零业务写入。回到工作只导航，不自动继续计时。此检查先于资格/事实校验：即使安排事实已变，回到真实会话仍是安全动作。
2. 任务/行动基础校验沿用现有（缺失/done/blocked 未确认 → RELATION_INVALID + needsConfirmBlocked）。
3. assertPlanExecutable：安排活引用、planned/partial、Task 同空间未完成、Action 按 ID 属于该 Task 且未完成（PLAN_NOT_EXECUTABLE / TASK_DONE / ACTION_DONE / RELATION_INVALID）。**不按 action_text 绑定**。
4. assertSnapshot(item, expected) → STALE_PLAN（首差异字段 + expected/current；UI 用 planSnapshotDiff 列全，沿用 5A-1 模式）。
5. facts 与事务内最新事实逐项比较 → BEGIN_FACTS_CHANGED，**附完整 diffs 列表**（事实不是白名单快照，域内直接列全）。
6. **历史前置核对（R3 整改，开工单§3.1）**：真正新建会话之前，对事务内最新 docs 调 summarizePlanTime(planItem, latest)。摘要非权威（冲突/非法时长/非法结束时刻）→ `HISTORY_UNRESOLVED` 附 problems，零创建——已知不能正常结束的历史在新开工作之前拦住，不拖到 end；state='planned' 且已有合法结束历史（endedSessionCount>0）→ `PLAN_REVIEW_REQUIRED` 附 history=historySignature(摘要)，零创建，先走人工进度核对，不当全新安排。partial + 权威历史允许新段。**不自动改旧状态、不清摘要、不重写历史**。第1步「同安排未结束会话优先回到工作」不受此拦截影响（即使历史异常，已有暂停/运行会话仍返回稳定 ID）。
7. 创建会话：plan_item_id=条目 ID，其余形状/快照/Task→doing/runtime 与现有一致。**begin 不写 PlanItem**（契约无 doing 态；进度只在 end 写）。

expected/facts 缺失或形状非法 → PLAN_CONFIRM_REQUIRED（零写入）。

### 2.2 end（focus.end / endPlan）

会话 plan_item_id == null：输入与行为完全不变；**携带 planProgress/expected/historyConfirm 任一 → PLAN_LINK_INVALID**（独立工作不生成 PlanItem）。

会话 plan_item_id != null 时新增必填：

| 输入 | 形状 | 说明 |
| --- | --- | --- |
| planProgress | 'partial' \| 'done' | 第二组显式选择；缺省不允许，不随 outcome 代选 |
| expected | planSnapshot 六字段 | 结束表单打开时冻结 |
| historyConfirm | historySignature 或 null | 表单打开时**已结束**历史摘要（天然不含本段未结束会话）；无已结束历史时必须 null |

另：**end 输入禁止携带 planItemId**（任何值）→ RELATION_INVALID「结束不接受改挂安排」。安排身份只来自会话真实 plan_item_id。

事务内次序（开工单§6）：

1. 现有校验不动：会话/owner/epoch/租约/正文修订/结果合法性 → settleRunning → 异常则 RECOVERY_REQUIRED（只写其恢复元数据，**不写**成功结束/Action/安排进度）→ assertLease。
2. 安排校验：条目存在、同空间、task_id === session.task_id（否则 RELATION_INVALID）；活引用且 planned/partial（否则 PLAN_NOT_EXECUTABLE）；planProgress 合法（缺失 PLAN_CONFIRM_REQUIRED / 非法 INVALID_FIELD）；assertSnapshot → STALE_PLAN。
3. 历史核对：对事务内最新 docs（本段仍未结束）summarizePlanTime。有已结束记录 → assertHistoryConfirm（HISTORY_UNRESOLVED / HISTORY_UNCONFIRMED / HISTORY_CHANGED，保留输入、零写入、不把异常当零、不自动修历史）；无已结束记录而 historyConfirm != null → HISTORY_CHANGED。
4. 构造 endedSession（现有结算规则），在本次事务临时文档视图中替换原会话。
5. 对临时视图重算 summarizePlanTime → 必须 authoritative（否则 HISTORY_UNRESOLVED）；生成 planDraft = { ...item, state: planProgress, actual_minutes: summary.actualMinutes, focus_session_id: summary.latestEndedSessionId }。累计规则完全沿用 5A-0（先 sum 再 floor；null/0 区分；最近已结束按真实结束时刻+ID 稳定排序；重试全量重算）。
6. 合并写集一次提交（§4）。Action done/Task 当前行动清理沿用现有显式规则；**Task 不自动 done**。info 增 planItem/history。

六种 outcome×planProgress 组合全部允许；blocked 卡点必填沿用。

### 2.3 legacyEnd（focus.legacyEnd / legacyEndPlan）

v0 会话无 plan_item_id：原路径不变（显式归档、释放占用、不新增自动 Action 完成）；携带计划参数 → PLAN_LINK_INVALID。

v0 会话有 plan_item_id：

- **关联有效**（条目存在、同空间同 Task、活引用、planned/partial）：planProgress/expected/historyConfirm 必填（缺失 PLAN_CONFIRM_REQUIRED），校验与 end 相同；同一事务更新安排摘要/进度。**不升 record_version、不补快照、不改 legacyEnd 原有 Action 语义（仍不触碰 Action）**。
- **关联异常**（缺失/跨 Task/终态/断引用）：携带计划参数 → PLAN_LINK_INVALID「无法联动安排，请先人工核对」；不带计划参数 → 保留原「显式结束并释放占用」兼容通路。此分支是遗留修复，**不是正常 v1 结束失败的降级通道**（v1 异常一律零写入保留输入）。

## 3 beginFacts：单一来源

domains/focus.js 新增（2B 面板与事务校验共用，禁止页面自造第二套）：

```
BEGIN_FACT_FIELDS = ['actionId','actionText','actionMinutes','taskStatus',
                     'taskCurrentActionId','deadlineValue','deadlinePrecision','confirmDate']
beginFactsOf(task, action, confirmDate) → 八字段对象
beginFactsDiff(expected, current) → [{field, expected, current}] 完整清单
```

- confirmDate = 确认时刻北京日期（beijingDateStr）。事务内用提交时刻 env.wallNow 重算比较：跨北京午夜 → confirm_date 差异，重新展示日期关系（E06）。started_at 永远取提交时真实时钟。
- taskCurrentActionId 入事实：确认期间当前行动被换 → 列差异；**服务始终用输入显式 actionId，绝不静默改绑新当前行动**。
- deadline 只是风险事实：变化要求重新核对，不自动改截止、不禁止过期后记录真实工作。
- facts.actionId 必须等于输入 actionId（一致性），否则 PLAN_CONFIRM_REQUIRED。

### 拒绝分支

- 断言型拒绝（fail 抛错）：事务整体回滚，**零业务写入、零台账条目**。
- info.code 业务拒绝（PLAN_SESSION_EXISTS / RECOVERY_REQUIRED）：前者零写入但记台账（可 replay 稳定会话 ID）；后者仅写其明确规定的恢复元数据 + 台账 ok:false 条目，不写成功结束/Action/安排进度。
- **禁止** focus.end 成功后再调 planStore.confirmProgress 补写；**禁止**把含本段的「结束前快照」当旧历史确认传给独立 confirmProgress。共用纯函数（summarizePlanTime/assertHistoryConfirm），但「用户核对的旧历史」与「本事务新产生的结束事实」分两次计算。

## 5 请求信封输入指纹（services/focus/service.js）

现状：台账绑定 op/空间/目标会话/签发时刻，**不绑定业务输入**——同 requestId 换正文/结果会 replay 旧成功并谎称新输入已保存。本批补齐：

- 范围：begin / end / legacyEnd 的**新台账条目一律带 input_fp**；其余 op 不变。
- 指纹内容（规范化 JSON，固定键序）：
  - begin: {taskId, actionId, planItemId, confirmBlocked, expected, facts}
  - end: {outcome, blocker, draftMdHash, planProgress, expected, historyConfirm, expectedRevision}
  - legacyEnd: {outcome, blocker, accumulatedMs, planProgress, expected, historyConfirm}
- **draftMd 只存哈希摘要**（`长度:FNV-1a`），台账不存明文正文副本。FNV-1a 32 位非加密哈希，仅作相等性指纹（用途是检测输入变化，不是抗攻击）。
- **draftSeq 不入指纹**：序号由服务在排队前分配，重试会再分配新序号但 replay 零写入不消费；若入指纹会造成自身失配（开工单§7.4 的 focus 特殊性）。expectedRevision 是用户冻结的修订前提，入指纹；它变化 = 新意图新信封。
- replay 校验：prior.input_fp 存在 → 与当前输入指纹不符 → STALE_REQUEST「请求输入已变化，请重新确认签发新意图」，**不回放旧成功**。裸 requestId 路径同样比较。
- **旧台账兼容**：prior 无 input_fp（旧版本条目）时——当前输入携带计划确认参数（begin.planItemId != null，或 end/legacyEnd 的 planProgress/expected/historyConfirm 任一非空）→ 无法验证即 STALE_REQUEST 拒绝；纯无计划输入 → 按原规则 replay（不伪造指纹）。计划关联结束是新命令，其台账必然带指纹，不存在「旧台账计划结束」的真实数据。
- 首次未提交失败（断言拒绝/SAVE_FAILED 探测无条目）不写台账，原信封可重试；重试沿用 requestId/issuedAtMs/全部不可变输入。

### 5.1 回执验证单一来源（R1 整改）

正常事务回放与 SAVE_FAILED 回执探测**共用 assertReplayEntry**，验证项完全一致：

1. 操作绑定：entry.op/session_id 必须存在且与当前 op/输入目标会话一致（begin 目标为 null）；workspace_id 存在时必须一致。缺绑定 → STALE_REQUEST。
2. 签发时刻：entry.issued_at_ms ?? entry.at_ms 为凭据；信封带 issuedAtMs 时必须与凭据一致。
3. 输入指纹：entry.input_fp 存在 → 与当前 fp 不符即 STALE_REQUEST；不存在（旧台账）→ 携带计划确认输入无法验证即拒绝，纯无计划输入按原规则放行（§5 兼容规则）。
4. 重试窗口：凭据缺失或早于 nowMs-OPS_WINDOW_MS → STALE_REQUEST。

SAVE_FAILED catch 分支：探测读取失败 → 保留 SAVE_FAILED；探到条目 → 走同一验证，**验证拒绝直接返回 STALE_REQUEST，不被外层 catch 吞回成功通路**；验证通过才 replay。任何无法验证或输入不符都不得返回成功回执。

### 5.2 首次接纳即冻结输入（R2 整改）

原空档：issued 内存记录只绑定 op/空间/目标会话/时刻，input_fp 只在成功或 info.code 回执写入台账后才有持久依据——首次事务中止且无回执时，同 requestId 可换行动/安排/正文再提交。整改：

- fp 在 runOp 排队前计算；**首次接纳完整输入时**（issued 登记或补绑定 `bound.fp == null && fp != null`）冻结到 issued，事务失败后保留。
- 后续同 ID 调用排队前核验 `known.fp != null && fp != null && fp !== known.fp` → STALE_REQUEST，不进事务。
- **issueRequest 只带部分参数不冻结 fp**（兼容 TaskDetailPage/WorkPage 现有预取调用）；绑定时点是首次 runOp 接纳完整输入，不是签发。
- 同输入重试允许（不重复创建/累计）；换输入必须新信封。业务断言拒绝（info.code 回执）同样已绑定。
- 已披露边界不变：未提交请求跨实例/刷新后无内存绑定也无台账条目，无法验证即 REQUEST_ENVELOPE_REQUIRED/SAVE_FAILED 重试语义，不伪造凭据。
- 兼容影响：同实例同 ID 先带计划输入被拒、再换纯无计划输入，也会被指纹绑定拒绝（换输入=新意图）；旧台账「纯无计划 replay」兼容的真实场景是刷新/跨实例后只凭台账验证（测试已按此适配）。

### 5.3 接纳即深快照：指纹与执行同版（R4/R5 整改）

原空档：input_fp 在接纳时计算，但 effectiveInput 与 enqueue 闭包仍引用调用方原 input 对象（end 的 draftSeq 展开也只浅拷贝一层，expected/facts/historyConfirm 嵌套仍共享）。调用方在异步完成前复用/修改原对象 → 登记指纹与实际执行内容脱节：提交行动 A、执行前改成 B，实际创建 B 的会话，原 A 请求重试仍 replay 成功。整改（R4 复验文档§4；R5 输入快照复验文档§2/§3）：

- **runOp 入口即生成服务独占深层快照**：R4 初版用 `structuredClone(rawInput)`；**R5 改为复用 db.js 既有 `snapshot`（`deepRaw` 逐层 toRaw 脱 Vue 代理后 structuredClone）**——顶层即使是普通对象，expected/facts/historyConfirm 仍可能嵌 ref.value/reactive 数组（PlanEditor/PlanDetail 的确认基线就存在 ref 里），直接 structuredClone 会抛 DataCloneError。含全部嵌套对象/数组；对象展开或仅根层 toRaw 都不够；不冻结调用方原对象（避免副作用）。在**服务边界统一解决**，不要求每个页面各写一套脱代理转换。
- **协议外确实无法复制的值**（如函数）：快照失败返回明确输入错误 `INVALID_FIELD`「命令输入无法快照」，零写入零登记（不进 issued、不排队），同 requestId 换纯数据可重试；**不得描述成「数据库保存结果未知」（SAVE_FAILED）**。
- 指纹、目标/空间校验、issued 登记、队列 key、effectiveInput、enqueue 闭包、事务调用、台账记录、SAVE_FAILED 探测**全部读同一份已捕获命令**（同一 input 绑定），不再通过闭包读调用方原 input。
- 服务自分配的 draftSeq/epoch 按现有规则组合到内部命令；draftSeq 仍不入指纹，重试协议与业务输入指纹不变。
- issueRequest 不克隆（同步、只读 sessionId，无异步空档）；store.run 到 service 调用前无 await，快照时点即接纳时点。
- 新业务输入仍须新意图/新请求；R1–R4 已修复逻辑与无计划旧调用兼容保留（全量回归）。
- 边界如实说明：这是调用边界的确定性保证（调用方异步完成前复用/修改传入对象、或提交后修改原 ref/reactive 数组，均不再影响执行）。本批无计划 UI，不宣称现有页面点击必然触发原反例；响应式输入兼容按现有表单模式（ref 保存确认基线）接 2B 即可用。2A 不可变命令承诺在服务边界成立，不依赖未来 2B 禁用按钮。

## 6 结果透传与 store 刷新

- service result 增：`planItem`（end/legacyEnd 成功）、`history`（摘要，供 UI 展示）、`samePlan`（PLAN_SESSION_EXISTS）。失败回执透传现有 extra（session/recovery/holder/needsConfirmBlocked/currentSeq/currentRevision/leaseExpired）+ 新增 diffs（BEGIN_FACTS_CHANGED）、problems（HISTORY_UNRESOLVED）、field/expected/current（STALE_PLAN）、current/confirmed（HISTORY_CHANGED）、**history（PLAN_REVIEW_REQUIRED / HISTORY_UNCONFIRMED，R3 整改透传）**。
- replay 仍只回结果摘要（session_id 等）；导航用稳定 session_id 重读实际记录，不依赖 r.session 存在。
- stores/focus.js run()：`result.ok && (result.task || result.action || result.planItem || result.replayed)` → app.reloadDocs()。partial/blocked 计划结束、replay 成功都刷新正确空间的 docs；归属不匹配（晚到原空间结果）只返回结果不动本地 ref（现有守卫保留）。
- 刷新后重试：沿用现有按空间隔离的内存信封（envelopes Map）；**本批不实现浏览器刷新后的未保存输入恢复**，交回如实说明（现有台账 replay 只恢复已提交结果，不恢复未提交表单输入）。
