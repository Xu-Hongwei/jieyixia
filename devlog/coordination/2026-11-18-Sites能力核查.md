# Qoder Sites 能力核查

核查日期：2026-11-18  
方式：只读核查，没有创建 Site、没有部署、没有修改后端。

## 已核实事实

1. 当前账号没有可读取的已拥有 Site；Sites 列表返回为空。
2. 当前仓库没有 `.openai/hosting.json`，因此还没有绑定的 Site 项目、project_id 或部署版本。
3. 当前前端是普通 Vite 构建，`frontend/vite.config.js` 里的 `/api` proxy 只在本地开发服务器生效，不能当作生产代理。
4. Sites 支持两种部署形态：
   - 静态 Site：部署 `dist` 等目录中的 HTML/JS/CSS。
   - Server-backed Site：部署带 `fetch` handler 的 Worker，Worker 可以通过 HTTP 连接外部后端。
5. 因此，不能从当前仓库证明“静态 Sites 自动支持同源 `/api` 反向代理”；但如果采用 Sites Worker 或独立边缘网关，可以实现同源 `/api` 转发和服务端 token 注入。

## 对当前项目的结论

### 推荐架构

```text
浏览器
  ↓
Qoder Sites 前端
  ↓ 同源 Worker / 边缘网关，服务端注入 JXL_API_TOKEN
独立 FastAPI 后端
  ↓
真实模型厂家
```

这条路线保留现有 FastAPI，不需要把模型预算、图片校验、限流和每日额度重写成 Function 逻辑。

### 尚未验证的唯一环境事实

还没有一个现存 Site 可以实际验证以下行为：

- `/api` 是否能配置同源 rewrite。
- Worker 是否能访问部署中的 FastAPI 地址。
- Worker 是否能安全保存并注入后端 token。
- 生产响应中的 `X-Request-ID`、CORS 和错误状态是否原样转发。

这些不能通过静态源码检查得出，必须在创建一个私有测试 Site 或选定现有网关后做一次部署验证。

## 下一步验证顺序

1. 选择一个可运行 FastAPI 的后端地址，先只启动 fixture 模式。
2. 创建私有测试 Site 或 Worker，不直接发布真实模型。
3. 配置 `/api/healthz` 和 `/api/analyze` 的同源转发。
4. 验证 200、401、413、422、429、503 和 `X-Request-ID`。
5. 确认 token 只存在 Worker/后端运行时，不出现在前端构建产物。
6. 确认后端只信任可信网关传入的 `X-Forwarded-For`，再决定是否修改 `guard.py`。
7. 验证完成后再设置公开访问，不要直接拿真实模型端点做第一次试验。

## 当前阻塞结论

阶段 6 的部署方向可以先定为“Sites 前端 + 独立 FastAPI + Worker/网关代理”。但由于当前没有已绑定 Site，尚不能声称同源 `/api` rewrite 已被真实环境验证。创建测试 Site 属于外部资源变更，需在明确测试项目和后端地址后再执行。
