## 2 元数据类型与 DB v2→v3 迁移

- DB_VERSION=3，onupgradeneeded 仅 createObjectStore('focus_runtime',{keyPath:'id'})；sources/docs/workspaces 不触碰。v1→v2→v3 链式迁移有测试守着；真实浏览器项 1 用原始 IDB API 播 v2 种子（原图/任务/行动/v0 会话），升级后全部保留且 focus_runtime 就位。
- 旧标签持 v2 连接→升级 onblocked 明确报 DB_UPGRADE_BLOCKED（提示关闭其它标签），不无限等待；旧标签 onversionchange 主动关连接让位，重试即成功（项 1 双页实测）。
- focus_runtime 三类记录（**运行元数据，不入契约 schema、不进备份导出**）：
  - `run:<ws>` kind:'running'：全库 running 唯一=所有空间 run 记录中至多一条 session_id 非空；开始/继续事务内校验写入，暂停/结束原子置空。
  - `sess:<id>` kind:'session'：owner_id/epoch/lease_expires_at/revision/draft_seq/last_checkpoint_at/recovery/ended。**owner/租约/草稿序号只在此处，绝不私塞 FocusSession 领域对象。**
  - `ops:<ws>` kind:'ops'：幂等台账，10 分钟窗口顺带清理，超窗旧请求 STALE_REQUEST 明确拒绝；只存结果摘要不存草稿正文。
- clearWorkspace(id) 同时清该空间 runtime（demo 重置不留运行锁）。

### 设计说明：ownerId 每次页面加载新建（与方案 §3 文字的差异）

方案 §3 写「sessionStorage 持久，刷新换新 owner 走接管」两句本身矛盾（sessionStorage 在同标签刷新后存活）。实现取**每次加载 crypto.randomUUID() 新 owner**：刷新=新持有者，旧租约（默认 30s）过期后经 takeover 接管并强制进入 recovery 核对，不自动补计时。理由：刷新后的页面无法证明自己仍是原持有者，走接管+恢复核对比静默续写更安全，与「异常关闭后离线间隔先让用户核对」同规则。暂停仍保留 owner/租约独占草稿写入（项 8 实测）。此差异在此显式声明，供审查裁定。

## 附2 四项修复语义

- **F1（P1）迟到旧草稿**：服务入口（排队前）捕获/分配 draftSeq；调用方可显式携带 draftSeq 与 expectedRevision（编辑基于的 revision）。事务内 assertDraftProtocol：序号 ≤ 已提交序号或 expectedRevision ≠ 当前 revision → **STALE_REVISION，零正文写入**，返回 currentSeq/currentRevision 供刷新重试。同 requestId 重试仍幂等 replay。end/pause/resume 的最终草稿合并走同一前提。**注意**：检查点会推进 revision，长驻编辑页应携带 expectedRevision 或在被拒后取 currentRevision 重新提交（3B-2 接 UI 时的协议要点）。
- **F2（P2）跨空间互斥**：begin/resume 在同一原子事务内扫描**全库**真实会话（含无 runtime 元数据的 v0）。同空间未结束：v0→LEGACY_RECOVERY_REQUIRED / v1→ALREADY_ACTIVE；跨空间运行中同样拒绝（v0 显式 LEGACY 入口，不静默结束/删除/计时）；跨空间**暂停**允许并存。
- **F3（P2）租约过期写入**：所有续租写操作（检查点/保存/暂停/继续/结束）在事务内校验 lease_expires_at；过期 → **OWNER_CONFLICT + leaseExpired**，不提交计时/草稿、不自行续租。恢复路径：takeover（自接管或他页接管，epoch+1，旧 epoch 永久失效）→ recover keep/correct → 写入恢复。**语义变化**：暂停超过 30s 后继续也需接管+恢复确认（复审明确要求；原「暂停 1 小时直接继续」用例与 s7 item4 已按此适配）。时钟异常（跳变/回拨/长间隙）仍优先返回 RECOVERY_REQUIRED，不被租约拒绝掩盖。

## 附5 根因与修复语义

**根因**：F4 的两份签发凭据都是有限的——内存 issued 台账随实例消亡，持久墓碑上限 200 条会被淘汰。两者都丢失后，裸 requestId（不带 issuedAtMs）在服务入口被赋当前时刻，旧请求被当作新请求放行（审查方实测 103→104）。加大墓碑上限只是推迟问题。

**修复：不可变请求信封（requestId + issuedAtMs + op/空间/会话绑定），签发信息随请求本身保留，正确性不再依赖有限台账。**

- **无 requestId**（新用户意图，如自动检查点每一跳）：服务统一创建新信封（newId + 调用时刻），行为不变。
- **requestId + issuedAtMs**（信封重试，含跨页面/刷新/实例重建）：签发时刻以请求携带值为准，事务内**始终按信封年龄校验**（超 10min 窗 → STALE_REQUEST），与台账/墓碑是否存在无关；同窗内命中台账仍幂等 replay。issuedAtMs 非正整数 → RELATION_INVALID；与本地首见记录不一致（篡改）→ STALE_REQUEST；requestId 错绑 op/空间/会话 → STALE_REQUEST。
- **裸 requestId**（不带 issuedAtMs）：本地 issued 有记录 → 复用原签发时刻；本地无记录 → 事务内只能凭台账验证：台账条目担保签发时刻（issued_at_ms ?? at_ms）→ 年龄校验 + replay；命中墓碑 → STALE_REQUEST；**两者皆无 → REQUEST_ENVELOPE_REQUIRED（新错误码），绝不自动用当前时刻续成新请求**。
- 新增公开方法 `issueRequest(op, input)`：只创建信封不执行，返回 {request_id, issued_at_ms, op, workspace_id, session_id}，供调用端「首次发起创建一次、失败重试复用」。失败返回也带 issued_at_ms 供复用。
- **store 同步适配**（stores/focus.js run()）：对携带 requestId 的调用首见记录签发时刻（页面生命周期内保留，不清理），重试复用同一信封；透出 issueRequest。**边界**：刷新后内存信封丢失——跨刷新重试需 UI 持久化信封或明确重新发起（新信封），服务层对无法验证的旧 ID 一律拒绝，不会静默重建。此为 3B-2 接 UI 时的协议要点。
- 墓碑机制保留（200 条上限不变）作为纵深防御；runtime.js 本轮零改动。契约/公开数据模型零改动，无正文长期台账。
