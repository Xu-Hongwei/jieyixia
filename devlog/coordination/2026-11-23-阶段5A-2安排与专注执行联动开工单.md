# 阶段5A-2：安排与专注执行联动开工单

日期：2026-11-23。状态：产品与工程实施设计，尚未实现。

前置：[阶段5A-1最终人工验收](./2026-11-23-阶段5A-1最终人工验收.md)已通过。本单承接[5A总计划](./2026-11-22-阶段5A统一日程与手动安排开工单.md)第7–9节，以及[5A-0交回](./2026-11-22-阶段5A-0交回.md)第9节修正后的单事务方案。旧文件里的历史行号仅供定位，以当前函数为准。

## 1 本阶段要交付什么

完成这条用户路径：

**安排某天的工作 → 确认具体行动 → 开始并记录成果 → 分别确认行动结果和安排进度 → 回到原日程看到实际投入 → 必要时另安排一天。**

例：总任务是“周五交报告”；周一安排“整理资料”、周三安排“完成初稿”。周一实际做了两段各40秒，安排累计为80秒，整数摘要为1分钟；用户可选择“行动尚未完成，但周一这项安排已完成”。周三条目独立累计，总任务的周五截止保持不变。

三个结果不能混成一个完成按钮：

| 对象 | 回答的问题 | 完成影响 |
| --- | --- | --- |
| Action行动 | 这个实际步骤是否完成 | 显式选择行动完成才更新Action |
| PlanItem安排 | 这天安排的这项工作是否完成 | 显式选择安排进度才更新本安排 |
| Task任务 | 整个目标是否交付 | 继续由任务详情的任务完成操作负责 |

## 3 开始入口：少加页面，明确选行动

### 3.1 安排详情的主操作

在已有安排详情内增加主操作，不在每个日格堆一排按钮。

| 当前事实 | 展示与行为 |
| --- | --- |
| planned/partial、Task有效未完成、没有未结束工作 | “开始这项安排”，点击打开执行确认 |
| 本安排已有未结束会话，包含暂停 | “回到工作”，只导航；不新建、不自动继续计时 |
| 本空间另一安排或独立会话未结束 | 提示已有工作，给“查看已有工作”；不替用户结束或改挂 |
| 其它空间存在运行会话 | 沿用既有冲突提示和明确切空间入口，不自动暂停/接管 |
| done/cancelled/moved或任务引用已删除 | 历史只读；符合既有条件时可另安排一天，不重新开启旧安排 |
| Task已完成、Action已完成/失效 | 说明原因，回任务处理；不能借安排绕过限制 |
| 旧planned已有结束历史尚未核对、历史摘要异常 | 先走已有进度核对/异常记录入口，不把它当全新安排 |

识别“同一工作”必须比较workspace、task、action及plan_item_id。来自安排甲的入口不能因为Action相同，就把安排乙的会话当成安排甲正在执行。

### 3.2 执行确认内容

一个确认面板依次展示：所属任务、安排日期、安排说明、安排预计分钟、准备执行的Action名称/估时、总截止及必要风险。

- 有合法当前行动：显示该行动，用户点“确认并开始”。禁止点击安排卡就自动计时。
- 没有当前行动或想更换：按钮“去任务选择行动”。跳转现有Task详情，在顶部标出“正在为这项安排选择行动”，复用已有行动列表、新增和设为当前行动功能。
- 从该上下文开始时显式传planItemId；普通Task详情入口仍开始独立工作，plan_item_id=null。
- 相同文字的两条Action也必须按ID明确选择。PlanItem.action_text永远只是说明，不是绑定依据。
- Task为blocked时，在同一确认流程明确确认“仍要开始”；沿用现有begin成功后Task→doing的规则。
- 提前/延后执行允许：面板明确显示“安排在11月25日，现在是11月23日，将提前执行；原安排日期保持不变”。不自动改期。
- 总截止只是风险信息；过期不禁止记录真实工作，也不自动修改截止。

### 3.3 开始确认的并发规则

打开确认面板时冻结目标IDs、完整planSnapshot，以及面板依赖的当前行动ID/行动文字和估时/任务状态与截止等相关事实。实现可定义本地beginFacts对象，不能塞进业务记录。

确认时事务重新读取：计划有效、状态planned/partial、Task未完成且同空间、Action有效未完成且属于该Task；计划快照和已确认相关事实仍一致。变化时保留用户选择，列出全部差异，用户重新核对后签发新意图；不能静默改成新的当前行动，也不能确认时自动抓取live对象替换expected。

非当日执行的确认绑定安排日期和当时的北京时间日期。确认期间跨北京午夜，重新展示日期关系；实际started_at永远由提交时真实时钟生成。

同一安排未结束会话的检查必须在同一事务内完成。事务发现已有会话时返回稳定会话ID供导航，创建数量仍为0；不能只有页面预检查。同空间/跨空间互斥继续复用既有Focus规则。

## 4 工作页：保持成果编辑为主

复用WorkPage，不新增“计划专注页”。计时、草稿自动保存、暂停、接管和恢复仍走原有机制。

关联安排时增加一块紧凑上下文：

> 正在执行：整理资料（真实Action）  
> 所属安排：周一整理资料 · 安排日期11月23日  
> 安排预计30分钟 · 历史已投入1分20秒 · 本段用时单独显示  
> 任务总截止：11月27日

历史累计只含已结束会话，本段运行时间单独标识，不能以视觉计时不断写PlanItem.actual_minutes。当前安排说明不是会话开始时的历史快照，不给它伪造“当时说明”标签。

增加“返回安排”入口，沿用工作页离开保护：运行中须显式保存并暂停/取消离开；暂停时保存草稿后离开。回到暂停会话仍要主动点击继续。不要通过路由跳转绕过草稿、租约、恢复确认。

## 5 结束表单：两个独立问题，一次提交

关联安排的会话结束表单保留原有第一组，并增加第二组。

| 分组 | 选项 | 初值 |
| --- | --- | --- |
| 这次行动的结果 | 行动完成 / 部分完成 / 被阻塞（卡点必填） | 部分完成 |
| 这项安排的进度 | 还需要继续 / 这项安排已完成 | 还需要继续 |

两个分组必须同时可见、各有明确标题；不根据第一组自动代选第二组。提交按钮“结束并保存”。取消只关闭表单，不结束、不暂停、不改变安排。

所有组合均允许：例如Action.done + PlanItem.partial表示这个行动已完成，但本安排还有其他步骤；Action.partial + PlanItem.done表示今日安排的工作已完成，但长期行动仍继续。blocked + done也由用户明确确认，卡点仍保存，不自动给PlanItem增加blocked状态。

保存成功后的提示同时列结果，例如：“本次工作已保存 · 行动部分完成 · 安排已完成”。Task不自动完成；沿用现有“Action完成后清除相同current_action_id、不自动选下一条”的规则。

无plan_item_id的独立工作不显示第二组，不要求planProgress，不生成PlanItem。

### 5.1 结束前确认事实

- 冻结本次安排六字段快照及已有已结束会话的历史摘要；历史摘要不包含本段尚未结束的会话。
- 结束表单展示已有历史累计与本段用时的区分。本段最终有效计时仍按既有计时结算规则；不把弹窗打开时的视觉数字当成权威结算值。
- 旧历史/安排在确认期间变化，列完整差异并重新确认；不能自动信任新摘要。
- 保存期间冻结正文和两个结果；同输入失败重试保持同请求。用户改结果、正文或重新确认事实，属于新意图。
- 租约、恢复待核对、正文修订冲突仍优先处理。因这些原因退出结果弹窗时，在当前会话范围保留两组选项和卡点，恢复后重新核对；切会话/切空间不串表单。

## 6 结束必须是一个原子事务

主路径为现有focus.end → transformFocusAtomic。按以下次序构造写集，最后一次提交：

1. 事务内验证空间、会话、owner/epoch、租约、正文修订及结束结果；结算本段有效时间。需要恢复核对则停止正常结束流程，不偷偷计入未确认间隔。
2. 如果关联安排，验证该会话真实plan_item_id对应的PlanItem归属/引用/状态及用户确认快照；输入不得把正在工作的会话改挂另一安排。
3. 核对此前已结束历史摘要。异常历史返回可读原因，保留成果输入，不把异常当零分钟或自动修历史。
4. 构造endedSession；在本次事务的临时文档视图中用它替换原会话。
5. 用summarizePlanTime重算该安排全部已结束会话，生成PlanItem.state、actual_minutes、focus_session_id。
6. 合并最终正文、会话结束、显式Action完成、必要Task当前行动清理、PlanItem进度与摘要、运行占用释放、运行元数据与成功回执，原子提交。

**禁止先focus.end成功，再调用planStore.confirmProgress补写。** 不直接把“结束前快照”当作包含新会话的历史确认传给独立confirmProgress命令；可提取共用纯函数，但要区分“用户核对的旧历史”和“本事务新产生的结束事实”。

普通失败/异常不得半提交；断言型业务拒绝应零业务写入。既有RECOVERY_REQUIRED允许留下其明确规定的恢复元数据，但不写成功结束、Action完成或安排进度。失败注入需分别证明这些分支，不能笼统宣称每种拒绝连恢复元数据都不写。

### 6.1 累计规则继续沿用5A-0

- 仅统计同空间、同Task、plan_item_id匹配的已结束会话，按ID去重。
- 先累加accumulated_ms，再统一floor(totalMs/60000)。两段40秒=80秒=actual_minutes 1。
- 没有已结束记录=null；有记录不足1分钟=0，显示“<1分钟”。
- focus_session_id只指最近已结束会话，按真实结束时刻、同刻ID稳定排序；运行会话不能写入该快捷引用。
- 重试从完整会话集合重算，禁止“旧累计 += 本段”，禁止重复计入。
- done/partial都写真实摘要；取消旧安排不删除已投入记录。

## 7 请求重试与页面同步：本轮必须一并补齐

当前focus回执不应被假定已经绑定全部业务输入。为本轮计划关联begin/end补足校验，并保持原有无计划流程兼容：

1. 意图形成时冻结workspace、目标Task/Action/Plan或session、两个结果、正文、确认事实，以及需要的修订前提。首次调用前取请求信封。
2. 同意图重试沿用requestId、issuedAtMs及不可变输入。相同ID换planProgress、目标安排、Action或正文必须拒绝，不能回放旧成功并声称新结果已保存。
3. 必要输入指纹放在既有focus_runtime请求回执元数据；不增加业务契约字段，不增加明文正文副本，不为旧台账伪造不存在的指纹。旧台账兼容与不可验证请求拒绝规则要明确测试。
4. 不机械照搬Plan服务：focus有内部草稿序号/修订推进。签名范围、序号何时固定、首次未提交失败如何重试必须先定义，避免每次重试自动生成新序号导致自身失配。
5. 成功回放可能只有session_id。导航使用稳定ID并重读实际记录，不能依赖r.session.id必然存在。
6. 成功begin/end、计划更新、成功回放后，按归属刷新会话与app.docs；不能只有返回task/action才刷新。partial/blocked结束也会改变PlanItem和会话历史。
7. 提交结果未知先核实原请求/目标记录，保留原请求重试；不能因为UI刷新失败另开新会话。切空间后晚到结果不跳页、不弹错空间成功、不覆盖新草稿。
8. 若支持刷新后重试，复用已有按空间隔离的临时凭据方式；这些凭据不进正式备份、不在启动时自动重放。未实现刷新恢复时必须如实说明，不宣称浏览器关闭后任意未保存输入均安全。

## 8 路由和行动选择上下文

沿用已有/today、/tasks/:id、/work/:id、/work-records/:id结构。参数名可统一，但规则固定：

- 日程点击安排 → 当前详情保留原date/view/plan。
- 去任务选行动时附显式plan参数和原日程return；任务页展示计划上下文，不能仅因return字符串里碰巧含plan就隐式绑定。
- 开始成功进入/work/:sessionId；工作身份始终来自数据库session，URL里的plan只用于导航提示，不得决定实际归属。
- 从计划上下文结束成功回原日程日期/视图并定位原安排；done安排已折叠时展开目标历史。展示本次已保存提示和“查看工作记录”。
- 从普通任务入口开始且无plan上下文，沿用原任务返回路径。
- 浏览器前进/后退、同组件参数变化、刷新深链接不自动开始或重复结束。不允许无限嵌套return造成往返循环。
- return只接受受支持的站内路由及正确空间对象；无效/跨空间上下文清理后回当前空间安全入口，不静默切空间。

## 9 多天继续：复用“另安排一天”

结束为partial后给两个入口：“回到安排”“另安排一天”。前者回原条目；后者打开已有PlanEditor的another模式。

- 新日期初值沿用现有max(原安排日+1,北京时间今天)，用户可编辑。
- 说明和预计分钟只作为可编辑初值；不自动计算“原预计减实际”。
- 创建新PlanItem、新ID，actual_minutes/focus_session_id为空；不迁移原Focus，不复制历史投入。
- 原partial条目保持原进度，不因新建另一日自动done/cancelled。界面简短说明“新建不会结束原安排”；如用户不再继续旧条目，使用既有取消安排并确认。
- 原安排仍有未结束会话时，先回到工作处理，不通过“另安排一天”绕开互斥。
- Action已完成而新安排需继续：回任务明确选择/新增Action，不自动复活已完成Action。

## 10 删除、备份和旧数据

5A-0/5A-1已建立的保护需要接真实执行记录回归，不能只验证手工种子：

- 运行/暂停会话仍阻止对应Task/Action删除或完成；取消/失败不删除。
- 有已结束Focus引用的安排保留；Task删除后按既有断引用规则保存成果与安排历史，撤销不覆盖后来修改。
- 删除Action不删除PlanItem或实际投入；历史行动快照仍可读。
- planned+已有结束会话的旧安排先人工核对进度，不能按planned无脑随Task删除。
- 真实ZIP导出→新空间恢复，验证同Task多天、多段会话、摘要、快捷引用和正文。源空间不改，双向关联重映射完整；恢复后仍走既有待核对/接管规则，不能因进入恢复空间自动计时。

旧记录边界：

- 已结束v0/v1不批量重写，不补造缺失快照。
- 无计划的v0 legacyEnd保持既有显式归档语义，不新增自动Action完成。
- 有有效活安排关联的v0遗留结束：增加显式安排结果，可在legacyEnd同一事务更新安排摘要/进度，仍不升级会话版本、不补快照、不改变legacyEnd原有Action语义。
- v0已有引用缺失/安排终态等异常：保留原有“遗留记录可显式结束并释放占用”的兼容通路，不修造关联、不重开终态；清楚提示无法联动安排，后续人工核对。这是遗留修复分支，不能作为正常v1结束失败时的降级通道。
- 正常v1遇到安排缺失/非法历史等异常不静默拆成两次保存；保留输入与可定位错误，先核对实际数据。

**交给Qoder时先只执行5A-2A。** B/C是已设计的后续范围，不是本批一次全做的授权。无需先大改视觉，沿用现有日程布局与工作页。

5A-2A建议步骤：先写明本地命令输入/错误码/兼容表与事务写集 → 用反例锁定行为 → 接begin → 接end/legacy边界 → 补服务回执与store刷新 → 运行门禁 → 整理交回。不能因还没有新UI，就将底层未实现功能标记为整阶段完成。

## 14 门禁与交回格式

最近已验收基线为684/684、check/build与契约校验通过；开工重新测当前基线，有其他人在改代码则记录实际版本，不机械把684作为最终固定数量。

每批运行适用的npm test、npm run check、npm run build；契约用python contract/generate.py --check与python contract/selftest.py只读检查。涉及备份、删除、计时的必要回归不能省略。既有包体积提醒单独记录，不混成新增功能失败。

交回文件：devlog/coordination/日期-阶段5A-2A（或B/C）交回.md。包含：本批范围、修改文件、本地输入/错误协议、原子写集、兼容边界、验收逐项结果、失败注入方式、真实/模拟时钟、未覆盖项、复现命令。证据放对应private-evidence目录，使用虚构脱敏资料，截图可用于后续比赛留档。

每批完成后暂停，等待人工验收；不提交/发布比赛作品、不触碰用户实际后端进程、不把“写了helper”或“单测通过”描述成完整产品链路已实现。
