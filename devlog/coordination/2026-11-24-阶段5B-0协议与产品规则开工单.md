## 0 本批交付什么，做到哪里停

本批要把“给截图和文字，补充要求，助手拆解并安排每天工作”转成可验证、前后端不必各自猜测的协议。交付**产品决策、隔离的契约提案、输入输出样本、排程算例、采用事务协议、迁移与恢复方案**。

本批允许新增协议提案、样本、纯离线校验脚本和测试；不开放新API，不接真实模型，不新增正式页面，不接真实IndexedDB，不改现有业务写入路径，不实施版本升级。

5B-0结束后交回人工验证，不自动开始5B-1。协议测试通过不等于排程器、采用服务或智能体已经实现。不能先做大部分功能，再补一份“协议已冻结”的文档。

## 1 产品决策：本次直接定下

| 编号 | 决策 |
| --- | --- |
| D01 | 一个“工作助手”入口。现有日程、资料、待核对和工作记录仍是正式业务界面；助手不维护另一套任务真相 |
| D02 | 首版生成连续7个北京时间自然日的安排；默认起始日为操作时北京时间今天，可以改为未来日，不创建过去的新安排 |
| D03 | 默认按天分配“做什么、多久、产出什么”，没有小时槽。严格的上午/晚上可用时段不能被自动当成已满足 |
| D04 | 模型理解、拆解和估时；本地确定性规则排日期、算容量、查冲突。最终保存由本地事务负责 |
| D05 | 用户看到完整草案后一次采用当前版本；不用逐条手建，但不支持同一版本分几次部分采用 |
| D06 | 允许采用有明确未排分钟的有效方案，必须额外确认“仍有未排工作”；不声称已排完。硬冲突、关键事实未确认、采用范围内估时未知时不可采用 |
| D07 | 估时未知用null，不能用0。用户需补估时，或明确从本次采用范围移除该步骤后重算；移除项留在草案的excluded列表，不静默丢掉 |
| D08 | 已知估时但本周排不下的行动可以一并创建，保持未完成；本周没有对应安排，草案及结果明确显示未排分钟 |
| D09 | 截止不等于安排日。多个真实交付截止提出多个候选Task，由用户选择；不拼接到一个deadline，不把计划日期伪装成截止 |
| D10 | 无截止目标可排在有截止工作之后；7天窗口结束不是新增截止。逾期任务须明确选择“逾期补做”，保留原截止 |
| D11 | 已有安排默认全部保护。5B-1至5B-4先做新增规划，不替换正式安排；replacement_ids必须为空。5B-5再启用显式选择未执行安排的改排。这是总方案的分批落地，不另建第二个助手 |
| D12 | 既有任务在规划窗口已有安排时，必须确认本次估时是否为“额外尚未安排工作”；不默认重复规划旧工作，也不擅自从估时扣历史专注分钟 |
| D13 | 草案可修改，但采用后只读。要改已采用方案，创建新的草案；不重新应用原草案，不提供首版整批撤销 |
| D14 | 确认截图候选时保留origin/derived/quote；模型不能生成confirmed、保存成功或执行成功结论 |
| D15 | 首版不做周期任务、自动滚明天、后台自主写入、多智能体互聊、联网搜索、外部日历同步或跨设备同步 |

D11让首个闭环先聚焦新增规划：同一助手可以重新生成尚未采用的草案；“重新排已有正式计划”在5B-5才开放。不得在5B-4界面放一个无效的“自动改排所有任务”按钮。

## 2 业务对象与用户流程

### 2.1 四种正式对象保持分工

- Task：一个交付目标及一个总截止；计划调整不自动修改其状态/截止/current_action_id。
- Action：可执行步骤。现有minutes是估计，不因专注已运行若干分钟自动缩减。新建建议步骤的basis按证据使用requirement或suggestion，用户明确自建才是user。
- PlanItem：某天安排，planned_minutes正整数，action_text说明当日工作。一个步骤分几天时生成多条PlanItem，不复制多个同名Action冒充多个步骤。
- FocusSession：实际执行身份、时间、成果；仍由5A现有开始/结束流程产生。

助手草案可以记录WorkItem→Action→多个Segment映射。正式PlanItem仍只引用Task；应用后从日程开始工作仍使用现有明确Action选择。草案中的步骤顺序是规划建议，当前执行入口不强制依赖锁；不要宣传已实现强制执行顺序。

### 2.2 一条完整路径

1. 用户明确选资料、任务，上传新截图或输入文字；显示当前空间与将发送给模型的范围。
2. 新截图逐份走既有analyze；已有有效分析不重复发送。图片/文字解析失败保留资料，不能拿半份来源假装理解完整。
3. 用户提供每日可投入分钟、不可用日、优先级等。每轮集中询问最多3个关键问题，不无限追问。
4. 助手给任务/行动建议，标明事实出处、建议估时与待确认项。
5. 本地排程器生成7天草案、产出说明、每日占用、未排工作和冲突；用户可编辑或继续说要求。
6. 采用前展示新增/修改对象、字段前后值、来源确认、缺口和保护项，绑定当前草案版本。
7. 一次事务保存正式对象和应用回执；成功后才显示真实创建数量，提供“打开日程/任务”。失败和结果未知分开处理。

无资料也可只用文字规划；有资料不代表必须创建新Task。与已有同名任务关联必须选中明确ID，不能按名字自动合并。

## 3 协议分层与唯一来源

协议分为四层，不能把模型输出直接当数据库命令：

| 层 | 提案类型 | 所有者 |
| --- | --- | --- |
| HTTP输入/输出 | AssistantProposeRequest/Response | 后端校验输入并封装响应 |
| 模型结构化建议 | AssistantModelProposal | 模型只能建议；无授权、无持久化状态 |
| 本地草案与排程 | AssistantDraft、PlanningInput/Result | 前端规则及用户编辑 |
| 应用信封/结果 | ApplicationEnvelope/Receipt | 本地服务与原子事务 |

5B-0的提案类型独立放入`contract/proposals/assistant-v1/`，以该目录models.py为本批唯一手写类型来源，生成该目录schema.json/typedefs.d.ts；不加入当前正式ALL_MODELS，不让生产前后端import提案。

所有新对象使用严格字段白名单、枚举和有界数组。拒绝额外执行字段、无效真实日历日期、非法数值、重复key、跨空间/跨任务引用。schema验证结构，语义校验验证引用、依赖、数值守恒；不能只有一份看似完整的JSON Schema。

临时引用使用判别类型：`{kind:"draft", key:"w1"}`；既有引用为`{kind:"existing", id:"..."}`。key只在一个草案版本内有效，正式ID由客户端采用时产生；不复用模型自造的UUID作为正式ID。

## 4 HTTP与模型建议协议

### 4.1 POST /api/assistant/propose 请求

| 字段 | 必须的语义 |
| --- | --- |
| protocol_version | 固定"1.0"；不支持的版本明确拒绝 |
| request_id/thread_id/turn_id/client_seq | 客户端关联信息；seq单调递增；请求ID不等于采用ID或服务端计费去重凭证 |
| workspace_id | 当前本地归属标识，仅关联，不作服务端身份认证 |
| intent | new_plan / revise_draft / explain_today；正式已采用安排的replan留到5B-5 |
| user_message | 本轮用户要求；不是将附件中的文字升级为指令 |
| selected_sources | 显式选择的source/note引用、内容指纹、必要片段与字段候选；含origin/derived/quote/status的只读快照 |
| selected_tasks/actions | 明确ID及当前状态、截止、行动估时等必要字段，不携带整个工作区正文 |
| planning_context | timezone、today、start_date、horizon_days=7、每天预算及占用摘要、已有受保护安排摘要 |
| confirmed_requirements | 本地经用户确认的结构化约束及其ID/版本；模型只能引用，不能直接修改确认状态 |
| pending_requirements | 尚待澄清的约束候选，与confirmed明确分开 |
| previous_draft | revise_draft必需：draft_id/revision、选定范围、上版结构化建议与当前修改要求；其它intent可为空 |

只发送必要上下文；空间内其它任务可以占用容量，但不必把其正文发给模型。本地容量必须读取完整窗口内的安排，不能因模型上下文只选20个任务就漏计其它任务的占用。

日期默认由前端在操作时读取北京时间；后端检查形状与时区，不默默把用户选的未来规划起点改为服务器今天。跨午夜是否还可采用由本地事务重新核对。

### 4.2 响应

后端响应封装原请求关联字段、protocol_version和`kind=clarification|proposal|explanation`。关联字段由服务端从请求复制，不让模型填写。

- clarification：最多3个问题，每个有question_id、问题、候选选项、阻断原因；缺关键事实时不同时宣称ready。
- proposal：TaskProposal[]、ActionProposal[]、WorkItemProposal[]、RequirementCandidate[]、EvidenceRef[]、Assumption[]、Warnings[]。
- explanation：基于请求中已存在的事实说明今日工作或限制；不携带隐式新建、删除或开始命令。

响应不包含confirmed_at、应用回执、数据库操作、可执行脚本、HTTP工具地址；本地需要的导航由已验证对象ID构造。

### 4.3 建议对象字段

| 类型 | 必须覆盖的字段与规则 |
| --- | --- |
| TaskProposal | key、op=create/link/update、target_id、title/description/completion_criteria/deadline候选、evidence_refs。更新只允许这四类字段；不能改status/current_action_id/空间/历史。link不改对象，create无target_id |
| DeadlineCandidate | value、precision、evidence_refs、origin、derived、basis；无截止precision=none/value=null。不能由模型盖confirmed_at |
| ActionProposal | key、op=create/reuse、task_ref、target_id、text、minutes建议、basis、evidence_refs。首版不批量修改或完成既有Action；reuse必须属于明确Task |
| WorkItemProposal | key、task_ref、action_ref、deliverable、remaining_minutes:int或null、estimate_origin=user/model、splittable、min_segment_minutes、earliest_date、depends_on[]、priority。这是本次剩余工作，不是历史投入换算 |
| RequirementCandidate | key、type、value、strength=hard/soft、provenance；只允许预算、不可用日、起始日、优先级、最小工作段、可拆性、先后关系等白名单 |
| EvidenceRef | kind=source_excerpt/note_field/user_message/existing_fact、对应typed ref及定位信息。既有事实指到对象与字段，不能假装原文里出现了模型估时 |

5B-0必须把create/link/update和create/reuse写成可校验的判别联合，不使用任意JSON Patch。新增Task及已有Task合计不超过本次20个目标；未知已有ID、跨任务Action、依赖环和跨空间引用拒绝。

来源确认与Task关联遵守现有note_ids/from_note_id不变量。来自截图的新截止经对应Note候选确认后写source=note；来自用户直接手动要求则source=manual。无来源的模型估计不能直接变成正式截止。

### 4.4 固定初始限额及错误映射

| 项目 | 初始值/规则 |
| --- | --- |
| 选定目标 / WorkItem | 最多20个目标、100个工作项；新Action不超过100个 |
| 资料 / 新图片 | 最多20份选定资料；一批最多3张新图片，图片字节/像素限制沿用现有analyze配置 |
| 用户本轮文字 | 最多16000字符；单来源片段最多2000字符，超限提示缩小范围，不静默删除约束 |
| propose请求体 | 512KiB，以UTF-8实际字节和分块累计验证 |
| propose模型输出 | 最多128KiB解码文本；专用profile初始max_tokens=8192，不改旧analyze的profile默认值。100项是上限，不保证所有上限组合都能一次输出 |
| propose预算 | 整体120秒；最多2次实际厂家HTTP尝试，含重试、结构修复和fallback，共享同一预算 |
| 单日预算 / buffer | 0–1440整数分钟；buffer_pct=0–50整数，默认15；预算未指定为null并澄清，不能默认0 |
| 分段 | 默认25分钟，可改为1–240整数；新工作项剩余估时为正安全整数，或null待核对；超出7天容量允许显示未排，不强行截断 |

将这些值集中成一份提案常量清单，并列出未来映射到配置、校验、提示和测试的位置。更低的已配置上限优先，不能让单接口放宽全局保护；额度耗尽禁止fallback继续绕过额度。

120秒/2次只指一次propose，不包含之前最多3次图文analyze；每份analyze按现有独立预算处理，所有实际厂家尝试均消耗共享每日额度。交回必须列清一次完整用户操作的各调用，不能把“2次propose尝试”宣传为全流程最多2次模型调用。

复用现有ApiError外形，code仍为开放字符串；提案列HTTP语义：413输入过大、422结构/引用非法、400协议不支持、401鉴权失败、429限流或额度不足、503模型/并发不可用、504预算超时、502输出非法。必须对照现有错误映射形成新端点一致表，不能改旧analyze的既有错误行为。local取消/响应过期属于客户端状态，不伪造成服务端事务成功。

guard、BodyLimit、模型实际尝试计数、错误脱敏在5B-3一起覆盖新端点；5B-0只列接入点及反例，不改guard/XFF。首版不宣称request_id可保证付费调用恰好一次；取消请求也不保证免除已发生的费用。

## 5 排程输入、输出与唯一计算规则

### 5.1 输入与容量

PlanningInput含algorithm_version="daily-v1"、timezone="Asia/Shanghai"、起始日及连续7日预算、已确认约束、WorkItem、当前完整占用、replacement_ids（首版空）、用户确认的额外工作口径。

每一天：

`allocatable = floor(budget_minutes × (100-buffer_pct) / 100)`

`free = max(0, allocatable - committed_minutes)`

`overbooked = max(0, committed_minutes - allocatable)`

按唯一PlanItem ID计占用；planned、partial、done均按原日期和原planned_minutes保守计入窗口，cancelled/moved不占用。done不自动腾出容量，有实际投入也不按Focus分钟再次相加。未来安排提前执行不移动原日期，仍按保守承诺计占用；用户需要额外空闲时明确调整预算。

历史断引用的partial/done不因Task被删而自动消失；不得拿“不是活任务”当释放容量的理由。非法日期/时长、planned断引用等不可信占用应明确阻断并引导核对，不按0计算。已存在过载可以展示，但该日不得新增安排；采用时需明确确认仍存在的旧过载。

这是对已录入安排的预算核对，不是现实日历的全自动空闲检测。未录入会议、无安排独立工作的实际时间不自动推算进容量，界面说明用户提供的预算必须考虑这些现实事项。

### 5.2 算法顺序

1. 校验真实日期、空间归属、引用、正整数、未知估时、依赖无环与所有硬约束；不把非法输入归为“无容量”。
2. 确定每个工作项最早日与最迟可排日：日期型截止允许当天；精确时刻截止在缺少小时窗口时取其北京时间日期前一天；无截止取窗口末，仅作规划边界。
3. 过期截止：未明确选择补做则列待确认；明确补做时可在当前窗口安排，保留逾期警告与原Task截止，不声称按时完成。
4. 拓扑选择已满足前置条件的工作项；从这些项里按有效截止升序、priority（high/normal/low）、稳定key排序。无截止最后；不得为了优先级突破依赖。
5. 从允许的最早日扫描到最迟日。不可拆工作整段放入首个足够容量的日期；可拆工作逐日分配，非最终余量段不得小于min_segment_minutes，最终余量允许小于最小段，所有段必须正分钟。
6. 前置全部工作排完后后继才可排；可同日但必须给明确segment顺序。若前置仍有未排量，后继标dependency_blocked，不把部分前置完成当全部完成。
7. 不做隐藏的随机重排/回溯优化。若没有找到完整方案，说明当前规则未找到，不把启发式失败称为数学无解。

既有已完成Action只能作为已满足前置的明确事实引用，不能重新排为未完成步骤。未来已承诺安排没有正式Action绑定，不能按action_text相似就断言已覆盖某个依赖。

5B-1需实现确定性算法；5B-0只给规范化输入、手工可核算输出与伪代码，不提前把完整排程器接进应用。

### 5.3 输出与守恒

PlanningResult包含segments[]、days[]、unscheduled[]、unknown_items[]、excluded_items[]、conflicts[]、warnings[]、complete=false/true。

- Segment：segment_key、work_item_key、task_ref、suggested_action_ref、date、minutes、order、action_text、deliverable。不能包含真实计时或完成结果。
- Day：budget、buffer_minutes、committed_minutes、allocated_minutes、free_minutes、overbooked_minutes；已过载时free为0，不显示负的“可用时间”。
- Unscheduled：work_item_key、remaining_minutes、reason（no_capacity/not_splittable/dependency_blocked/outside_horizon/deadline_window/needs_deadline_day_window/overdue_requires_consent）。未知估时单列，不填gap=0。
- 每个已知估时工作项必须满足：原remaining_minutes = 已分配段分钟和 + 未排分钟。已经过用户排除的项单独统计，不混入该等式分母。
- complete=true只在全部采用范围有已知估时、无未排量、无阻断项时成立。可采用且有缺口不等于complete=true。

5B-0至少提供下列手工算例，并写出精确预期，而不是只写“应该合理”：

| 算例 | 必须输出的事实 |
| --- | --- |
| 7天每天60，buffer15，第3天不可用，已有第1天30，新工作200可拆 | 可用分钟21/51/0/51/51/51/51；按默认25分段，首日21不能放非尾段，后续51+51+51+47，总计200 |
| 截止前仅3个可用日，每日60、buffer15，工作200 | 最多153已排，47未排；不偷用禁用日，不延后总截止 |
| 无截止目标40，另一有截止工作先占容量 | 无截止项用剩余容量，Task.deadline仍为空 |
| 不可拆70，各日可用51 | 0已排、70未排，不能拆为51+19；原因not_splittable |
| A40→B30，当日容量100 | 同日A先B后；不保证具体小时；若A未排完B全部dependency_blocked |
| 精确截止2026-11-26T09:00+08:00 | 默认最迟11月25日，不能默认26日晚完成；需要当天时段核对时给独立说明 |
| 已有占用70，当日allocatable51 | overbooked19，free0，无新增；不得删除旧安排来让算例通过 |
| 一个未知估时项+一个已知60项 | unknown_count=1；已知缺口独立计算，采用前补估时或明确排除未知项 |

另给同输入稳定排序、跨月/跨年/闰日、非中国设备时区、同名不同ID、删除历史、依赖环、超过窗口、取消安排不计占用、重复引用不双计等反例。

## 6 草案状态、来源与操作权限

### 6.1 持久对象

| 对象 | 必须覆盖字段 |
| --- | --- |
| AssistantThread | id、record_version=1、workspace_id、title、messages[]、selected_refs、confirmed_requirements、created_at/updated_at；消息带id/role/content/type/typed refs/时间。不保存隐藏推理 |
| AssistantDraft | id、record_version=1、workspace_id、thread_id、revision、revision_history、status、proposal、planning_input/result、事实基线、assumptions、用户确认项、excluded_items、源引用、applied_summary、created_at/updated_at |
| ApplicationEnvelope | application_id、workspace_id、draft_id/revision、input_signature、固定新ID映射、完整准备写集、事实与容量基线、用户确认的字段变化/缺口、issued_at |
| ApplicationReceipt | application_id、draft_id/revision、input_signature、ID映射、正式新增/更新数量、committed_at；只能由本地成功事务产生 |

助手对象不塞进当前docs的未知kind，不复用旧PlanDraft去私加任意字段。首版线程最多200条消息，每条最多16000字符；单条草案序列化最多1MiB。达到上限提示新建线程/缩小范围，不静默截断已保存对话。长期累计数据受浏览器配额约束，配额错误必须可恢复；不自动删除旧草案来腾空间。

首版每个草案最多保留20个版本（含当前），旧版的建议、要求和排程快照放入revision_history，整体仍受1MiB约束；旧版本只读，不能采用。达到版本/体积上限时提示基于当前内容新建草案，原记录保留，不静默删历史。并发修改采用revision比较，不能用晚到回调覆盖另一页面的新版本。备份的typed引用映射必须覆盖这些历史快照，不仅映射当前版本。

### 6.2 状态变化

`editing → generating → needs_clarification / ready / needs_review`

`ready → applying → applied / needs_review / result_unknown`

未应用草案可discarded；已应用草案不可回ready。修改范围/需求/建议/排程都递增revision，采用只接受当前版本。旧响应匹配thread/turn/client_seq/workspace/draft revision后才接纳，取消或切空间后晚到结果不覆盖新内容。

明确增加result_unknown状态：它是本地保存结果待核实，不等同模型超时，也不能显示“没有写入”。刷新后的generating标为中断待显式重试；applying/result_unknown先核实原application_id。

来源/任务删除后，未应用草案标needs_review或在读取时派生失效；采用事务必须再次检查，不能只依赖页面先变灰。对话文字和已应用历史仍可读，不能因为历史ID被删除就自动级联删除线程。

### 6.3 采用资格

ready必须同时满足：关键Task事实已明确确认；采用范围内所需新Action估时为正数；工作项剩余估时已知；所有引用有效；无新硬约束违规；有缺口/既有过载时取得独立确认；已有安排重叠的工作量口径明确。

候选证据的确认不是模型状态。用户确认事件绑定草案版本、字段和值；改值使旧确认失效。重要字段更新展示旧→新，必须对具体字段确认，不能被一句“重新安排”授权。

confirmed_requirements来自本地交互，服务端接收到它也不获得数据库权限。附件原文中的“忽略规则/执行删除”等属于资料，不进入工具授权。

## 7 采用事务与失败恢复协议

### 7.1 准备阶段

prepare_application读取当前空间，创建不可变快照，冻结草案版本、用户确认、影响清单、分段顺序、正式ID映射和application_id。所有哈希/异步计算在事务外完成。

Source原始文字/图片采用不可原地改写的身份规则：替换原文或图片需新Source ID，确认/修改解析候选发生在Note字段。5B-0必须审计所有putSource、恢复和撤销入口，列出5B-1/2如何在写入边界保证这一前提；不能仅凭Blob大小相同宣称来源未变。事务内核对Source仍存在、归属及允许变化的元数据，并核对完整Note字段基线；原文内容哈希用于前置快照和证据，不在活事务内await读取Blob/计算摘要。普通恢复继续生成新Source ID，合法撤销只能恢复原快照，不借机替换原文。任意开发工具直接篡改浏览器数据库不属于应用并发保护的承诺。

正式写入前把待核实信封保存到assistant_ops，并将对应草案标applying；这一步只写协调状态，不创建正式Task/Plan。落盘失败即不提交业务事务。两个标签不得为同一draft revision各自创建一份生效信封。

### 7.2 业务提交阶段

同一IndexedDB事务覆盖docs、所需sources只读、assistant_drafts、assistant_ops及读取保护所需focus_runtime；若thread需更新结果引用，也在同事务覆盖assistant_threads。列出具体store范围和读写步骤，不串行调用现有多个独立提交方法冒充原子性。

事务内按顺序核对：

1. 同application_id已有receipt则核对输入签名，匹配返回原结果，不匹配拒绝。
2. 草案仍属同空间、同revision、未被其它application采用。另一个application已采用同版本时返回冲突及可核实原回执入口，不重复创建。
3. 读取最新对象、被引用来源、候选字段、所有规划窗口占用和相关执行记录。必须发现新插入的同日安排，不能只检查用户选中Task的updated_at。
4. 重新验证来源确认、任务状态、引用、当日/容量与预计变更。跨午夜或关键事实改变→needs_review，展示所有相关差异，禁止自动改方案后继续提交。
5. 全部通过后，一次写来源字段确认、Task/Action、新PlanItem、草案applied状态与ApplicationReceipt；任一步失败全部回滚。

正式Task created/updated时间由本地服务产生。新PlanItem初始planned、actual_minutes=null、focus_session_id=null、task_ref_state=active。同日新order在已有最大order之后按草案顺序分配，不重排现有条目；值超安全范围拒绝，不静默溢出。

尚未安排的已知Action创建但保持未完成；明确排除的步骤不创建。成功结果逐类列出新增Task、Action、PlanItem和保留未排项，不能把“建议100项”当“保存100项”。

### 7.3 重试与结果未知

失败必须区分：输入/事实拒绝（零业务写入）、事务中止（零业务写入）、事务可能已提交但页面读取失败（待核实）。查询原application_id应在相同事务范围协调后读取，不能因另一页仍在提交就把暂时没查到回执当绝对未执行。

查到回执→恢复原结果；确认没有提交→保留同一信封，用户显式重试前重新核对；不能生成新ID再写一批。新的需求或重新确认后的新版本才创建新意图。

assistant_ops分pending/committed等协调状态，pending保留冻结信封，committed保留回执。本地只承诺保留期间的去重；5B首版不自动清理该台账，用户清空空间/恢复到新空间是不同边界。applied草案不可再次采用，不能通过丢失回执重新放行。

5B-5替换协议预留：只允许今天及以后、用户显式选入、planned、活引用且没有任何Focus引用的安排。届时采用“旧安排cancelled + 新安排新ID”的同事务变更，不硬删原安排，不把moved伪装成已实现的迁移链；部分/已完成/有投入的记录继续保护。首版不执行此分支。

## 8 版本、迁移、备份与恢复

### 8.1 发布顺序

5B-0冻结方案→5B-1实施批准的DB v4新增store及草案保存，同时交付草案备份/恢复支持→5B-2启用正式批量采用并补齐采用后引用/回执兼容。不能先存助手资料，却让正式备份漏掉这些资料。

DB迁移只增store，不重写既有sources/docs/workspaces/focus_runtime或批量升级Focus记录。多个标签的versionchange/blocked沿既有逻辑解释处理。新版已升级DB后，旧应用可能无法打开更高DB版本，回退不能承诺“换回旧前端即可”；回退方案必须保存原数据并说明备份版本限制。

### 8.2 格式v2

保留manifest、data/sources.json、data/docs.json、assets机制，新增`data/assistant_threads.json`和`data/assistant_drafts.json`，即使为空也列在v2必需payload中。manifest增加明确的助手对象计数，全部payload有字节数与哈希。

不导出assistant_ops、在途请求、owner/租约、原应用权限信封或可重放写集。已应用草案可导出历史结果摘要和typed引用，用于展示“当时采用了哪些对象”，但不是可执行回执。

| 输入备份 | 新版行为 |
| --- | --- |
| v1 / schema0.4.0 | 按旧语义校验并恢复，新增助手store为空，不伪造对话 |
| v2 / schema0.5.0 | 按新规范校验全部资料及助手对象，完整恢复 |
| 其它组合/未来未知版本 | 明确拒绝；不猜字段、不忽略新资料后宣称完整恢复 |

旧应用拒绝新v2属于预期，不增加“导出旧格式并静默丢弃助手资料”的按钮。迁移前已有v1备份仍可保留使用。

### 8.3 typed引用与恢复后状态

为每个引用路径列：对象类型、active/historical语义、缺失时处理、是否重映射。至少覆盖thread→source/note/task、draft→thread/source/task/action、proposal existing refs、用户确认的字段引用、applied_summary的正式对象ID。

新空间和正式对象/线程/草案ID全部重建；草案内临时key不当全局ID重写。正文、原文quote、用户文本中恰巧出现的ID字符串不替换。缺失历史引用映射为隔离历史标识，不补建已删Task/Action。

未应用草案（含原ready/generating/applying/result_unknown）恢复为needs_review，清除可执行信封/旧事实基线/旧采用授权；完整保留用户可见内容。原applying结果不能据备份断言未提交，必须展示原状态待核对；不自动重放。applied草案保持历史只读，discarded保持丢弃。恢复后原空间不变，不自动生成新的PlanItem。

针对现有backup模块，必须逐一列adapt白名单、schema选择、format限额与manifest、validate引用、remap路径、restore事务store、export快照的变更，不只写“支持兼容”。新增JSON仍受既有ZIP/总解压/单JSON限额约束，不能扩大限额掩盖实现问题。
