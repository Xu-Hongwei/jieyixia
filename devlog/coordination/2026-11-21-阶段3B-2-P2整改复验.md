## 根因与修复要点（对应复审 6 条修改要求）

1. **注册 update 守卫、复用统一协调、不为无关 query 弹窗**：守卫先比较 sessionId，相同（仅 query 变化）`return true`；不同才跑 `requestWorkLeave()`，与 leave/切空间共用同一处理器与弹窗。
2. **参数更新前针对原会话保存/暂停**：`onBeforeRouteUpdate` 触发时路由参数尚未更新，`session.value`/`sessionId.value` 仍指向原会话 A；既有处理器此刻读取的就是 A，`issueRequest`/`focus.pause|saveDraft` 全部针对 A。无需等路由更新后再取旧对象。
3. **取消/失败留在原页**：处理器 `askLeave` 取消或保存失败 `return false` → 守卫 `return false` → 导航中止，URL/会话/输入保持原样（反例 P2-1/P2-2/P2-4b 已断言）。
4. **成功后才载入新会话、身份正确**：守卫放行后参数才更新，`watch([ready,sessionId,sessions])` 按新 sessionId 重置 `invalid`、`loadedId` 并 `draft.loadFromDb()`；`useWorkDraft` 既有 `watch(key)` 与 `doSubmit` 身份守卫（`sessionId/workspaceId` 变化即不应用旧结果）保证旧回调不清理新页面。A→已结束 C 先保存暂停 A，再经 watch 转 `/work-records/C` 只读详情。
5. **一次性令牌不残留**：参数更新复用组件、不卸载，`unregisterLeave` 不会触发，`requestWorkLeave` 批准后置位的 `approved` 会残留到下一次参数变化导致跳过检查。新增 `resetWorkLeaveApproval()` 在 update 守卫放行后显式消费该令牌；连续两次切换、前进/后退均重新询问（P2-4a/4b）。切空间走 leave 守卫 + 卸载重置，原语义不变（u-leave 9/9 回归通过）。
6. **不改领域/契约/后端**：本轮仅前端守卫层与离开协调单例，零后端/契约/DB 改动。
