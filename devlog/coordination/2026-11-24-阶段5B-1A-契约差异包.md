### 3.5 备份 manifest v1 → v2 逐项差异

v1 现状（format.js:95-108）：`format='jxl-backup', backup_format_version=1, schema_version='0.4.0', backup_id, exported_at, source_workspace{id,name,is_demo}, counts(按 DOC_KINDS 六类), source_count, image_count, payloads[{path,bytes,sha256}]`。
v2 提案（BackupManifestV2）：`backup_format_version=2, schema_version='0.5.0', backup_id, exported_at, source_workspace: dict, counts: dict, payloads`；必需 payload 增加 `data/assistant_threads.json`、`data/assistant_drafts.json`（即使为空）；counts 必须含 `assistant_thread_count`、`assistant_draft_count`；**禁止** `data/assistant_ops.json`。

**开放决策 D-3（提案 manifest 缺容器字段）**：ProposalModel `extra="forbid"`，而 BackupManifestV2 **没有** v1 的 `format`、`source_count`、`image_count` 三个字段。现有 ZIP 容器校验（format.js）与导出计数依赖它们。两个选项：
- 推荐：正式 BackupManifestV2 补回 `format: Literal["jxl-backup"]`、`source_count: int≥0`、`image_count: int≥0`（additive，与 v1 容器一致，图片限额检查不用改口径）；提案层同步修订并补样本。
- 备选：v2 明确废弃三字段，容器校验与限额逻辑按版本分支重写——改动面更大，不推荐。
此项涉及冻结提案形状，**先审查批准，再改提案与样本**。

其余容器规则不变：路径白名单 `data/[A-Za-z0-9_-]+\.json`（format.js:42）天然容纳新 payload；ZIP/总解压/单 JSON/图片/条目限额不放宽；版本组合严格等值分支（(1, 0.4.0) 与 (2, 0.5.0)，其它拒绝）。

## 6 UserConfirmation.object_id_or_key 判别（§6.6）

### 6.1 问题

`object_type∈{task, note_field, requirement, gap, overbook, extra_work}`，`object_id_or_key` 既可能是正式 ID 也可能是局部 key。按命名空间逐型分析：

| object_type | 实际指向 | 命名空间 | 歧义？ |
| --- | --- | --- | --- |
| note_field | note_id（+field_path 定位字段） | 正式 | 无 |
| requirement | requirement_id | 草案局部 | 无 |
| gap / extra_work | work_item_key | 草案局部 | 无 |
| overbook | 日期 YYYY-MM-DD | 局部（日期） | 无 |
| **task** | 既有 Task ID **或** 草案 task key | **混合** | **有** |

task 型不能靠形状判别：草案 key 满足 KEY_RE（≤40 字母数字），但正式 ID 允许任意 1–64 字符串，完全可能长得像 key；也不能按「字符串是否出现在 id_map」猜（开工单明令禁止）。若仅靠「先查草案 key 集、再查快照」的解析顺序，当某正式 Task ID 恰好等于本草案某 task key 时产生真歧义。

### 6.2 最小字段差异提案（开放决策 D-2，先审后改）

**推荐**：给 UserConfirmation 增加条件必填判别字段：

```python
id_scope: Literal["draft", "formal"] | None = None
# 校验：object_type == "task" 时必填；
#   draft  → object_id_or_key 必须是本草案同 revision proposal.task_proposals 的注册 key；
#   formal → 必须解析到捕获空间快照中的既有 Task（跨空间/未知拒绝）。
# 其它 object_type 必须缺省（命名空间已固定，不允许画蛇添足）。
```

影响面（本批实测）：现有 139 样本中含 UserConfirmation 条目的仅 5 份（f-envelope-ok / f-envelope-gap-noack / f-envelope-overbook-noack / f-op-pending-ok / f-op-pending-with-receipt），**全部是 note_field 型**，不需要 id_scope，现有样本零破坏；5 份草案样本的 user_confirmations 均为空数组。需新增：task 型 draft/formal 正向各 1、task 型缺 id_scope 负向 1、id_scope 与解析结果矛盾负向 1、非 task 型携带 id_scope 负向 1。该类型 0.5.0 才进正式，**无旧数据迁移**。

**备选（若审查否决形状变更）**：保持现形状，解析规则固定为「object_type=task 时：值 ∈ 本草案注册 key 集 → draft；否则必须解析到快照既有 Task → formal；**两者同时命中 → 判歧义拒绝，要求用户重新确认**」。代价：合法但撞名的正式 ID 永远无法确认，且规则依赖解析顺序，不如显式判别可审计。

两案都不改「确认≠改值」语义；draft_revision 绑定与改值失效规则不变。

## 7 缺失历史引用的编码与展示（§6.7）

现状：ObjectRef / ExistingRef / TypedRef **都没有 deleted 标记**；正式 FocusSession/PlanItem 用 `task_ref_state/action_ref_state: RefState` 表达断引用，但那是业务记录字段，不是引用容器字段。**不得给引用容器私加未注册字段。**

策略（沿用并扩展 remap.js 既有隔离模式，1B 实施）：

1. **持久层编码不变**：引用保留原 ID 字符串原样落库/进备份。缺失与否是**读取时计算的状态**，不是持久字段——由 `assistant/refs.js` 类型化遍历（§5 全表）对照当前空间快照 registry 得出 resolved / missing。
2. **备份恢复隔离映射**：正式引用先查 liveMap（包内闭包）；解析不到的历史引用进 historyMap 隔离段（remap.js:69-76 现行机制扩展到助手路径），生成隔离 ID、**不伪造实体**；违反必须同包闭包的活引用（如 draft.thread_id、占用 plan_item_id 指向包内应有对象）→ 拒绝整个恢复。不允许「缺一个线程就静默丢掉它的草案」。
3. **展示**：草案/线程正文、title、quote、action_text 已随记录保存，缺失引用不删内容；UI 以「原对象已删除」只读标注呈现（标注来自读取时状态，不落库）。
4. **阻断使用**：所有编辑继续/重算/ready 判定前先跑失效检查；missing 活引用 → 草案标 needs_review，列变化清单，不静默重排。历史 partial/done 占用断引用继续计分钟（OccupancyEntry 现语义）；planned 断引用阻断核对，不按 0 计。
5. **撤销删除**：重新验证后引用恢复 resolved，可用性可恢复，但旧确认不自动复活（确认绑定 revision+值）。
6. **类型调整结论**：1B 不需要修改任何引用类型形状；若后续审查认为需要持久化失效清单，再提最小差异（当前不建议——读取时计算即可满足全部验收）。

today: str | None = None   # 真实北京今天；缺省按 start_date 解释（旧金标零破坏）

- 语义：真实逾期 = 截止**日** < today（整个截止日已过去）；`latest`（保守最迟可排日）与 `overdue` 判定分离。当天 datetime 截止不再误判逾期，走 `needs_deadline_day_window` 时段核对。

### 11.2 R4 截止确认适配器：绑定约定与协议守卫（已实施）

复用既有 `UserConfirmation` 形状（无新类型），约定如下（`normalize.js` confirmTaskDeadline 实施）：

| 场景 | object_id_or_key | old_value 基线 | new_value |
| --- | --- | --- | --- |
| create 草案目标 | 草案 task key | `null`（无既有事实） | `{value, precision}` 或 `null`（明确无截止） |
| update 既有目标 | 正式 Task ID | 快照 Deadline 的 `{value, precision}` 投影（无截止则 `null`） | 同上；等于基线 = 保留旧事实（宽松口径，允许旧 datetime 无秒） |

- 绑定校验：`draft_revision` 必须等于当前草案版本（options.draftRevision，默认 1）；`old_value` 与基线 JSON 深比较，不符 → `q-deadline-stale`。多条确认 new_value 不一致 → `q-deadline-conflict`。有值候选且无确认 → `q-deadline-confirm`，**不产出输入**。
- 闸门范围：仅被 work_items 引用且带**有值**截止候选的目标；无候选/无工作项引用的 update 不受影响（f-sem-update-deadline-ok 原样通过）。
- update 语义：未确认时澄清同时列旧事实与新候选（保留旧事实待确认）；确认后以新事实进 PlanningTaskFact 预览，**不预写正式 Task**（快照逐字段不变有测试断言）。
- 协议机器表达（models.py UserConfirmation 新增条件校验）：`object_type=task ∧ field_path=deadline` 时 old/new 值必须是 `null` 或恰 `{value, precision}` 投影，precision∈{date,datetime}，值过真实日历/时刻校验（宽松既有口径；新值严格候选规则由适配器按 keep-old 例外判定）。新增 4 样本：f-confirm-deadline-ok / f-confirm-deadline-none-ok / f-confirm-deadline-raw-string / f-confirm-deadline-bad-date。
- 与 D-2 的关系：本轮绑定约定按「create→draft key、update→正式 ID」的**操作语境**消歧，不依赖字符串形状猜测；审查已同意 D-2 增 `id_scope=draft/formal` 条件必填作为持久层显式判别，1B 实施时本协议守卫与 id_scope 叠加（碰名/错空间/错 revision/恢复映射测试随 D-2 落地）。

### 12.2 task/deadline 确认必须显式携带 old_value 与 new_value（C2，已实施）

- **协议（models.py）**：`object_type=task ∧ field_path=deadline` 时用 `model_fields_set` 检查 old_value/new_value **原始输入在场**；缺失拒绝（`task/deadline 确认必须显式携带 …`），不先默认补 null。`new_value=null` 且显式在场才是明确无截止。显式 null 属 fields_set，`model_dump`（含 exclude_unset）→ 再解析往返不丢失（verify_protocol.py 断言）。
