# M3 人工验收（2026-11-26）

结论：暂不通过，保留 3 项整改。正常改排闭环、事务回滚和历史保护已有有效实现，但新改排面板的未保存输入没有接入采用阻断；建议转为用户清单时会静默丢弃排程约束；当前全量测试有一项失败。

审查依据：M3 开工单、契约差异、2026-11-26 开发交回以及当前代码。本轮只读审查产品代码，复制验收脚本到独立目录并加入反例；未调用付费模型，未改业务代码，未提交/推送/发布。所有浏览器数据均为隔离虚构数据。

## F1 / P1：改排面板的未保存修改仍能沿用旧授权取消安排

位置：`frontend/src/components/assistant/ReplanPanel.vue:23`、`:60`；`frontend/src/pages/AssistantPage.vue:247`、`:557`。

ReplanPanel 的 selected、statement、rows 都是组件内的编辑状态，只发出 started 事件，没有向父页面或 store 传递 dirty/输入版本。父页面的 canAdopt 只检查原有通用内容和预算窗口，没有检查这个新面板。因此用户更改范围和分钟数后，页面仍显示“就绪核对通过，可采用”，旧预览和采用信封继续有效。

真实浏览器独立复现：

1. 选择 p-1/p-2 两条旧安排，填写 90 分钟，完成排程及范围确认。
2. 在改排面板取消勾选 p-2，把分钟数改为 180，不点击保存。
3. 采用按钮仍可点击；继续打开确认弹窗并提交。
4. 实际 p-2 仍被取消，新安排总量仍是 90 分钟。

日志：`unchecked=true, minutes=180`，但提交后 `p2=cancelled, newMinutes=90`。这里仍经过用户点击采用弹窗，不是后台自动提交；问题是表单中刚收回的替换选择和新工作量没有使旧采用资格失效，页面没有阻止保存旧意图。

最低修复要求：

- 新面板的范围、说明、清单、复用行动、拆分等所有编辑都纳入统一 dirty/输入版本管理。
- dirty 时阻断打开采用和最终提交；清除/失效旧 prepared，显示先保存并重排的提示。不能仅在点击“保存改排内容”后才失效。
- “请助手整理剩余工作”也须使用已保存的最新输入，或明确阻断未保存输入；生成中更改输入时，旧响应不得覆盖新编辑。
- 对采用弹窗已打开后发生变化的情形仍应在提交入口复核，不能只禁用外层按钮。

复验：取消勾选、修改分钟数、清空说明/工作内容、切换复用行动、载入建议后未保存，以及在途编辑，都应使旧方案不能被采用；保存并重新核对后才恢复。

## F2 / P2：载入建议再保存会清空最早日期和依赖等排程条件

位置：`frontend/src/components/assistant/ReplanPanel.vue:116` 的 loadSuggestion；`frontend/src/domains/assistant/replan.js:182-184` 的 buildReplanProposal。

loadSuggestion 只复制工作文字、分钟数、行动引用和拆分参数。保存会重新构造整份 proposal，其中 earliest_date 固定为 null、depends_on 固定为 []、priority 固定为 normal。用户核对分钟数并不代表同意删除原有开始时间、先后依赖或优先级。

真实浏览器独立反例：在隔离 fixture 响应中给工作项设置合法 earliest_date=2026-11-28，页面成功接收建议。用户点击“载入建议到清单”，再点击“保存改排内容”，该字段变为 null；继续排程和采用，安排实际出现在 2026-11-26 和 2026-11-27。

这是当前建议转换链路的缺陷，不是排程器不执行 earliest_date；约束在进入排程器之前就已丢失。依赖和优先级同样在该重建函数中被硬编码清空/重置，本轮浏览器动态证据专门验证了最早日期。

最低修复要求：

- 将建议转换为用户确认清单时保留有业务意义的日期、依赖、优先级和稳定工作项关联；如果重建 key，必须重映射依赖，不能直接清空。
- 核对页面展示这些约束，让用户明确调整；如初版确实不能承载某项约束，应提示并阻断该转换，不能静默删除后允许采用。
- 用户修改分钟数只改变其确认的输入；清单增删导致依赖失效时明确要求处理。

复验至少包括：最早日期仍约束最终日程；有前置依赖的两项工作经过载入、保存、刷新后仍保持依赖；用户确认的分钟数和既有行动复用不回归。

## F3 / P2：全量测试实际为 1382 通过、1 失败，交回成绩不可复现

位置：`frontend/src/tests/planning.refs.test.js:133`（f-plan-replacement-nonempty 的 null 预期），断言执行在 `:142`。

契约样本已改为 101 个 replacement_ids 的超限负例，但此测试仍按照“合法非空替换集”预期不抛错。当前独立运行结果：

`B1-09 冻结 planning fixture × validatePlanningInput f-plan-replacement-nonempty（reject）`

失败信息：`expected [Function] to not throw an error but 'Error: replacement_ids 最多 100' was thrown`。

产品拒绝 101 个 ID 是正确的，应同步测试语义。分别保留“合法非空且占用无重叠”的正例与“超过 100”的负例；不能把这项标成忽略，也不能放宽产品限额来让测试通过。修复后重跑并更新交回成绩。
