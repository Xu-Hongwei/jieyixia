## 1 本批要交付什么

建立可以安全保存、修改和读取“某天做某项工作”的前端基础，使后续统一周表直接使用同一套规则。验收重点是落库事实、事务和引用闭合，不是页面外观。

## 4 权威数据与输入规则

### 4.1 分清三个对象

Task回答“最终完成什么、什么时候交”；PlanItem回答“哪一天准备做什么、预计多久”；FocusSession回答“实际执行了什么行动、留下什么成果、用了多久”。三者不得互相猜测。

一条PlanItem只属于一个workspace和一个Task，同Task可跨天或同日有多条安排。工作说明允许与Action文字不同；同名Action也不得自动绑定。安排保存不修改Task.current_action_id、status、deadline或原便签。

### 4.2 新建字段

| 字段 | 新建规则 |
| --- | --- |
| id/workspace_id | ID在同一次保存意图中固定；空间在发起调用时捕获，禁止调用方伪造跨空间归属 |
| task_id | 必须是事务内仍存在的同空间、未完成Task；blocked允许安排，返回受阻提示 |
| date | 严格真实YYYY-MM-DD；拒绝2026-02-30等非法日，不自动滚动修正 |
| action_text | 字符串，去首尾空白后非空；不按文字识别Action |
| planned_minutes | 有限安全正整数；拒绝0、负数、小数、NaN/Infinity和非数值；UI转换字符串留给5A-1 |
| state/task_ref_state | planned / active |
| actual_minutes/focus_session_id | null / null，不拿预计分钟填实际分钟 |
| order | 由服务在事务内按目标日分配，调用方不得任意覆盖 |

调用方未指定日期时，在本次意图形成时读取实时北京时间今天并固定进输入；重试不因跨午夜变成另一日。后续UI在每次打开新表单时重读今天，用户改过的日期不被午夜刷新覆盖。

预计分钟由调用方明确提交；5A-1可给30分钟或已有行动估时初值，本批不偷偷补成“用户已确认”。

### 4.3 编辑与冲突前提

不开放通用对象patch。每个命令只接受白名单字段。编辑说明/估时、改期、取消、手工确认进度均携带“用户当时看到的相关字段快照”；事务对比最新事实，不符返回STALE_PLAN。无需为此增契约revision字段。

比较包括原Task归属、原日期、状态、说明、预计分钟，以及当前命令依赖的引用状态；执行历史始终事务内重新检查。它是相关字段的并发保护，不宣称能检测所有修改历史或ABA问题。

Task已完成/删除、空间已切换、引用不合法时拒绝新建/变更；历史读取仍允许。成功结果携带原workspace_id，晚到结果不能应用到新空间的store。

## 5 命令与状态规则

建议新增`frontend/src/domains/plan.js`，以纯函数返回现有风格的`{ puts, deletes, info }`，不直接触库。具体函数名可调整，以下能力和边界不得省略。

| 命令 | 允许条件与结果 |
| --- | --- |
| create | 创建planned，无任何Focus引用，字段按第4节 |
| edit | 仅active、planned且没有任何关联Focus；只改说明/预计分钟 |
| move | 同上；保留ID，改日期及目标日order；总截止不变 |
| cancel | active、planned/partial、没有未结束Focus；显式确认后设cancelled，保留记录与历史 |
| confirmProgress | active、无未结束Focus、planned/partial；显式选择partial或done；不完成Action/Task |
| arrangeAnotherDay | 新建另一条安排；说明与分钟重新确认，不迁移原会话、不自动相减历史用时 |

done/cancelled/moved不支持“恢复planned”或覆盖编辑；继续工作应新建安排。相同命令的有效重试返回原结果，不因当前已done/cancelled而误报第二次失败。

### 5.1 以真实会话决定历史保护

- 判断依据是同空间、同任务、plan_item_id命中的FocusSession集合；不能只看快捷focus_session_id或actual_minutes。
- 任何未结束会话（含暂停、恢复待核对及旧版未结束记录）：拒绝编辑、改期、取消与手工进度，返回UNFINISHED_FOCUS，附可定位的会话ID。
- 任何已结束会话：拒绝原地改日期、工作说明、预计分钟，返回PLAN_HAS_HISTORY；允许明确确认进度或取消，不删成果。
- 没有会话也允许用户确认partial/done；actual_minutes仍为null，代表未记录用时。
- 旧/导入planned已有已结束会话：只读时标记需核对；允许用户明确确认partial/done/cancelled，不自动改状态。确认命令展示/返回完整历史摘要，并在同一事务按本单口径重算摘要；不静默启动全库修复。
- moved仅兼容读取，不产生伪造的“改期链”；deleted引用只读，不开放新操作。

本批服务接口要有明确的确认输入；后续UI负责实际展示确认。不能只传一个任意布尔值就绕开“已看到哪些对象/截止风险”的事务校验。

### 5.2 顺序

同空间同date按order升序、再按ID稳定排序。新建及跨日改期追加到目标日现有最大有效order之后；其它记录不批量改号。取消/完成不改变原顺序，同日改期是无操作。缺省order按契约0解释；读取不改写旧记录。

## 6 持久化、重试和失败

建议新增`frontend/src/services/plan/service.js`，向app store提供薄入口。全部业务校验和写入在事务里，UI禁用按钮不能代替校验。

由于本批还需要操作回执及并发保护，命令优先沿用transformFocusAtomic覆盖docs+focus_runtime；这不代表“创建Focus”。不要新增数据库store。纯读取无写入。

### 6.1 同一次保存只能一条

- 服务提供固定的操作信封：requestId、issuedAtMs、操作名、workspace、目标ID及不可变输入；新建的PlanItem ID也预先固定。
- 相同信封重试返回同一结果；相同requestId换输入/目标/空间必须拒绝。用户修改输入或明确再添加相同内容，是一个新意图。
- 可在既有focus_runtime中使用独立`plan_ops`命名空间存本地回执，不改变业务契约、不混用Focus的ops/session/run记录；如抽共用工具，保持现有Focus行为。
- 回执与业务变更同事务提交；不得先保存安排再补回执。约束窗口复用现有请求规则，迟到超窗明确拒绝，不因回执清理后当新请求重新执行。裸requestId无验证依据时拒绝。
- 回执只存校验重放所需内容，不存原图、成果正文等资料；不进入业务备份。新空间恢复使用新的操作意图，不承诺跨备份恢复重放旧操作。
- 同一次新建双击/跨服务实例重试/刷新后重试必须一条。仅靠按钮busy、本页Promise队列或同内容查重不合格。

### 6.2 相同内容是提醒，不是永久去重

同任务+日期+规范化说明已有非cancelled条目时，先返回DUPLICATE_PLAN及对应ID，不写库。用户看过后明确仍要添加，发新意图并携带已确认的匹配ID集合；事务内重算集合，变化则重新确认。

跨日相同说明允许；同日不同说明允许；允许用户明确创建完全相同内容的第二条。不得用内容hash代替PlanItem身份。

### 6.3 并发和原子失败

事务内同步完成计划计算，不在IndexedDB事务回调中等待网络/任意异步工作。异常整体回滚，返回稳定code及可读message。重试使用原信封；修改输入后使用新信封。失败不清草稿，不改Task，不留下半条计划/半份回执。

编辑冲突、重复确认范围变化、截止风险变化分别返回明确错误，不通过“重试直到成功”覆盖别页改动。store只应用提交成功且归属匹配的结果。

## 7 周聚合与待安排：先提供数据，不改页面

新增纯读取能力，接受明确workspace数据、周起始日、now；复用time.js的北京规则及week.js的deadlineSlot。不得引入第二套设备本地时区计算。

建议统一输出每天`plans / planHistory / deadlines`，保留原weekGrid调用兼容；通过新函数或适配层接入，不能让旧页面结构突然失效。

- plans：活引用、未完成Task下的planned/partial；排序按第5.2节。
- planHistory：done/cancelled/moved、已删任务引用，以及Task已完成后保留的旧安排；保留原因可供后续UI解释，不当成今天待做。
- deadlines：只从Task.deadline计算，每Task最多一次；含Z/偏移先转北京落日，日期型不补23:59；已完成Task保留标识并淡化由UI处理。
- 同Task三天安排、一个总截止，输出上区三条，下区一条；无截止Task的安排仍在上区；周外记录不丢失，只是不在当前七日列。
- 两个计数分开：工作安排数与截止任务数，不合成“本周任务N项”。

待安排分类针对所有未完成Task、读取该Task全量计划，不只看当前周：

| 分类 | 判定 |
| --- | --- |
| 已有后续安排 | 至少一条今天或未来的active planned/partial |
| 待续安排 | 没有上项，但有过去的active planned/partial |
| 尚未安排 | 上述均无；包括只剩done/cancelled/moved历史的任务 |

“尚未安排”不是“从未安排过”的历史断言；Task已完成或删除不进入待安排。未来已有安排同时也可能存在过去未处理项，因此另外输出过去未完成集合，不能被单一分类隐藏。

不自动把过期安排移到今天，不因Task无截止隐藏它；全部Task仍由原任务数据入口读取，不靠当前周反推全集。

## 8 截止风险规则

风险是只读派生结果，不落新业务字段，不自动移动安排或改Task.deadline。

| 情况 | 派生结果/保存规则 |
| --- | --- |
| 无截止 | no_deadline，可安排 |
| 安排日早于截止北京日 | before_deadline；不保证估时足够 |
| 与日期型截止同日 | due_same_day，显示当日截止，不制造23:59 |
| 与含钟点截止同日 | due_same_day_timed，显示真实北京钟点并提醒核对，不宣称小时安排可行 |
| 安排日晚于截止北京日 | after_deadline；创建/改期必须明确确认 |
| Task截止已过 | 独立overdue标记；完成Task不标逾期 |

先后关系与overdue是两个维度，允许同时存在。纯风险计算返回所依据的截止值/精度和安排日，后续确认回传这些事实；事务内Task截止变化则返回DEADLINE_CHANGED要求重新核对。日期型从北京次日00:00起逾期；datetime按真实瞬时比较。

不按“还有几小时”自动判断一天的安排放得下，也不在5A-0引入每日容量算法。

## 9 实际用时与执行边界

### 9.1 本批实现纯汇总，不提前接真实结束流程

输入PlanItem及相关Focus集合；只纳入同空间同Task、plan_item_id正确且ended_at非空的会话，按ID去重。相同ID出现冲突数据时报告问题，不能随数组顺序随便取一条。

返回：endedSessionCount、totalMs、actualMinutes、latestEndedSessionId及异常信息。未结束会话不混入已记录累计；invalid引用或非法负时长不得静默算成有效记录。

actualMinutes规则：先sum(accumulated_ms)，再floor(totalMs/60000)，只取整一次。无已结束会话=null，有已结束会话但不足一分钟=0。两段各40秒应得总80秒、整数1分钟。最近已结束会话按ended_at真实瞬时排序，同刻按ID稳定决胜；不采用数组末项。

读取时可返回“缓存与明细不一致”，但不偷偷回写旧actual_minutes/focus_session_id。明确确认进度时可按已展示历史更新；5A-2新会话结束则在既有focus原子事务中重算并写入，不能先end成功再补写计划。

### 9.2 本批提供执行资格校验及接入说明

纯校验至少覆盖：PlanItem active、planned/partial；Task未完成且同空间；明确传入有效同Task未完成Action；不通过action_text查Action。done/cancelled/moved/deleted不允许新开工作。

服务返回“已有同安排未结束会话”可供回到工作；另一安排与其它空间冲突仍由既有Focus规则处理。回到暂停不等于自动继续。

本批不把校验helper存在宣称为执行入口已受保护：生产focus.begin/end的接入及双结果UI在5A-2完成。交回附具体接入位置、一个事务内如何合并Focus/Action/PlanItem写集，以及错误如何整组回滚。无plan_item_id的旧执行流程必须保持原行为。

## 10 删除、撤销与备份

### 10.1 本批必须落地的引用修复

修改matter.js相应删除计划并回归删Task、便签联删、undo：

1. planned且无任何Focus引用：随Task删除，撤销快照保留。
2. 有未结束会话：按既有保护拒绝，不把暂停视为已结束。
3. planned但已有结束会话：拒绝整个删除，PLAN_PROGRESS_REQUIRED；返回需确认进度的安排ID，不生成悬空引用。调用者在后续UI核对进度后重新确认删除。
4. partial/done/cancelled/moved历史：保留PlanItem并按契约断Task引用；会话历史/成果继续闭合。
5. 删除Action不连删PlanItem；撤销只恢复本次移除/断开的对象，若后续已有新修改则沿用冲突感知规则，不覆盖新安排或新成果。

如果跨页在删除确认后新增关联安排，导致受影响计划ID/保留方式变化，必须要求重新确认；扩展现有影响快照时保持旧调用兼容，并在事务内对旧快照至少实施实际历史保护，不能因旧调用未传新字段绕过保护。不要扩大到无关便签/其它任务。

### 10.2 真正的备份往返

至少一个独立测试走现有真实ZIP编码→解码验证→重映射→新空间提交，不仅测试JSON拷贝。数据包含：同任务三天安排、无截止任务、planned/partial/done/cancelled/moved、已删除Task历史、多个ended Focus、快捷会话引用、整数实际分钟及工作成果。

断言PlanItem和Focus双向关联重建、原任务截止不变、历史状态不丢、原空间内容不变；回执不作为业务恢复对象。沿用现有运行/暂停恢复待核对规则，不自动启动计时。

测试使用合法完整数据；“缓存与明细不一致”的诊断样本另测，不用放宽现有备份校验来让脏样本通过。本批无新字段原则下，应主要补往返用例；若必须改backup代码，解释现有路径哪里实际不满足。
