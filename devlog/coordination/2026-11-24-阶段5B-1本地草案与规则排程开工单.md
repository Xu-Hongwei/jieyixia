# 阶段 5B-1 本地草案与规则排程开工单

日期：2026-11-24（北京时间）。本文将本轮“5-1b”按当前进度解释为 **5B-1**。

承接：[5B-0 整改人工验收](./2026-11-24-阶段5B-0整改人工验收.md)、[5B-0 协议决策](./2026-11-24-阶段5B-0协议决策.md)、[迁移与采用协议](./2026-11-24-阶段5B-0迁移与采用协议.md)。

## 1 交付目标

**把已经结构化的目标、步骤、用户要求和现有日程，变成可信的七天草案；可以修改、重新计算、保存、刷新恢复及完整备份。**

本阶段通过固定的虚构模型结果验证这条链路。用户最终希望的“截图＋文字＋额外要求→智能体自动排表”分工为：5B-1 做本地规划基础，5B-2 做确认后正式采用，5B-3 接真实建议接口，5B-4 接完整助手页面。当前阶段不能展示“已自动创建任务”或“已加入日程”的成功结果。

产品关系继续保持：Task 是交付目标及总截止；Action 是行动步骤；PlanItem 是某天打算投入的工作；FocusSession 是实际执行。一个任务可以分多天安排，截止日期不会因安排日期变化而改变。草案段不是正式 PlanItem，不能出现在现有日程中冒充已安排事项。

示例：报告总截止周五，剩余工作 200 分钟；截止前只有三个可用日，每日预算 60 分钟、缓冲 15%。草案最多安排 153 分钟，明确显示 47 分钟未排；用户调整预算后重新计算。不会偷偷占用禁用日、推迟总截止，或把缺口标成完成。

以下为建议路径，可依仓库命名小幅调整，但职责不可混合。

| 模块 | 职责 |
| --- | --- |
| frontend/src/domains/planning/normalize.js | 校验建议、解析引用、把已确认要求和快照转为 PlanningInput；返回待澄清项 |
| frontend/src/domains/planning/schedule.js | daily-v1 七天纯规则排程 |

| frontend/src/domains/assistant/draft.js | 草案修订、历史快照、确认失效、状态和限额纯规则 |
| frontend/src/domains/assistant/refs.js | 类型化引用遍历；供校验、失效检查、备份重映射共用 |
| frontend/src/services/assistant/context.js | 按捕获空间读取一致快照，组装上下文；哈希在事务外 |
| frontend/src/services/assistant/drafts.js | 线程/草案读写、并发版本检查、事务编排 |
| frontend/src/services/storage/db.js | v4 迁移、助手读写、一致导出快照、恢复事务、清空 |
| frontend/src/services/backup/* | v1/v2 分版本适配、校验、映射、恢复，不重复另一套 ZIP 系统 |

概念调用链：

```text
固定建议 + 用户确认要求 + 当前空间一致快照
  → 校验/规范化（不完整则返回待澄清）
  → PlanningInput
  → scheduleDaily（纯函数）
  → 独立校验 PlanningResult
  → 保存当前草案版本与历史
  → 导出/恢复
```

算法不能访问数据库、网络、Pinia、当前系统时间或随机 ID。默认“今天”由调用层按 Asia/Shanghai 读取并显式传入；测试可传固定日期。同输入应得到完全相同的语义输出，稳定排序不能依赖数组遍历顺序或浏览器语言环境。

建议接口为 `normalizePlanningContext(snapshot, proposal, requirements, context)`、`scheduleDaily(input)`、`validatePlanningResult(input, result)`。名称可调整；不要在 PlanningInput/Result 内加入未经批准的便利字段。排除清单、原始确认信息按已冻结草案层保存，由组装层配套传递。

## 5 排程规则

### 5.1 输入和事实核对

1. 窗口为起始日及随后六天，时区固定 Asia/Shanghai；未来窗口允许显式选择，过去窗口只能查看旧草案，不生成当下可用的新建议。
2. 每日预算为 0–1440 的整数；0 表示明确不可安排，null 表示还没确认，不能静默当 0 或默认一小时。未知预算返回待澄清，不调用排程器。
3. buffer_pct 为 0–50 整数，默认 15；任务最多 20、工作项最多 100，其余沿 limits.json。
4. remaining_minutes 为正安全整数或 null。未知不能偷换为 0，也不能默认采用原 Action.minutes 或从专注历史自动扣减。
5. 检查未知 ID、跨空间、跨任务、重复 key、依赖环、已完成行动及任务状态。已完成/不再可执行的目标不作为新工作投入；需要另一个交付目标时由用户明确建立。
6. Task link/update 的 draft key 必须解析到它实际指向的既有 Task。归属比较使用解析后的身份；保留原有临时 key 用于展示。不得仅因两个引用字符串不同就把合法别名视为两个任务，也不得按同名自动合并。
7. 窗口占用必须读取当前空间全部相关 PlanItem，包括未选中任务；组装阶段按 ID 去重，同一 ID 内容矛盾直接报错。纯算法入口收到重复占用 ID 时仍拒绝。
8. 对同一目标已有未来安排、又提出新增剩余工作，落实 D12 额外工作确认；不能根据 action_text 猜测哪些安排已覆盖本次工作。
9. 明确排除项不生成段；依赖排除项的后继不会自动视为前置已完成。用户应明确调整依赖或补足事实，否则保留依赖阻断。
10. R1–R4 的回归必须跨到 JavaScript 实现：旧时间格式、判别引用、done 行动 direct/reuse、create/update 截止证据统一校验。

### 5.2 日期与容量

```text
allocatable = floor(budget × (100 − buffer_pct) / 100)
buffer_minutes = budget − allocatable
committed = 唯一占用记录 planned_minutes 之和
available_for_new = max(0, allocatable − committed)
overbooked = max(0, committed − allocatable)
free_after = max(0, allocatable − committed − allocated)
```

planned/partial/done 均按原计划分钟占用原日期；cancelled/moved 不占用。完成不自动释放预算，FocusSession 投入不二次相加，提前执行不自动搬移计划日期。历史断引用 partial/done 继续计入；planned 活引用失效要阻断核对，不能视为零占用。

旧截止无秒、无时区、小数秒均继续可读；无时区按北京时间解释。不要依赖宿主时区解析日期字符串，也不要以“每次加 24 小时”替代日历加一天。

日期型截止允许截止当天；精确时刻截止先转换为北京时间，按天规划默认最晚排在前一天。当天有剩余容量但无法证明能在具体截止时刻前完成时，输出 needs_deadline_day_window。无截止目标只受七天窗口限制，不能新增一个“窗口最后一天截止”。逾期需用户明确补做授权；获授权后可排当前窗口，原截止不改，保留逾期警告。

### 5.3 排序、拆分与依赖

- 仅从前置全部安排完成的就绪项中挑选；按有效截止、优先级 high/normal/low、稳定 key 排序，无截止在后。
- 可拆项从最早允许日向后填充。非最终段至少 min_segment_minutes，默认 25；最终余量允许更小，所有段必须为正分钟。
- 不可拆项寻找能完整容纳它的最早一天；找不到就保留未排项，不偷偷拆分。
- 前置跨多天时，后继不能早于前置最后一段；同日后继 order 必须严格在最后前置段之后。不能仅检查“前置在数组里更早”而把后继排到前面的日期。
- 前置尚有缺口、未知估时或被排除时，后继不产生段，说明依赖阻断；与它无关的工作仍可安排。
- 分段 key 由稳定输入键及稳定分段顺序派生，重复计算一致；不是正式 PlanItem ID。
- replacement_ids 必须为空；不取消、不覆盖、不搬移旧安排。本算法不做隐藏回溯或随机重排。

### 5.4 结果与说明

每个未排项必须给出冻结枚举中的原因，遵循协议决策 §7 的适用前提；多个原因同时存在时按已冻结金标解释，新增歧义先形成明确反例和规则差异，不为让实现通过而重写金标。

对每个已知且未排除工作项满足：`输入剩余分钟 = 所有段分钟之和 + 未排分钟`。未知和排除分列，不能混进数值缺口。每日新安排不能突破可用容量。

`complete` 只是排程完整性，不等于草案可采用、更不等于业务已保存。`ready` 还要求事实/证据/确认完整、无阻断、未知项已处理，缺口和既有过载已分别确认。用户可以保存不完整草案，不能把保存成功解释为 ready。

错误文案使用“当前规则未找到完整安排”，不声称数学无解。明确显示已排、未排、待估时、排除、既有占用及缓冲，避免只显示一个看似全部完成的总进度。

## 6 5B-1A 的契约差异包

在改变正式版本前交回一份精确差异文档，包含下列内容；同时可以完成隔离的排程器及 fixture 测试，不需空等。

1. 新增类型和正式唯一来源。避免把 88 个提案定义不加区分全部复制进生产；生产不 import proposals。通用枚举/已有模型复用，新助手类型清楚归档，生成器可重复生成。
2. 0.4.0 schema 原始快照、摘要及固定回归输入。v1 备份始终使用冻结的旧 schema；冻结文件不能在每次生成时被新版内容覆盖。
3. 新增持久对象/备份字段与旧业务模型的逐项差异。Task/Action/PlanItem/FocusSession 语义保持不变，旧 PlanDraft 不被重解释成 AssistantDraft。
4. 当前 AnalyzeResponse 和 HealthResponse 的 schema_version 默认取正式 SCHEMA_VERSION。必须明确升到 0.5.0 后这两个响应的预期版本、兼容消费方和测试，不能写“前端升版，后端绝对零影响”。推荐保留统一版本声明并验证 additive 兼容；API_VERSION、路由及 analyze 业务行为不变。确需分离版本常量时列出具体方案，先审后改。
5. 引用路径完整表，按真实类型字段列举；不能仅写 `proposal.existing_refs` 这种概念路径。至少覆盖 task link/update.target_id、action reuse.target_id、task_ref/action_ref、全部嵌套 evidence、requirement 的类型化 value、planning_input/result、source_refs、消息 refs、applied_summary、revision_history。
6. `UserConfirmation.object_id_or_key` 既可能是正式 ID 也可能是局部 key，不能按字符串是否出现在 map 中猜。列明判别依据；如现有形状不足以无歧义解释，提出最小字段差异和迁移方式后审查。
7. 缺失历史引用的编码与展示策略。当前 ObjectRef/ExistingRef 并没有统一 deleted 标记，不得擅自加未注册字段；明确如何隔离映射、保留可读内容、阻断使用，必要类型调整写进差异包。
8. 新 store 的索引、事务范围、恢复回执影响和清空范围；给出版本升级前后样本，而非只有一张目标架构图。

采用层的协议继续保留给 5B-2；5B-1 不为演示方便临时实现一个绕过确认的 apply。

## 7 草案编辑与保存规则

### 7.1 服务能力

提供创建线程、读取当前空间线程/草案、创建草案、修订草案、重新排程、保存、读取历史、标记待核对/放弃等服务接口。当前不新增正式页面；用测试夹具和隔离验收入口调用真实服务。

草案写入捕获空间、世代、draft_id、预期 revision 和不可变快照。事务内比较最新 revision，两个标签同时编辑只有一个成功，另一个返回可解释冲突，保留用户当前输入；禁止最后写入静默覆盖。原位对象后续突变不能污染已经排队的写入。

### 7.2 修订与确认

- 修改目标、估时、要求、依赖、范围、窗口、占用基线产生新 revision；旧版本存只读历史。
- 单纯保存同一版本、重读、重试同一保存不新增 revision；相同输入重算不制造无意义历史。
- 新 revision 清理旧授权有效性，重新检查与本次内容相关的确认；不能把旧版本确认直接当作新版本授权。
- 最多 20 版本（当前加历史），整体 JSON UTF-8 序列化不超过 1MiB；超限拒绝覆盖旧草案，提示由用户显式基于当前内容新建草案，不偷偷删历史。
- 线程 200 消息、单条 16000 字符；超限同样不静默截断。
- 编辑后的排程结果和所依据的输入必须同版本保存；旧异步计算晚到时不得盖掉新版本。

### 7.3 状态与新鲜度

按冻结状态机实现，不根据存在 planning_result 就标 ready。本阶段服务不能自行生成 applied、ApplicationReceipt 或业务采用成功消息。

打开/恢复/重新计算时核对当前北京时间日期、引用、任务/行动状态、资料字段和整个窗口占用。事实变化将当前可用性标为 needs_review，保留旧草案可读并列出变化；不静默重排并继续确认。跨午夜用注入时钟和浏览器时钟控制验证，无需真实挂机等午夜。

同库刷新与备份恢复是两种路径：同库 generating 按规则中断待核对，applying/result_unknown 保持结果待核实，不擅自断言未保存；备份恢复到新空间按第 9 节去除原执行权限。5B-1 不发起采用，因此后者仅作兼容状态测试，不冒充真实采用恢复已实现。

## 8 存储迁移与删除兼容

DB v4 只新增 assistant_threads、assistant_drafts、assistant_ops，不重写 sources/docs/workspaces/focus_runtime。保留 onversionchange 让位和 onblocked 可解释错误。

assistant_ops 本阶段只建立存储边界，不创建 pending 采用信封，不开放通用写接口绕过将来的采用服务。为将来台账确定主键与 application_id 映射；keyPath 与记录形状必须一致，不能建 id 主键却保存不带 id 的 ApplicationReceipt。

线程与关联草案需要同时创建/更新时使用同一事务。空间切换发生在提交前则拒绝；提交后才切换时按捕获空间返回已发生事实，不把成功错误地描述为回滚。

删除资料、任务、行动后，旧线程文字、草案与历史仍可读。允许立即失效或读取时重新核对，但所有“编辑继续/重算/ready 判定”都必须先检查失效引用，不能再写回缺失对象。撤销删除后重新验证，可恢复可用性，不自动复活旧确认。

既有 `clearWorkspace` 用于演示空间重置，当前只清 sources/docs/focus_runtime。本批必须扩展到三个助手 store，仍按目标 workspace_id 过滤并在同一事务完成；不得清掉个人空间数据或留下旧助手资料串进重新生成的演示空间。常规资料删除不能顺带清助手线程。

Source 继续原文不可变、新资料新 ID；不为草案功能增加同 ID 覆盖原图/原文的路径。

## 9 备份与恢复必须同批闭环

### 9.1 导出

沿用现有备份模块。v2 即使助手资料为空，也含 assistant_threads 和 assistant_drafts 两个必需 payload；计数、原始字节哈希、大小校验完整。

**sources/docs/工作区元数据/线程/草案必须由同一个只读事务取得一致快照**，不能先读业务，再另开事务读助手。否则并发编辑会导出彼此不对应的版本。Blob 读取、哈希、压缩在事务结束后处理。

assistant_ops、可执行信封、在途请求、锁/租约不进入归档。applied_summary 仅是历史展示信息，不能赋予新空间执行权。现有 ZIP、总解压、单 JSON、图片和条目限额不放宽；助手数量较多超包限额时明确拒绝，不删除旧对话凑大小。

### 9.2 校验与映射

v1/0.4.0 用旧分支完整恢复，助手 store 为空；v2/0.5.0 用新分支；其它组合拒绝。旧包不得被新 schema 猜测性修补后标为完整恢复。

按 1A 批准的真实引用路径，对正式对象、thread、draft 全量生成新 ID；草案局部 key 保留，正文、quote、用户文字中的 ID 字符串不替换。全部 revision_history 也纳入映射和校验。

历史已删除对象使用隔离映射，不伪造实体。活引用异常则明确拒绝或恢复为不可执行的待核对内容，按批准的分类规则处理，不把活对象跨到原空间。不允许“缺一个线程就静默丢掉它的草案”；违反必须同包的引用则拒绝整个恢复。

### 9.3 恢复落库

沿用已有恢复准备、幂等回执、全量 add 及单事务提交。恢复事务增加两个助手 store，assistant_ops 永不导入；业务与助手任一记录写入失败，整个新空间回滚。恢复重试不能生成重复空间。

未应用草案统一 needs_review，移除旧 fact_baseline 和采用授权，保留可读内容及必要原状态说明；历史快照中的确认只能展示，不能成为当前授权。applied 保持历史只读，discarded 保持放弃。旧空间与原包不改变，不自动创建任何额外 PlanItem。

IndexedDB 事务 mode 作用于整个事务，并非每个 store 各一个模式。需要原子写入时整个事务使用 readwrite，再由代码约束 sources/focus_runtime 等只读用途；不能实现成多个分散事务后宣称原子性。
