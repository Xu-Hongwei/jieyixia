## 1. 目标与分工

把工作组织为“明确问题 → Qoder 提出选择 → 审查取舍 → Qoder 实现 → 验证 → 留档”的小步循环，同时形成可用于比赛提交的真实过程材料。

| 角色 | 责任 |
| --- | --- |
| 参赛者 | 确认产品目标、重大范围取舍、审查结论及最终提交内容 |
| 总工程师协作 | 拆任务、整理方案与验收建议、通过 Qoder 界面推进、核对结果及整理资料 |
| Qoder | 检查项目、比较实现方案、开发修改、运行验证、通过 Qoder Sites 完成部署流程并记录实际过程 |
| 产品前端队友 | 依既有团队分工实现产品 UI；涉及交接先准备文档，不代发消息 |

过程记录的审查栏目统一称“人工审查”。该栏目区分“辅助意见”“待人工确认”“人工已确认”，没有得到参赛者确认的意见不得写成人工决定。原始对话、截图和执行来源保持真实，不重写历史操作归属。

协作文档不是产品代码。产品开发与部署通过 Qoder 执行，实际使用方式在作品介绍中如实说明；完整规则对辅助工具的要求仍需核实。

## 3. 每轮推进规则

1. **观察**：确认 Qoder 当前任务和运行状态。已有任务正在修改时，先让其完成并留档，避免并发改同一文件。
2. **任务卡**：每轮一个编号、一个主要目标；明确范围、允许修改文件、验收条件和停止点。
3. **方案选择**：遇到实质取舍，让 Qoder 给出 A/B 方案、代价、推荐及理由。普通局部修复按已授权范围推进；重大产品和接口取舍交参赛者确认。
4. **实现**：Qoder 按选定方案执行。保存失败或测试失败时，先定位原因，不能为得到通过结果直接删除有效断言。
5. **核对**：检查实际改动和验证输出。分别记录“Qoder 报告”“独立复核”“人工确认”，不能互相代替。
6. **留档**：保存原指令、方案、变更摘要、失败及修正、测试结果、截图、遗留问题，再进入下一轮。

状态用语：计划中 / 已下达 / 运行中 / 待审查 / 需返工 / 已验收 / 已归档。任务“完成回复”不自动等于“已验收”。

用户已授权通过 Qoder 进行日常任务拆分、界面操作和资料保存。保留已有改动；公开发布、对外提交、删除资料等按届时具体授权及实际操作要求处理。准备可审阅的成品后再处理最终发布，不提前反复询问。

### C01 的实施边界

先让 Qoder 比较“最小存储边界修复”与“抽出仓库层”的取舍，推荐适合当前规模的方案。第一轮只诊断、给方案及验收设计，待审查后实施。

修复应覆盖：

- 存储边界生成独立快照，处理嵌套响应式值，保留 Blob/File；不使用 JSON 转换图片。
- 在副本上修改，事务完成后再更新界面；失败保留原记录、更新时间及编辑输入。
- 明确区分网络失败、模型失败和本地保存失败。
- 分析成功但保存失败时保留待保存结果，重试保存无需再次调用模型。
- 同一记录保存期间避免冲突写入；失败后可重试。
- 保留现有数据库、表及用户数据；无需迁移的方案优先。

验收用例：嵌套响应式数据写入、图片回读、确认/编辑/审阅/完成后刷新恢复、写入异常、事务中止、失败重试、重复点击、分析结果只重试保存。重要存储行为需要真实浏览器 IndexedDB 验证，模拟测试不能单独代替。

## 6. 归档位置

沿用 [开发日志规范](../README.md)，本目录作为过程证据目录的子目录，不另建竞争的主档案。

```text
devlog/
  YYYY-MM-DD.md                         当日主日志，由 Qoder 补自己的执行记录
  coordination/
    总工程师协作与比赛留档.md             本文：流程、任务顺序、提交材料清单
    YYYY-MM-DD-Cxx.md                   每轮任务卡、指令、方案、审查与结果
  assets/YYYY-MM-DD/                    经过检查、可公开的截图
  private-evidence/YYYY-MM-DD/          原始截图与规则附件，默认不入库
```

原始证据可能包含账号、用户资料或界面上下文，先存 private-evidence。公开前检查并生成适合展示的副本，原件保留。证据索引记录时间、路径、SHA-256、对应任务及公开状态；没有拍到或保存成功的截图标待补。

历史日志中“无法截取 Qoder 桌面”是历史运行条件。本次桌面操作若成功截图，可补充为新增能力，不回填伪造旧日期截图。
