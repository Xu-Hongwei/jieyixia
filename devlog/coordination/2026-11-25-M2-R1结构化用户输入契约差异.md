# M2 R1 结构化用户输入契约差异（2026-11-25，先差异后动手）

依据：用户裁定「把用户输入单独存成字段，不再从拼接文本里猜是谁说的」；
《2026-11-25-M2整改人工复验》R1「若需小幅协议增量，先写差异，不以删除问题或清空证据绕过校验」。
本文件先于代码修改提交；实施后在文末补实际核对结果。

## 1. 动机（R1 残留）

现行澄清续轮把「原始要求 + 历轮问/答」合成为一条 role=user 文本归档，出处接地靠机器固定标记逐行解析用户段。
残留缺口：**模型提问本身若含换行 +「答：…」行**（如「请确认截止日期，例如：\n答：11月30日」），
行解析会把注入行误判为用户回答段——仍是「从拼接文本里猜是谁说的」。
结构化字段后，问题内容无论含什么标记都永远留在 assistant_question 字段，不取得用户身份。

## 2. 新增类型（2 模型 + 1 渲染函数 + 5 格式常量，contract/assistant_models.py）

| 类型 | 形状 | 说明 |
|---|---|---|
| ClarificationTurnRecord | assistant_question: str(1..500)；user_answer: str(1..16000) | 一问一答。question 上限与 ClarificationQuestion.question 同口径；user_answer 由前端按用户实际提交填写，绝不来自模型输出 |
| UserAuthoredInput | original_user_request: str(1..16000)；clarifications: list[ClarificationTurnRecord](≤50，默认[]) | 真实用户输入的结构化记录；核验「用户明确要求」只读本类型字段 |
| render_user_authored_text(ui) | 纯函数 | clarifications 为空 → 原样返回 original_user_request；否则按既有机器固定标记渲染（原始要求：/空行/此前的澄清问题与我的回答：/问：/答：/空行/请结合以上回答继续生成方案。）。模型读到的合成文本由本记录渲染，单一来源 |
| CLARIFY_* 常量 ×5 | 字符串 | 格式标记的契约权威定义；前端 clarification.js 与后端 semantics.py 为同口径镜像（JS 无法 import Py） |

## 3. 既有类型增量（两处可选字段，additive optional）

- **ThreadMessage.user_input: UserAuthoredInput | None = None**（持久层，落 IDB/进备份）。
  新增 validator：user_input 非空时 role 必须为 user。旧记录缺字段 → None，照常通过。
- **AssistantProposeRequest.user_input: UserAuthoredInput | None = None**（HTTP 请求层）。
  新增 validator：user_input 非空时 render_user_authored_text(user_input) 必须与 user_message 完全一致
  （模型读到的上下文 = 被核验的结构化记录，杜绝两份数据分叉）。不一致 → 请求级拒绝。

## 4. 核验规则变化

- 后端 semantics.check_evidence（UserMessageEvidence）：请求带 user_input 时，
  用户段 = [original_user_request] + 各 user_answer（trim 非空），摘录须落在某段内；**不再解析文本**。
  未带 user_input 的旧请求/旧 fixture 保留现行标记解析 fallback（既有负向用例全部保留，不放宽）。
- 前端 application.deadlineForCreate：归档消息带 user_input 时同上取结构化段；
  旧归档（无字段）保留 userAuthoredSegments 文本解析 fallback。
- 前端澄清恢复（restoreClarification）：优先读 user_input.clarifications；旧归档保留 parseClarificationHistory fallback。
- 模型提示词不变：模型仍读渲染后的完整问答上下文（不删除问题、不清空证据）。

## 8. 旧归档/旧请求来源收口（P2 整改口径，先差异后动手）

依据：《2026-11-25-M2结构化输入人工复验》P2——旧归档恢复把模型示例（问题内注入的「答：…」行）
经文本解析升级为新 user_answer，经确认/排程/采用后错误落为 manual。§4 当时保留的三个旧文本
fallback（前端恢复、前端采用接地、后端旧请求）即泄漏入口，本节将其全部收口。

### 8.1 信任规则（三入口同一口径）

用户段（可用于 manual 出处核验/升级为 user_answer 的内容）只有两个来源：

| 记录形态 | 用户段 |
|---|---|
| 带 user_input 结构化字段 | [original_user_request] + 各 user_answer（trim 非空）——不变 |
| 旧记录，content 为合成澄清格式 | **[]（零可信段）**——不解析、不猜测，任何部分都不取得用户身份 |
| 旧记录，content 为普通文本（首轮原话/手动改值归档） | 整条 content（trim 非空）——不变，明确手动设置日期路径不受影响 |

合成格式识别 = **保守前缀判定**：content 以「原始要求：」开头即视为机器合成文本（该前缀是渲染器
的机器指纹）。只判断「这是合成文本」，**不做任何问/答角色解析**；格式被篡改/不完整的合成嫌疑
文本同样零可信段——宁让用户重填，不猜。用户原话恰以该前缀开头的极端情形按合成处理，重填即可，
属可接受的保守边界。识别函数 looks_like_composed_clarification(text) 新增于
contract/assistant_models.py（纯函数，不进模型注册表、不改 schema $defs），
前端 clarification.js 同口径镜像 isComposedClarificationText。

原 §4 的 userAuthoredSegments / _user_authored_segments 逐行问/答解析**从信任路径删除**（不新增
字符串规则，直接移除猜测）；parseClarificationHistory 降级为**仅供展示**（旧记录只读回显），
其输出绝不进入 history/user_answer/核验段。

### 8.2 三入口行为

- **前端恢复续轮（stores/assistant.js restoreClarification）**：旧合成记录 → history=[]、
  gen.legacyUntrusted=true、gen.legacyDisplay=parseClarificationHistory(content)（只读展示）。
  originalMessage 取首条非合成用户消息原文（首轮原话，可信）；若不存在则置空，续轮合成时
  以 ORIGINAL_MISSING 拒绝并提示重新发起生成。GenerationPanel 澄清面板显示警示：
  旧问答无法可靠区分角色，仅供展示，请重新填写真实回答；用户本轮实际提交的回答照常结构化。
  模型丢失旧轮上下文时可能重新提问——即重填路径，符合「有歧义的内容让用户重新填写」。
- **前端采用接地（application.js）**：旧合成消息零可信段 → 仅凭模型示例的 origin=user 候选
  无法接地 → DEADLINE_PROVENANCE_REQUIRED，提示在对话中重新提交明确截止后重排。
  旧普通消息（含首轮原话、手动改值）接地不变。
- **后端旧请求（semantics.py check_evidence）**：无 user_input 且 user_message 为合成格式 →
  segments=[] → 摘录不接地 → invalid_output（既有 502/≤2 次重试策略不变）；
  无 user_input 的普通文本请求照旧整条可信。
