## 1. 交付目标与阶段边界

**证明同一份七天草案能从固定结构化建议出发，经过用户修改、真实重算、保存、刷新、备份，恢复到新空间后重新核对并继续编辑。**

1A 已验证算法，1B 已验证存储与备份服务。1C 要验证这些能力连接后仍遵守同一套规则，并形成可复跑、可审查、可用于比赛说明的真实过程材料。

主链路：

```text
虚构截图/文字及明确要求
  → 明确标注的固定结构化建议（fixture，非实时识别）
  → 真实规范化与七天排程
  → 展示容量与缺口
  → 用户修改要求 / 截止决定
  → 阻断旧计算 → 重算 → 当前版本确认
  → 保存 → 刷新读取 → 导出 ZIP
  → 原包校验 → 新空间恢复
  → 待核对、旧授权失效 → 重算/确认 → 继续编辑
```

本批默认不增加产品功能。允许新增隔离验收脚本、固定案例、最小验收展示页、行为回归及发现缺陷后的必要修复；继续使用生产算法、服务、IndexedDB 和备份模块。

以下范围保持冻结：

- 正式契约 0.5.0、DB v4、备份 v2/0.5.0，同时兼容 v1/0.4.0；冻结旧文件原字节不变。
- Task 是目标与总截止，Action 是步骤，PlanItem 是每日安排，FocusSession 是实际执行。助手草案分段仍不是正式 PlanItem。
- 不做正式采用、批量写业务对象、替换日程或自动开启专注；不生成真实采用回执。
- 不调用真实模型，不新增 propose 接口，不改后端路由、guard、网关或部署方案。
- 不增加正式助手导航或进行整站视觉改版，不增加生产离线缓存能力，不发布网站。

出现既有范围内的真实缺陷可直接修复并补测，交回说明原因与影响。若必须改动契约/DB/备份格式、算法产品规则或引入新能力，先提交具体反例和最小差异方案，停在相关变更处，继续不受影响的验收工作。

## 3. 隔离验收入口

### 3.1 实现方式

优先沿用已验证的 Playwright + 独立 Vite origin + 独立 BrowserContext。参考 `output/playwright/5b1b-final-2026-11-24/real-idb-1b.mjs` 的启动、清理和真实服务调用方式，1C 脚本另存。

最小验收展示页建议由自动化脚本在隔离 origin 的专用地址注入，只负责呈现实际返回值和触发真实服务调用，不注册正式路由、不纳入生产构建。现有数据管理页面负责真实导出、下载、上传、预览和恢复；不要复制备份页面。

验收页只需展示：

- 顶部：“本地规则排程验收 · 固定建议输入 · 未接真实模型”。
- 输入区：虚构资料、固定建议、用户已确认要求；区分原文、建议和确认。
- 七天预览：每日预算、缓冲、既有占用、新增草案段及未排分钟；总截止另列，日期不与安排混同。
- 草案信息：revision、持久状态、当前可用性、阻断原因，三者分别显示。
- 操作：修改要求/截止、重算、确认当前版、刷新后读取，以及进入现有数据管理页。按服务真实持久化结果提示“已保存”，不要虚构一个服务没有的独立保存接口。
- 细节折叠区：只读历史、关联身份与验收日志，供工程验收，不搬进正式用户页面。

不要求新设计系统、图标、动画或完整聊天界面。展示的所有分钟、状态、原因、版本和计数都来自实际结果，不得手填“成功”覆盖错误。

### 3.2 隔离与可重复执行

- 固定基准时刻 `2026-11-24T10:00:00+08:00`，算法时区 Asia/Shanghai；时钟依赖显式注入。跨午夜单独推进时钟，不等待现实零点。
- 每次运行使用全新浏览器上下文和虚构空间；端口先检测占用，遇占用选择新端口或明确退出，不结束未知服务。不访问用户常用 origin 或个人浏览器配置。
- 用于验证刷新/双标签的场景必须共享该场景的真实浏览器存储；不同场景彼此隔离。
- 拦截并拒绝模型、生产后端和非必要外部请求；报告实际命中。需要页面 healthz 状态时显式桩化并标注，不把健康桩当后端联调。
- 脚本通过、失败和异常均退出非零/零正确，并在 finally 清理自己创建的浏览器与临时服务；断言失败不能被“已有通过项”掩盖。
- 若环境不允许本机进程通信，记录为环境未执行，不记产品失败或通过；在允许的隔离环境完成后再交回。

## 4. 主案例：课程报告的三天投入计划

### 4.1 固定输入

建立一个虚构“课程报告”已有 Task，总截止 **2026-11-27（date）**，一个已有 Action，用户确认剩余工作 **200 分钟**，可拆分、最小非最终段 25 分钟。只设置一个工作项，避免把依赖或碎片规则混入本例手算。

七天窗口 11-24 至 11-30，只有 **11-24、11-25、11-27** 可投入；其余四天通过已确认 `unavailable_days` 要求禁用。缓冲 15%。另一个未选中任务在 **11-25 已有 20 分钟 planned 安排**。课程报告自身不预置未来安排，本例不触发 D12 额外工作确认。

初始每日预算 60 分钟；调整时通过 confirmRequirement 使用新 requirement_id 和更高 version 添加同强度预算决定（沿用现有“同强度取最高版本”规则），不原地篡改线程记录。固定建议可引用虚构图片和文字，图片/文字与 fixture 对应关系明确；这里不声称运行了截图识别。

### 4.2 先锁定手算，再比较真实输出

| 情况 | 11-24 可用/安排 | 11-25 可用/安排 | 11-27 可用/安排 | 总已排 | 未排 |
| --- | --- | --- | --- | --- | --- |
| 每日 60，缓冲 15% | 51 / 51 | 31 / 31（扣已有 20） | 51 / 51 | 133 | 67 |
| 每日 90，缓冲 15% | 76 / 76 | 56 / 56（扣已有 20） | 76 / 68 | 200 | 0 |

第一轮可用量：`floor(60×0.85)=51`，总计 `51+(51−20)+51=133`。第二轮为 `floor(90×0.85)=76`，总容量 208，安排完剩余 8 分钟。禁用日零新增，正式总截止始终为 11-27。

这是主案例的验收预期，不是已经执行过的新成绩。若实际结果不同，先查种子/规则/实现；不能直接用算法实际输出反向改写预期。

### 4.3 主链路必须完成的动作

1. 经真实服务创建线程、消息、草案，确认预算与禁用日；以快照证明尚无助手采用副作用。
2. 调用真实 reschedule，独立校验结果并比较 133/67；未确认缺口时不能 ready。
3. 单独保留一个分支：确认当前版本的已知缺口后允许 ready，但 complete 仍为 false、未排仍为 67。主线继续调整预算，不把该分支当完整排程。
4. 将预算提高到 90：旧计算失效，原内容可读；重算得到 200/0，必要的确认绑定当前版后才就绪。验证历史可读、旧版确认不自动有效。
5. 推进操作时刻但不改变事实与输入，再次重算：revision/history 不增加，有效确认不丢。
6. 硬刷新（不是只换 hash 路由）后，从 IndexedDB 重新构造服务并读取同一草案；核对实际内容、revision、历史及可用性，不依赖刷新前内存。
7. 通过现有 DataPage 实际下载 ZIP，再实际上传检查与预览、恢复到新空间。读 DB 验证结果，不能只看成功提示。
8. 进入恢复空间：未应用草案 needs_review、fact_baseline 清空、旧确认无执行效力；正文、建议、历史、旧计算可读，新 ID 及引用正确。
9. 在恢复空间用映射后的业务对象与真实服务重算，重新确认当前版；继续修改一次合法内容并刷新验证保存。证明恢复结果可继续工作，而不只是能列出记录。

## 6. 数据与断言规则

### 6.1 哪些变化允许发生

- 主案例在种子完成后，草案流程只允许助手线程/草案变化。对 sources 内容哈希及 docs 中 Task/Action/PlanItem/FocusSession 作规范化前后对比；不能只比较数量。
- 恢复会在新空间复制业务对象，这是备份恢复允许的行为。核对复制后的业务内容与引用映射，不把这些对象误报为“正式采用”；不得额外把草案段生成新 PlanItem。
- 事实变化、删除、切空间等测试的预设业务变更单独记录；只允许这些明确注入变化，不以“测试修改过数据”为由关闭副作用断言。
- Source 产品语义仍为原文不可变、新资料新 ID；同 ID 替换仅用于并发防护故障注入，退出场景后丢弃隔离上下文。

### 6.2 不能拿 raw JSON 全等代替恢复验证

恢复后正式 ID、thread/draft ID、空间 ID 按协议变化；局部 key 与正文文本保持。按已批准类型化映射比较业务语义、历史版本与引用。

content_version 为本地可信内容字段，恢复时从真实字节重算，不进业务归档。Blob 比较字节 SHA-256，不比较对象地址。原空间与原 ZIP 必须保持不变。

### 6.3 状态与重试

持久 status、readiness.ready、planning_result.complete 分开断言。发现失效可以由已批准的读取结果/blocker 表达，不要求为展示强行修改持久状态；任何 ready 提交仍须经真实服务最后核对。

按现有状态机走合法边；验收脚本不能直接写 status=ready、补 fact_baseline 或伪造当前版确认来通过。主链路中只能播种初始业务与 fixture，后续内容从实际服务产生。迁移/历史 applied 的兼容场景可 raw seed，但明确标记为历史夹具，不计作真实采用成功。

重复重算不增版；真实改动增版后重新读取基线。测试应断言相对版本关系，不硬编码所有步骤必定落在某个 revision。确认/状态更新不一定增版，要求变更的等价失效机制也沿用 1B 已验收语义。
