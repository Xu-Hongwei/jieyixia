## 2. 必须整改

### R1 / P2：ExistingDeadline 未兼容正式 Task 已允许的时间格式

位置：提案 `models.py:64`、`models.py:573`；对照正式 `contract/models.py:316`。

`ExistingDeadline` 声称镜像 0.4.0 Deadline，却调用严格的 `DEADLINE_VALUE_RE`。正式 Task 的 `Deadline` 实际使用 `DATETIME_RE`，不是该严格表达式。

独立构造三个带合法确认时间的手动截止，正式 Deadline 均接受，提案 ExistingDeadline 均拒绝：

- `2026-11-26T09:00+08:00`
- `2026-11-26T09:00`
- `2026-11-26T09:00:00.123+08:00`

影响：将已有合法 Task 放入助手上下文时可能校验失败；无秒旧值不能仅凭“改样本为带秒”获得兼容。协议决策 §7.1 和交回文档 §5 对现有契约的解释也有误。

整改要求：

1. 既有事实快照接受正式 Deadline 的合法输入，或明确定义无损的边界适配；不得缩窄旧数据的可读集合。
2. 模型新候选如需规范输出，可另定规则，不与旧事实快照共用不兼容约束。
3. 增加上述三种兼容正向样本，以及非法日期/偏移的负向样本；无时区按北京时间处理，保留有效精度。
4. 修正文档中“0.4.0 Deadline 必须带秒”的说法。

### R2 / P2：TypeScript 生成器丢失判别联合类型

位置：提案 `generate.py:69` 起；生成物 `typedefs.d.ts:170`、`:335` 等。

生成器处理 `anyOf`，未处理 Pydantic 判别联合使用的 `oneOf`，最终落到 `unknown`。实际生成结果包括：

- `AssistantModelProposal.task_proposals?: Array<unknown>`
- `AssistantModelProposal.action_proposals?: Array<unknown>`
- `AssistantProposeResponse.payload: unknown`
- 多处 `task_ref`、`action_ref`、`evidence_refs` 同样丢失类型。

影响：后续前端不能按 `kind`/`op` 正常收窄已定义的协议对象，只能额外断言或另写类型，破坏“唯一类型来源”。`--check` 只证明生成物与生成器一致，不能发现生成器本身丢失语义。

整改要求：支持 `oneOf` 递归生成联合，重新生成；增加覆盖 ResponsePayload、TaskProposal、ActionProposal、EvidenceRef、DraftRef/ExistingRef 的类型检查用例。允许本来就有意开放的 `Any` 字段保留 `unknown`，不应机械消除所有 `unknown`。

### R3 / P2：直接引用已完成 Action 绕过禁止重新排程的规则

位置：提案 `selftest.py:154` 起的 work item 既有 Action 分支；对照 `:136` 的 reuse 分支。

相同上下文中，`a-1.done=true`：

- 使用 `ActionProposalReuse(target_id=a-1)`：正确拒绝。
- 不提交 reuse 对象，直接使用 `work_items[].action_ref={kind:'existing', id:'a-1'}`，并填写 `remaining_minutes=40`：结构和语义校验均接受。

影响：同一规则取决于模型选择哪一种引用路径，已完成步骤可作为待排工作进入规划输入。此问题属于已实现的提案校验遗漏，不要求本批提前实现真实排程器。

整改要求：所有可排工作引用在解析为真实 Action 后统一检查完成状态；已完成 Action 只允许作为已满足前置的事实。加入 direct/reuse 两条路径的对照负例及未完成 Action 的正例。

### R4 / P2：更新已有任务的截止候选跳过证据与来源校验

位置：提案 `selftest.py:117` 起，截止候选遍历只处理 `TaskProposalCreate`。

独立复现两种输入：

1. `changes.deadline_candidates[].evidence_refs` 指向未选中的 Source。
2. 截止候选声明 `origin=user`，只有截图摘录，没有用户消息证据。

同一候选放入 create 均正确拒绝；放入 update 均接受。结构校验仅确保“有证据对象”，无法证明出处和来源有效。

影响：已有任务的截止更新建议可以携带新建任务不允许的无效出处，后续逐字段确认将基于不一致的可信规则。

整改要求：create/update 统一遍历截止候选并验证证据引用、用户来源规则；保留逐字段确认边界。补两类 update 负例、合法 update 正例，并检查其他嵌套证据路径是否存在同类遗漏。

### R5 / P2：文档将单 profile 的尝试次数误当成整个 analyze 上限

位置：`2026-11-24-阶段5B-0交回.md:116–119`、协议决策 `:163`；对照正式 `backend/app/model/registry.py:151–153`。

文档称 analyze 每次最多 2 次厂家尝试，并推导完整流程最多 `3×2+2=8` 次。实际 ModelRouter 外层遍历所有可用 profile，内层分别按各自 retries 尝试。`retries=1` 是单 profile 上限，未限制整个 analyze 为 2 次。

独立探针用两个无网络假适配器调用真实 ModelRouter，均配置 retries=1，实际顺序为 `a,a,b,b`，一次调用共 4 次。整个流程的“最多 8 次”不是现有实现保证。

整改要求：

1. 改为：propose 未来整体最多 2 次；analyze 沿用现有 profile/fallback、时间预算和共享每日额度限制。
2. 如展示 `3×2+2=8`，只能标明“每次 analyze 仅有一个 retries=1 profile”的特定算例，不得称普适最坏上限。
3. 增加多 profile 预算设计样本；次数按实际尝试求和。无其他终止时，一次 analyze 的配置尝试上界为各 profile 的 `(1+retries)` 之和，实际还受时间/额度/成功提前结束影响。
4. 本批修正文档和设计样本即可，不为符合旧文案而擅自修改正式后端重试策略。
