# 统一智能体与智能规划：产品与工程方案

日期：2026-11-23。状态：待实施设计，不代表接口、智能体或自动排程已经实现。

依据：用户要求将截图/文字理解、补充需求、任务整理、自动排表和已有执行功能统一为一个助手；核心输出是“每天具体做什么、做多久”，不只是显示截止日期。

本方案承接[5A-2B最终验收](./2026-11-23-阶段5A-2B最终人工验收.md)与[5A-2C开工单](./2026-11-23-阶段5A-2C综合验收开工单.md)。2C先完成并验收。之后按本方案进入新版5B；它替代旧5B“仅前端确定性规划、不新增后端接口”的范围约束。旧5B的容量、缺口、用户确认和保护历史等原则保留。

本次只定产品和实施方案，未修改业务代码、契约、数据库或部署。下一实施批次应先为5B-0协议与规则冻结，完成后交回验证，不能依据总方案连续做完全部批次。

## 1 产品定位

产品中的统一助手暂称“工作助手”。用户通过同一个入口完成：

**给资料与要求 → 理解目标 → 核对关键事实 → 拆解行动 → 分配每日工作 → 采用计划 → 执行并记录 → 根据进展调整剩余计划。**

助手不是另一份任务数据库。资料、Task、Action、PlanItem和FocusSession继续是正式业务对象；对话用于表达意图，草案用于预览变化，正式页面用于执行和查看真实结果。

“自动”的边界：助手可自动阅读已选资料、整理需求、生成步骤和排程草案，也可按反馈重新生成；一次明确“采用”后成批创建用户看到的对象。它不需要用户逐条手建任务，但不能在用户尚未看到结果时改动正式日程、截止或成果。

## 2 一个可验收的完整示例

用户上传一张“周五提交课程报告”的截图，并输入：

> 材料还没整理。每天最多一小时，周三没空，先做报告，提交前留一次检查。另有一个无截止的阅读目标，有空再排。

助手先展示来源与理解：报告交付要求、截止候选、每天容量、不可用日、检查偏好、阅读为低优先级。日期模糊或截图无法辨认时集中询问；不替用户虚构截止。

之后生成一份示意草案：

| 可用日 | 安排 | 预计时间 | 完成这一段应得到什么 |
| --- | --- | --- | --- |
| 第1日 | 整理报告材料并确定提纲 | 50分钟 | 提纲与缺失材料清单 |
| 第2日 | 完成报告主体初稿 | 50分钟 | 可继续修改的初稿 |
| 第3个可用日 | 补充论据、图表和引用 | 50分钟 | 内容完整版本 |
| 提交前可用日 | 检查并准备提交 | 50分钟 | 可提交文件 |

这是解释用示例，不预先保证某一真实周一定容得下。假设每天60分钟、默认15%缓冲，每天可分配51分钟；如果截止前只有三天可用，以上200分钟工作就不能完整放入153分钟容量。系统必须展示缺口或未找到完整分配，不能偷排周三、删掉检查或延长截止。

用户再说“第一步已经做完，第二天只能半小时”，助手生成新版本，只比较受影响工作与余量。已完成记录保留；剩余工作量根据用户反馈更新，不直接按历史专注分钟相减。

点击“采用这份计划”后，正式日程上方出现每日工作，下方仍是总截止。点击某项安排沿用当前Action选择与开始确认进入工作页。

## 3 能力范围与操作权限

| 能力 | 首版目标 | 正式写入规则 |
| --- | --- | --- |
| 截图/文字理解 | 复用现有分析，支持多份资料和补充说明 | 原始资料先明确保存；解析结果仍为候选，不由模型标confirmed |
| 查询现有工作 | 读取当前空间用户选择的任务及规划周期内占用 | 只读，不把其它空间资料自动带入上下文 |
| 新建任务、拆解行动 | 提出任务/行动草案、估时及来源 | 采用时成批写入，临时ID由本地映射成正式ID |
| 修改任务事实 | 首版允许草案中提出明确字段变更 | 总截止等重要事实单独突出前后差异；需要用户明确确认相应变化，不能被“重新排表”隐含授权 |
| 每日排程 | 未来7天，容量/不可用日/先后关系/已有安排 | 草案检查后一次采用，不能覆盖受保护记录 |
| 修改规划要求 | 对话输入或直接编辑约束卡 | 产生新草案版本，旧版本停止采用，不自动改正式日程 |
| 查看今日建议 | 基于现有有效安排、截止、未结束工作排序并解释 | 不自动创建记录或启动计时 |
| 开始/返回工作 | 助手给明确目标卡，转已有执行入口 | 复用begin/确认/互斥；“回到工作”不自动继续 |
| 根据进展改排 | 新版5B后续批次，在同一助手入口内增加 | 用户确认剩余工作量及改动清单后应用，不改历史成果 |
| 删除、结束、备份恢复 | 首版提供当前对象的原功能入口 | 继续使用原确认页，不让模型直接批量删除、结束计时或恢复数据 |

首版不做小时级日历、外部日历同步、周期任务、后台自主执行、网页浏览代理、任意代码工具、跨设备对话同步。用户说“晚上八点至九点”时保留为偏好并解释当前按天排，不能声称已保证小时冲突检查；严格小时约束需用户明确改为日容量后才能按天处理。

无截止目标可以参与本次7天规划，排在有截止、同等条件更紧急的工作之后；规划周期末只是安排窗口，绝不是自动补出的Task截止。此规则明确替代旧5B“所有无截止项不自动排”的限制。

## 4 页面设计：一个入口，三个主要视图

保留日程、资料库、待核对三个主导航。增加全局“工作助手”入口，进入次级路由`/assistant`，不把所有页面塞进聊天窗口。

桌面采用“对话区 + 当前草案区”；手机切换“对话 / 计划”，对话输入和待确认状态清晰可达，不依赖悬浮小窗完成复杂确认。

### 4.1 输入与上下文

顶部显示当前工作区、本次选中的资料/任务、规划起止日期。附件区支持截图和文本，单次建议最多3张截图；已有资料直接引用，不重复创建Source。

输入下方提供可编辑约束卡：

- 规划起始日，默认操作时北京时间今天；首版固定7天。
- 每日可投入分钟及不可用日期；容量未设置时集中问一次，不静默假设每天有空。
- 缓冲比例，默认15%，可见且可调整。
- 重要任务、最早开始日、不可拆分项和最小工作段。
- 已有安排按日占用与不可修改说明。

“日程已知事项”不等于整个现实日历。页面要说明容量由用户提供，未录入的会议、课程等不会被系统自动知道。

### 4.2 助手消息类型

不用一段大文本同时承担事实、计划与执行结果。呈现为有限类型卡片：

| 类型 | 内容/操作 |
| --- | --- |
| 理解结果 | 资料出处、已知事实、未确定问题、用户补充要求 |
| 集中澄清 | 每轮优先1–3个关键问题；可以回答或明确接受某个假设 |
| 任务与行动草案 | 新建/关联已有Task、行动步骤、估时依据、先后关系 |
| 每日安排草案 | 每天安排、预计分钟、产出、容量、缓冲、未排事项 |
| 改动摘要 | 新增、调整、移除未执行安排、保持不变的锁定项 |
| 冲突与缺口 | 哪条约束冲突、哪些工作未安排、可以由用户选择的调整 |
| 采用结果 | 真实写入数量及“打开日程/打开任务”，不以生成成功代替保存成功 |

### 4.3 采用与调整

主按钮“采用这份计划”，有未确认关键事实或硬约束违规时不可用。估时属于建议时，卡片明确标注；用户可以在一次采用确认中一起接受这些建议，不要求每个分钟数单独弹窗。

“暂不采用”“继续调整”“手动编辑”不会修改正式记录。直接编辑日期/时长/说明后重新校验，不保留已经失效的“可行”标记。

首版只整体采用当前版本；要去掉某项工作，先从草案选择范围移除并重新检查，不实现难以追踪的半份草案分次采用。

## 5 资料、事实、要求与推测

每条重要输入必须能分辨：

| 来源 | 示例 | 处理 |
| --- | --- | --- |
| 资料事实候选 | 截图写“周五提交” | 保留Source、原文引用及解析依据，日期歧义先核对 |
| 已确认业务事实 | 现有Task总截止 | 正式事实优先，模型不能因另一句含糊文字自动覆盖 |
| 用户明确要求 | 周三不排、先做报告 | 标为用户要求；硬/软分类可见，有冲突时让用户决定 |
| 助手建议 | 阅读需要90分钟、先整理资料 | 标为估计或建议，不伪造截图出处 |

截图、原文、OCR和历史成果属于待分析内容，不是智能体执行指令。截图中出现“忽略前面规则”“删除所有任务”等文字不能改变用户权限或触发工具操作。

同名任务只作为“可能相关”候选。自动匹配必须有可靠的现有对象ID及上下文；关系不确定时让用户选“补充已有任务/新建任务”，不能悄悄合并。

一张图有多个真实交付截止时，保留为多个候选交付目标，用户可选择创建多个Task；不能把它们都写进一个Task.deadline，也不能用工作安排日冒充交付节点。

原有待核对页继续有效。助手内确认采用既有字段确认语义：模型字段确认后仍保留origin=model、derived及出处；用户改值才反映为用户修改。确认失败不允许部分Task已经创建、对应来源却仍宣称未确认。

## 6 排程规则：模型提议，程序计算与验证

### 6.1 模型与确定性程序分工

模型输出目标、行动建议、估时、拆分建议、依赖及需求解释。确定性排程器据此计算日期和容量；可以接收模型的软偏好，但不能把模型生成的“周表看起来合理”当可行性证明。

服务端校验模型结构、ID与约束类型；前端对选定空间最新事实再次校验并排程。采用事务最终核对输入事实和被修改对象。服务端没有用户本地数据库的权威写入能力。

### 6.2 容量口径

每日可规划容量：`max(0, floor(用户当日可投入分钟 × (1 − 缓冲比例)) − 已承诺占用分钟)`。

已承诺占用按唯一PlanItem ID计一次，包含目标日已存在且未列入本次合法替换集的有效安排。过去已完成工作的分钟不抵扣未来容量。今天已完成/正在进行的已承诺安排首版仍保守占用原预计额度，不因状态变化自动腾空容量；用户觉得今天还有余量时，明确调整今天预算。

任务截止不是占用时长。跨日、未结束工作不自动换日期；存在未结束工作时建议先处理，再安排下一段。本次剩余估时是用户当前估计，不再次减去历史Focus分钟。

已有未来安排与“剩余工作”要避免重复：展示该任务已有几段、多少预计分钟；用户选“保留已有安排，只规划新增剩余工作”或“替换指定未执行安排后重新规划”。模型不能默认在旧安排旁再加同一批工作。

### 6.3 硬约束与软偏好

- 硬约束：不可用日期、每日容量、最早开始日、用户确认的截止、不可拆分、已锁定/有执行历史/未结束会话关联项。
- 软偏好：优先某任务、尽量连续、减少每天任务切换、偏好某一天；满足不了时解释，不偷偷改硬约束。
- 同优先级使用稳定顺序：有截止且更早截止优先，再按用户优先级和稳定ID排序；依赖项必须先满足。无截止工作利用剩余容量。
- 依赖图出现环或引用未知步骤时先拒绝/澄清。前序在更早日期完成，或同日有足够容量且提供明确顺序；按天算法不保证精确小时可行。
- 可拆工作默认建议最小段25分钟，作为可编辑建议；允许最后不足25分钟的剩余段并显示，禁止生成0分钟条目。不可拆的步骤必须整段放入有足够容量的一天。
- 日期精度截止可以安排当天；有精确时刻但缺少小时可用窗口时，保守排到前一天。若因此排不下，显示“需核对截止当天时间”，不能声称一定可在上午截止前完成。
- 过期截止不能被新计划“满足”；显示逾期补做选项，用户明确选择后才做恢复计划，总截止事实不自动延后。

### 6.4 可行性和缺口

输出必须区分：已安排工作、已知时长但未安排工作、估时未知项、硬约束冲突、依赖阻塞、规划窗口外的剩余工作。

例如“已知工作240分钟，当前可安排180分钟；60分钟未安排，另有2项尚未估时”。不能把未知时长算成0，或宣称gap=60就是全部真实缺口。

启发式算法没找到方案，不等于数学上证明无解。文案使用“当前规则未找到完整安排”，提供容量不足等确证原因；不将算法局限包装成绝对不可行。相同规范化输入的排程器结果应稳定；模型再次拆解可能改变输入，要作为新版本显示。

## 7 一套协调流程，多种明确工具

首版不引入多智能体互聊或无限循环代理，使用有状态协调器：

`接收 → 读取选定上下文 → 需要澄清/生成结构化草案 → 本地排程校验 → 待用户采用 → 正在应用 → 已采用/冲突待核对/结果待核实`。

可调用能力按作用划分：

| 能力 | 运行位置 | 权限 |
| --- | --- | --- |
| read_selected_context | 前端本地 | 只读用户选定对象及必要占用，限制当前空间 |
| analyze_source | 现有后端分析能力 | 读取明确选择的截图/文字，返回候选 |
| propose_work | 新后端规划能力 | 产出结构化建议，不执行数据库命令 |
| schedule_and_validate | 前端纯规则 | 计算日期、冲突、缺口，无正式写入 |
| prepare_application | 前端 | 冻结确认版本、影响范围、ID映射及写入方案 |
| apply_application | 本地事务服务 | 只接受用户确认的当前版本，整批应用 |
| open_task/open_plan/start_work_entry | 前端导航/现有执行入口 | 明确ID，保留草稿保护与既有开始确认 |

模型只能返回白名单的建议类型和引用，不接受任意HTTP地址、任意方法名、SQL、文件路径或代码作为可执行工具。日后扩展工具也要按同一规则接入。

用户说“开始吧”，只有明确唯一目标才进入对应开始确认；有多个候选时让用户选。用户说“做完了”时，引导当前工作结束表单，不能根据聊天文字悄悄结束另一个会话或完成整个Task。

## 8 前后端协议建议

### 8.1 实际需要新增的能力

当前后端实际主入口是`POST /api/analyze`，模型适配器主要处理一份图文分析；前端现有API入口只有healthz/analyze。不能因为契约里有PlanDraft类，就认为完整智能规划接口和持久草案已经存在。

首版复用现有analyze解析每份新截图，已有确认资料不重复解析。截图数量设限，解析结果在本地汇总；规划接口接收选定资料的结构化候选/已确认事实及必要原文片段，不重复传所有图片和整个工作区。

新增建议端点：`POST /api/assistant/propose`。先采用普通请求响应，状态栏说明“正在理解/生成草案”；首版不需要SSE或流式工具执行。

### 8.2 请求最小字段

| 字段 | 用途 |
| --- | --- |
| protocol_version | 独立的智能体协议版本，拒绝不兼容输入 |
| request_id / thread_id / turn_id / client_seq | 请求定位、对话归属及旧响应丢弃；不是数据库写入授权 |
| intent | new_plan / revise_plan / explain_today等白名单 |
| user_message | 本次明确要求 |
| selected_sources | ID、版本/摘要、引用片段、解析候选及确认状态 |
| selected_tasks/actions | 只读当前空间对象摘要，明确ID和已完成状态 |
| planning_context | 北京日期、7天窗口、逐日容量、已承诺占用及受保护安排 |
| requirements | 用户已确认约束和待确认项 |
| previous_draft | 修订时提供旧版本结构化信息，避免只靠长聊天猜状态 |

浏览器的workspace_id只用于本地关联，不能当服务端认证凭据。首版维持本地数据架构，服务端不根据该ID查询别人数据；若未来有云存储，另做用户身份与权限。

### 8.3 响应与错误

响应是`clarification`、`proposal`或`explanation`之一，包含请求关联信息、简短说明、结构化问题/建议、证据引用、假设与警告；模型不能返回confirmed=true或已保存数量。

proposal包含临时任务/行动ID、已有对象引用、估时、最早日、可拆分、依赖、用户要求解释。具体排程和采用结果由本地规则产生。

错误至少区分输入过大、结构不合法、上游不可用、超时、额度不足、不兼容协议、取消/过期响应。原始资料与已保存草案保留；失败不显示伪造计划，不反复自动重试。

同request_id不等于服务端已具备持久计费去重。首版后端无持久任务库，模型重试可能再次调用厂家；采用幂等由本地application_id保证，不把两者混淆。

### 8.4 成本和输入边界

建议首版每次规划：至多20个选定任务、100个建议步骤、7天窗口；图片分析批次最多3张，沿用图片体积上限；超限明确缩小范围，不静默裁剪重要约束。

规划请求设置整体超时、输出长度与厂家尝试上限；建议总体预算120秒、最多2次厂家尝试（包括修复非法输出/重试/切换profile），不是每层各重试2次。每次实际厂家尝试计入现有额度。限制最终在5B-0结合现有配置形成唯一常量来源。

当前guard只匹配POST /api/analyze，新端点必须在开放时一起接入鉴权、请求体限制、限流、并发、模型额度和错误契约。不能新开一条未受保护的付费调用路径。密钥继续只在后端/既定网关，绝不放VITE变量；可信代理部署问题仍由阶段6处理，不顺带改为无条件信任X-Forwarded-For。

用户取消或切空间后不应用晚到响应；已经发出的上游调用不保证能取消费用，页面不作此承诺。

## 9 数据模型、持久化与版本策略

### 9.1 保留现有业务主体

Task仍是总目标/单个总截止；Action仍是实际步骤；PlanItem仍是某天安排；FocusSession仍保存真实执行。PlanItem.action_text不是Action身份，不能开始按同名自动关联。

草案里的每个工作段可引用建议Action ID，供用户预览和采用时映射。采用后首版仍沿用2B明确选择实际Action；不能因为草案有suggested_action_ref，就偷偷往正式PlanItem添加action_id。若后续要固定绑定，必须另做契约与历史兼容设计。

### 9.2 建议新增本地对象

| 对象 | 核心内容 |
| --- | --- |
| AssistantThread | workspace、标题、显式关联对象、消息与结构化交互状态、用户确认的需求摘要；不保存模型隐藏推理 |
| AssistantDraft | ID/revision、来源和事实快照、约束、建议任务/行动、排程结果、缺口与未知项、影响范围、状态 |
| ApplicationReceipt | application_id、draft_id/revision、完整输入指纹、实际ID映射、结果摘要、时间；用于核实及防重复应用 |

Draft状态：editing / generating / needs_clarification / ready / needs_review / applying / applied / discarded。生成中的临时文本不冒充已保存；刷新后generating恢复为已中断、可显式重试；applying先查回执，不能自动再写一批。

草案每次改要求递增revision。采用按钮绑定具体revision和摘要；新一轮生成开始后旧版本不可再采用，用户仍可查看其内容。应用后的草案只读，修改要创建新草案。

### 9.3 建议版本路线，先在5B-0冻结

推荐业务契约进入0.5.0，新增智能体协议/持久对象；保留0.4业务记录读取兼容。DB建议升v4，新增assistant_threads、assistant_drafts、assistant_ops，避免把未注册kind塞进现有docs后导致备份拒绝。迁移只创建新存储并标明版本，不重写历史任务和专注。

备份建议升级v2，显式纳入需要恢复的对话/草案及引用规则；新导入器继续读取v1。原0.4 PlanDraft过于简单，缺少草案修订、来源确认、临时ID、未知估时和变更集；不能直接往现有类私加字段或改变旧gap_total语义。

采用这个版本路线前，5B-0必须交回精确schema/typedef/fixture差异、迁移、导入/导出和旧测试影响，人工验证后再实际迁移。这里提供明确推荐，不是已经升版。

### 9.4 备份恢复与删除的新增边界

- 新版导出包含已保存对话及草案，原图仍通过Source资产机制；不导出密钥、owner/租约、在途请求或可重放的assistant_ops台账。
- 正式记录和新增草案的活引用全量重映射，历史引用采用明确历史标识，不能因为对象被删让整个对话不可读。
- 恢复后的未应用草案标needs_review，旧的基线/指纹不能直接当可采用授权；重新读当前空间事实、生成影响预览并确认。已应用草案保留历史状态，不自动重建业务对象。
- 删除资料/Task后，旧对话文字可保留，但相关草案需标失效/待核对，按钮不能写到缺失对象；新对话引用不随意扩张原有删除级联范围。
- 对话长度、单条大小和草案体积有明确上限；用户内容不因超过模型上下文被静默删除。只向模型提供有限原文和可查看的结构化需求摘要，不把摘要变成新事实。

## 10 采用事务：看到什么，就保存什么

采用不是依次调用几个store方法，而是一次可核实的批量应用。

1. 在用户确认前生成完整影响预览：来源候选确认、新建/更新的Task、Action、新增安排、待替换的未执行安排、保持不变的历史/锁定项。
2. 冻结workspace、draft ID/revision、相关事实快照、规划周期内占用、临时ID→正式ID映射、确认选择、完整写入方案及application_id。异步提交后不能继续读取可变的表单对象替换输入。
3. 本地事务内重读相关docs、草案版本和必要协调事实，检查对象归属、引用、已有会话/历史、删除或完成状态、容量及新增安排。采用期间另一页面新建了同日安排也必须被发现，不能只比被编辑的Task。
4. 快照变化则返回全部相关差异，草案进入needs_review；不自动调整为新方案再代用户采用。对同一目标进行第二次修改时仍需重新核对。
5. 同一事务写正式业务对象、必要来源确认、草案applied状态与ApplicationReceipt；任一步失败整体回滚。不先创建Task成功，再因PlanItem失败留下半份计划。
6. 结果未知先查原application_id；同输入重试只返回原映射。同ID改内容拒绝，新确认才签新意图。应用成功但页面读取失败，只重读结果，不再创建。

哈希、模型请求和耗时规划在事务外完成；IndexedDB事务内只做同步事实比较和数据库操作，不能在活事务中await网络或异步摘要计算导致事务提前结束。使用固定顺序的基线字段比较；输入指纹只是防意图变化，不能代替事务内重新校验。

替换集只允许规划窗口内、北京时间今天及以后，当前仍为planned、活引用、没有任何Focus引用且未被锁定的未执行安排；过去日期的记录不进入替换集。默认先全部视为锁定，只有用户明确选入替换集才允许改动。partial、done、cancelled、moved以及任何有未结束会话/历史投入的安排不做批量重写，继续使用既有“另安排一天/确认进度/取消”的显式流程。

首版不提供“一键撤销整次采用”这个新功能；若需要撤回已采用计划，走原对象操作与保护。幂等、事务回滚和用户事后撤销是三种不同能力，不混称已支持。

## 11 进展反馈与改排

第一批智能规划先打通新建闭环，之后在同一助手增加反馈改排，不另做第二个机器人。

例如“今天只完成一半”先定位具体Action/安排，读取其真实成果；有未结束会话时先回到工作处理。模型可以建议新的剩余估时，但用户必须能看到并修改。不得将“已专注30分钟”自动解释为“完成了30分钟工作量”。

重新规划默认保护所有正式安排，只对用户选定的未执行替换集形成差异。生成后列“保留哪些、移到哪天、新增哪些、仍有多少未安排”，一次确认后应用。

用户要求今天临时没空时，如果今天已有已执行/正在执行条目，保留事实并解释；只移动尚未执行且明确允许调整的条目，不把实际历史搬到明天。

## 12 降级和异常表现

| 情况 | 用户体验 |
| --- | --- |
| 模型不可用/断网 | 原资料、对话输入和已保存草案保留；可查看、手动编辑、执行已有任务，确定性排程可本地使用；不伪造智能回复 |
| 关键日期/容量未知 | 集中问少量问题；未知项保留待估计，不自动设0 |
| 超容量/依赖不成立 | 草案展示冲突、可选调整和未排项，不擅自减工作量 |
| 用户改了需求，旧响应晚到 | 仅当前thread/turn/revision/workspace匹配时接纳；旧回复不覆盖新草案 |
| 多页面同时采用 | 一个事务提交，其它按回执/冲突处理；不复制任务和安排 |
| 采用时空间切换 | 不跳走新页面，不清新输入，不把旧空间成功提示显示成当前空间结果 |
| 备份恢复后的旧草案 | 明确要求重新核对，不自动执行旧指令 |
| 资料中恶意指令 | 当作资料内容显示或忽略其指令性，不获得工具权限 |

## 13 分阶段实施与停止点

顺序调整为：**2C验收 → 新版5B分批实施 → 4-3完整演示 → 阶段6部署验证。** 4-3纳入最终智能体闭环，避免先制作一套马上过时的演示；正式发布仍单独执行。

| 批次 | 交付 | 暂停验收点 |
| --- | --- | --- |
| 5B-0 协议与产品规则 | 工具权限表、请求响应schema、草案/采用模型、容量口径、版本迁移及备份方案、fixture；明确旧5B变化 | 评审输入/输出与反例，不接真实模型、不迁移用户库 |
| 5B-1 本地草案与规则排程 | 结构化输入→7天草案→编辑/冲突解释，草案保存及版本；使用fixture模型结果；同时实施已批准的新存储迁移及草案的备份、恢复、删除兼容 | 容量/依赖/缺口/无截止/未知估时/午夜测试与草案恢复通过；旧资料仍能完整导出，不留下新增存储未被备份覆盖的窗口 |
| 5B-2 原子采用与数据兼容 | 批量确认、ID映射、原子写入、重试/并发；补齐采用后业务对象、回执与跨对象引用的备份恢复/删除验证 | 假模型也能从草案安全变成真实任务与日程；零半份写入，完整恢复后不重放采用 |
| 5B-3 后端智能建议 | propose接口、现有analyze串接、模型结构校验、预算与guard覆盖；fixture和真实模式分离 | 语义质量样本+拒绝越权/恶意资料/非法输出；有限真实模型验证 |
| 5B-4 统一助手页面 | 对话/约束卡/草案预览/采用结果；图文输入到执行的真实闭环、手机、离线降级 | 用户不用逐条手建即可完成主要路径；逐项证据，暂停交回 |
| 5B-5 反馈与改排 | 结合成果更新剩余估时、明确替换集、保护历史、差异采用 | 多轮修订不重复、不误改，形成完整智能工作助手 |

每批完成暂停，未验收不得自动进入下一批。首个可展示的智能规划版本在5B-4，5B-5可独立交付；两者都使用同一助手，不为了赶进度把未实现的反馈改排宣传为已完成。

推荐代码落点（名称在5B-0按仓库规范冻结）：

- 后端新增assistant路由/建议编排/输出schema与专用提示；复用模型适配层及额度，不将规划逻辑硬塞进旧analyze归一化代码。
- 前端新增domains/planning纯规则、services/assistant命令编排、独立草案/对话store、AssistantPage和结构化卡片。
- 既有Task/Plan/Focus业务规则通过共享纯写集与原子存储层复用，不能从模型回调直接putDoc。
- contract、storage迁移、backup适配/重映射与测试按新版本一起更新，先保证旧资料可读取和导出。

不要求引入新的智能体框架。先复用现有FastAPI、模型adapter、Vue/Pinia及IndexedDB，把状态和权限收口；是否需要新依赖只在出现明确能力缺口后评估。
