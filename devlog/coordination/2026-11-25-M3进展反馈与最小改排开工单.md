# M3：进展反馈与最小改排开工单

状态：设计完成，待 Qoder 实施。基线：2026-11-25《M2最终人工验收》。本单是《智能助手快速初版实施方案》§5 的具体执行方案，继续快速初版路线，一次交付可运行闭环，不回到原 5B-5 的长周期扩展规划。

## 1. 本轮交付什么

让用户对一个已有任务说清楚“做到了哪里、哪些工作还需要安排、哪几天没空”，选择允许替换的旧安排，得到新的七日日程预览，确认后一次保存。

示例：“资料已经读完，报告还需安排 90 分钟；周四没空，把我选中的两条未执行安排移开。”

保存结果：沿用原任务和可复用行动；所选旧安排标为 cancelled，新安排写入日程；已完成记录、已有投入、未选安排、任务总截止保持不变。模型只给建议，不能决定取消哪些旧安排。

### 本轮产品决策已定

| 项目 | 首版决定 |
| --- | --- |
| 入口 | 任务详情“调整后续安排”；助手页“新建计划 / 调整已有任务”两个模式，复用同一助手页面 |
| 范围 | 一次一个未完成且未删除的任务；北京时间，起始日默认今天，连续七天 |
| 旧安排选择 | 默认全不选；必须用户逐条勾选；只替换窗口内今天及以后的合格安排 |
| 剩余量 | 用户确认“本次需要重新安排的工作及分钟数”，不是自动推算整项任务总剩余量 |
| 完成状态 | 展示已有行动状态；需要更正时使用既有完成/恢复操作，改排本身不写完成状态 |
| 总截止 | 只读展示并参与排程，不由改排修改；要改截止先走任务原有编辑，再重新生成 |
| 改排提交 | 先预览，再明确“确认替换”；旧取消与新建在同一事务完成 |
| 无合格旧安排 | 提示“没有可替换安排”；可转入已有新增计划流程，不伪装成改排 |
| 模型不可用 | 已有有效工作清单仍可用本地规则调整；没有有效清单时保留输入，允许手动填清单 |

不扩展：多任务全局重排、小时级时间槽、拖拽大改、后台自动改排、整批撤销、改历史投入、自动完成行动、外部日历接入。

## 2. 必须尊重的现有实现

这些是本次读代码核对的事实，不是新需求：

- `PlanItem` 只引用 task_id，没有 action_id；action_text 是显示文字。不能按标题匹配认定某条旧安排属于某行动。
- `FocusSession.plan_item_id` 才能反查安排的全部执行历史；PlanItem.focus_session_id 只是最近结束会话的快捷引用。不能只检查这个快捷字段。
- `PlanningInput.replacement_ids` 当前必须为空；`checkAdoptionSupported` 也拒绝替换。M3 必须增加明确模式和校验分支。
- `transformAdoptionAtomic` 现有业务写入只有 docAdds/add()，不支持取消旧安排。需要增加受限取消写集，不能改成任意 docPuts。
- 当前 `FactBaseline.occupancy` 是占用摘要，不等于完整旧安排内容，也不能证明没有新增专注会话。
- 当前既有任务已有安排时要求确认 `extra_work_acknowledged`，避免同一工作重复排程。M3 必须明确区分“取消后重排”与“保留安排之外的新工作”。
- 后端 `check_supported_intent` 当前只接收 new_plan；单改请求枚举不会使改排可用，需要同步请求、提示词、语义检查及 fixture。

继续使用 Vue/Pinia、FastAPI、现有模型适配器、日级规则排程、IndexedDB、草案与采用服务、ZIP 备份。没有引入新智能体框架的必要。

## 3. 用户流程与页面

### A. 选择调整范围

任务详情进入后已选中任务；助手入口进入时先选一个任务。顶部固定展示任务名、总截止和“本轮不修改截止”。已完成或已删除任务拒绝进入生成。

七日列表每条显示日期、行动描述、计划分钟数和状态：

- 可替换：复选框，默认未选。
- 受保护：只读，并解释“已有投入 / 有专注记录 / 已完成 / 已取消 / 不在本轮范围”等原因。
- 目标任务的窗口外未来安排另作简要提示，不纳入本轮替换。

展示“本次将替换 2 条、保留 3 条”。选择集改变后，旧预览与采用确认立即失效，不能继续保存旧信封。

### B. 填写进展和工作量

展示行动完成情况和已有投入供参考；提供一句进展说明，例如“资料读完了，报告还要写结论”。完成状态只读，旁边提供原任务页入口；自然语言“完成了”不能直接回写 done。

待安排清单每行：工作内容、复用行动或新增行动、本次待安排分钟数、可拆分、最小段长。复用行动只能选本任务未完成行动；完成行动不进入新工作。优先复用，模型提出新行动时清楚标为“将新增”。

允许“请助手整理剩余工作”，也允许手动填清单。模型估时仍是建议；采用前必须确认。未知分钟数用 null 并提示补充，不能默认 0，也不能以旧 Action.minutes 减累计专注时间得到剩余工作量。

**本次待安排量的定义：已经包含所选旧安排对应的未完工作，但不包含用户决定由保留安排继续覆盖的工作。**

因为旧安排没有可靠行动绑定，程序不能自动从工作清单扣减保留安排的分钟数。存在同任务保留安排时，必须显示这些安排并确认“上述保留安排覆盖的工作，不包含在这次清单里”。用户说“整份报告共剩 90 分钟”但仍保留相关安排时，先澄清范围；不直接当成额外 90 分钟。

这项范围确认随清单、选择集、预算或事实变化失效。可复用现有确认机制，但不能把“勾选取消”当成完成了“工作量不重叠”确认。

### C. 生成与预览

复用每日预算与不可用日表单；默认起始日取设备的北京时间今天，用户可改为未来日期。预算未填沿用现有澄清，不假设无限容量。不可用日可保留既有安排，但新建议不能排入；明确提示旧占用仍在。

预览按三块展示：

| 保留 | 将取消 | 将新增 |
| --- | --- | --- |
| 未选及受保护安排、已有执行记录 | 仅本次明确选定且复核合格的旧安排 | 按天显示新安排、分钟数与对应工作内容 |

同时展示“待安排总量 / 已排入 / 未排入”，总截止和超期/容量提示。未排入不能消失；继续采用须明确确认缺口。新安排为零时不提供改排采用按钮，提示修改输入或使用既有单项取消操作，避免把本功能变成整批清空。

按钮文案：“确认替换 2 条旧安排，新增 3 条安排”。打开预览和关闭预览均不修改正式日程。采用成功显示回执，并链接现有日程与任务页；已采用草案只读，再调整时新建草案。

## 4. 替换资格和并发规则

同一条资格函数用于列表、准备预览与提交复查。只有全部满足才允许替换：

1. 同一工作区，属于本轮唯一目标任务，任务存在且未完成。
2. date 位于本轮七日窗口内，且不早于提交时北京时间今天。
3. state=planned，task_ref_state=active。
4. actual_minutes 必须为 null；0 也不自动当成“从未执行”。focus_session_id 必须为 null。
5. 全部 FocusSession 中没有任何记录引用该 plan_item_id，包括运行中、暂停或已经结束的记录。

同任务的其他安排、其他任务的安排不能被模型或前端偷偷加入替换集。所选条目发生日期、时长、文本、顺序、状态等变化，或新增引用会话，整次采用拒绝并要求重新核对；不能跳过变化的一条后继续提交其余部分。

检查须发生在最终读写事务内，不能仅依赖调用前的快照或按钮禁用。跨午夜、切空间、任务删除/完成、并发开启专注、预算/输入变化均按既有失效机制处理。

## 5. 排程计算口径

设 R 为本轮已验证可替换 ID 集合，O 为当前空间窗口内所有应计占用的安排，继续沿用既有计占用状态规则。

模拟占用 = O 中排除 R 的安排。可用量沿用既有“预算、缓冲、占用”公式，不能另写一套。

- 只有已经验证属于 R 的条目释放模拟容量，一条只减一次。
- 未选、受保护和其他任务的占用照常计算；不能仅传目标任务的占用给排程器。
- 原始事实基线保留完整 O 与旧记录；模拟输入单独得到有效占用，不修改数据库、不覆盖原基线。
- replacement_ids 在排程器中不得再次扣减已经排除的容量。明确由 normalize 的改排分支产生有效占用，schedule 只消费该结果。
- 工作清单中本次剩余量是权威输入：模型不能用自己的估计覆盖用户已确认值。若模型拆成多项，要求用户核对拆分后各项及总量，再生成可采用预览。
- 任务截止、依赖、不可拆分、未知估时、缺口、超载和缓冲规则复用现有逻辑。逾期任务不自动延长截止，沿用现有显式处理规则。

例：某日预算 120、缓冲 15%，有效容量 102；原占用包含选中旧安排 60 和保留安排 30。模拟占用为 30，可新增 72，不是 12，也不是 132。用户确认本次待安排 90 后，剩余 18 必须排到其他合格日期或明确列为缺口。

## 6. 数据与契约增量

以下为建议字段职责，Qoder 可沿用仓库命名方式；语义、权限边界和验收不能省略。先写一份短契约差异表，然后实现，不另开一轮全面架构设计。

### 6.1 模式与记录

- 草案与执行信封增加明确 mode：旧数据缺省 create，M3 为 replan。create 分支永久拒绝非空替换集、取消写集及改排范围。
- 新 `ReplanScope` 保存目标 task_id、七日起始日、用户选择的 replacement_ids；至少 1 个，最多 100 个，去重拒绝而不是静默扩大范围。
- 新 `ProgressInput` 保存用户本轮说明、明确填入/确认的工作清单、范围确认；由前端实际提交形成，与模型建议分开。不能从模型文字解析成用户事实。
- 新 `ReplacementBaseline` 保存每个所选 PlanItem 的完整语义快照，并保存无 FocusSession 引用的检查前提；prepare/apply 都基于活快照复核，历史字段没有 updated_at 时不能只比较时间戳。
- 新准备取消项保存 plan_item_id、预期旧快照和仅允许的状态变更 planned→cancelled。禁止任意字段覆盖。
- 回执和 applied_summary 增加被取消安排 ID、取消数量及目标任务引用；它们用于追踪和展示，不构成恢复后执行授权。

原方案、旧草案和旧安排之间的追踪关系保存在新草案/结果摘要中，不必给所有 PlanItem 添加行动绑定，也不为首版建立全局“剩余工作量账户”。

### 6.2 模型接口

继续使用 `/api/assistant/propose`，增加明确 `replan_task` intent 与受限 replan_context；后端支持检查不能继续只接受 new_plan。

请求中提供本任务、相关行动状态、用户的进展与待安排清单、待替换摘要、保留摘要、有效每日容量及只读截止。用户输入沿用 M2 结构化边界；机器快照放 context，不能伪装为 user_answer。

模型响应沿用建议结构：只能关联该既有任务，复用其未完成行动或提出需确认的新行动。禁止 task create/update、变更截止、生成取消写集、写完成状态、跨任务引用。replacement_ids 只由本地用户选择产生，模型即使返回类似指令也不能执行。

模型返回澄清时复用 M2 面板和续轮；本地改排选择及冻结事实独立保存。改选择/工作量后作废迟到响应，模型重试不扩大授权，取消等待不提前取消安排。

### 6.3 版本和备份决定

建议本轮正式契约升至 schema 0.6.0，模型 HTTP 协议支持新增 1.1；旧 1.0 的 new_plan 保持可用，新增改排只走 1.1。响应版本与被接受请求对应，旧客户端不得误接改排能力。模型输出自身既有协议标识如何适配须写入差异表，不能仅替换一个常量。

IndexedDB 保持 v4：现有存储区足够，无需新 store。ZIP 容器保持备份 v2，但明确允许 0.5.0 与 0.6.0 内容的读取适配；0.5.0 草案默认 create、取消集为空，不产生新授权。不要批量重写旧库或改动 frozen 0.4.0。

新备份不保证旧构建可读，要明确提示版本要求；不能伪装成旧 schema。更新 refs 注册表及备份校验/重映射，覆盖目标任务、替换 ID、旧快照里的真实引用、进展中的行动引用、结果摘要及 revision_history。文本中的 ID 不替换。

恢复只恢复内容：改排候选必须重新排程和核对当前事实；pending/执行信封/取消授权不随备份重放；已采用草案只读，被取消安排保持取消，已有历史不恢复成待执行。继续禁止导出 assistant_ops。

## 7. 原子采用：必须修改的最小事务能力

继续沿用 `prepare → apply → resolve` 和既有台账，不建立第二套提交系统。

1. prepare 读取固定空间快照，验证模式、范围、原始记录、无会话引用、当前容量和确认；生成完整取消/新增预览、固定 ID 映射及意图签名，零业务写入。
2. 意图签名必须覆盖改排范围、进展与工作量、所选旧记录基线、最终排程和确认。编辑其中任意内容使旧信封失效。
3. apply 的第一阶段可继续写 pending 台账及 applying 状态，但不能修改任何正式 PlanItem。
4. 最终提交事务重新读取 docs/草案/台账，复核所有所选旧安排、任务/行动状态、会话引用和完整占用。重建的取消集必须与用户选择和信封完全相等。
5. 在同一事务中取消旧安排、新增新安排与必要新行动、更新线程和草案为 applied、写成功回执。任何错误整体回滚，不允许先批量取消再逐条新增。
6. 新对象继续 add()，ID 冲突整体拒绝。旧对象只接受受限 plan-item cancellation 操作：同空间、同任务、预期内容完全匹配，只将 state 改为 cancelled，其余字段保留。
7. 双击、双标签、崩溃重试复用同一 application_id 与冻结 ID；已提交返回同一回执。结果未知先 resolve，不能再做一次新改排。采用后再次调整新建草案。

M1/M2 的普通新增路径继续执行原有拒绝修改规则，不能因为事务新增取消能力而获得泛化更新权限。

## 9. 实施顺序：三步完成一个版本

**第一步：规则和本地闭环。** 落契约差异，做单任务选择、资格、用户工作量和受限原子替换。先用手工工作清单/fixture 跑通预览、保存、失败回滚和恢复；这一步不依赖真实模型。

**第二步：接同一助手。** 增加 replan_task 请求与后端语义守卫，接进展理解、建议工作清单和澄清；复用 M2 的取消、迟到拒收、保存失败仅重试保存。完成备份适配与两处入口。

**第三步：体验和交回。** 跑必要回归和浏览器矩阵，做一例真实模型改排证据，保存桌面/手机截图或一段录屏，交一份短报告。

三步是内部实施顺序，不要求每一步停下来等人工验收；完成整个 M3 初版后统一交回。发现必须扩大到多任务、批改任务或改专注历史时才停下说明范围冲突，不自行扩展。

## 10. 最小验收矩阵

| 场景 | 必须观察到的结果 |
| --- | --- |
| 主线 | 一个行动已完成，另一项本次待安排 90 分钟，一天不可用，选两条合格旧安排 → 预览 → 保存；任务不重复创建，旧取消、新安排出现 |
| 保留范围 | 未选安排、窗口外安排、其他任务安排内容不变；仍计入适用窗口容量 |
| 历史保护 | done/partial、有投入、actual=0、有任意会话引用、正在专注的安排不能选；只读显示原因 |
| 模拟容量 | 预算 120/缓冲15%/选中占用60/保留占用30，得可用72；无重复扣减；所有任务占用参与 |
| 工作量 | 保留安排情况下先确认工作范围；不把专注时长当进度，不把旧预计量当剩余量；未知值不排成0 |

| 预览零写入 | 生成、改表单、取消预览、模型失败都不改变正式安排 |
| 事实漂移 | 预览后另标签开始专注、修改旧条目、完成/删除任务、新增占用或跨午夜 → 整体要求重核 |
| 原子失败 | 注入取消后、新增中途的写入失败 → 旧安排未取消，无半份新对象，无成功回执 |
| 幂等 | 双击/双标签只成功一份；结果未知后 resolve/刷新不重复取消新增 |
| 备份 | 新草案与已采用历史 ZIP 往返；恢复引用重映射；不恢复 pending 授权；旧0.5.0备份继续可读 |
| 普通新增 | 原 M1/M2 新建流程、八项来源/刷新/迟到反例保持通过；create 信封夹带取消集拒绝 |
| 手机和离线 | 手机能选范围、核对与保存；模型不可达保留输入，有效本地清单可继续规则排程 |
| 真实模型 | 虚构资料/任务，真实进展说明→建议→用户核对→日程改排，明确标注真实调用与最终结果 |
