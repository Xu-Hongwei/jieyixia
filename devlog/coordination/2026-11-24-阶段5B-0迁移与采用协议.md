## 2 DB v4 迁移与降级

迁移规则（5B-1 实施）：

- 沿 db.js:44-52 既有模式，`onupgradeneeded` 只 `createObjectStore`（keyPath 'id'）新增三个 store；**绝不重写**既有 sources/docs/workspaces/focus_runtime，不批量升级 Focus 记录。
- 多标签：`onversionchange` 关连接清缓存（db.js:57-60）、`onblocked` 报 DB_UPGRADE_BLOCKED（db.js:64-69）沿既有逻辑，不新造等待协议。
- 世代保护（db.js:12-21,86）继续适用：助手写入同样捕获 {ws,gen}，切空间拒绝。
- **降级不承诺“换回旧前端即可”**：旧前端 `indexedDB.open(name, 3)` 打不开已升 v4 的库。回退方案＝升级前导出 v1 备份留存＋说明 v4 库只能由新前端读取；不提供静默降库工具。
- 发布顺序硬约束：5B-1 同批交付「v4 迁移＋草案保存＋草案备份/恢复」，不允许先存助手资料、备份却漏掉这些资料的窗口。

三个新 store 的职责：

| store | 内容 | 是否进备份 |
| --- | --- | --- |
| assistant_threads | AssistantThread（record_version=1，≤200消息，每条≤16000字符） | 是（data/assistant_threads.json） |
| assistant_drafts | AssistantDraft（revision≤20，序列化≤1MiB，含 revision_history） | 是（data/assistant_drafts.json） |
| assistant_ops | 采用协调台账：pending 冻结信封 / committed 回执 | **否**（永不导出/导入） |

助手对象不塞进 docs 的未知 kind，不复用旧 PlanDraft 私加字段。

## 3 Source 身份审计（开工单§7.1 要求，已完成）

对全部 putSource / 恢复 / 撤销入口的只读审计结论：**当前代码不存在原地改写 Source 或以原 ID 覆盖原文的路径。**

| 入口 | 位置 | 事实 |
| --- | --- | --- |
| putSource（唯一底层写入口） | db.js:108-113 | stamp+snapshot 后 put；调用方仅下列两处 |
| collectFiles | frontend/src/stores/app.js:276 | 每次 `crypto.randomUUID()` 新 ID（:282）→ putSource（:285） |
| collectText | app.js:297 | 新 ID（:303）→ putSource（:306） |
| runAnalysis | app.js:354 | 只读 source（:368-371），写仅 putDoc（:383,:411），不重写 Source |
| retrySave | app.js:443 | 仅 doc，不触 Source |
| 备份恢复 | backup/remap.js:63-84 | buildRemap 对**全部** Source 生成新 ID（:65,:80）；sourceFromBackup（adapt.js:87-100）用归档字节重建 Blob；仅 id/workspace_id/is_demo 变化 |
| 撤销删除 | app.js:866 → domains/matter.js:315 undoDeletePlan | 经 transformFocusAtomic 只写 docs；Source 从不删除（无 deleteSource），撤销不触 Source |

5B-1/2 在写入边界保证该前提的规则：

1. 采用事务对 sources **只读**：核对 Source 仍存在、归属当前空间、允许变化的元数据；核对完整 Note 字段基线。确认/修改解析候选一律写 Note 字段（putDoc），绝不 putSource 到既有 ID。
2. 替换原文/图片＝走 collect 路径生成**新 Source ID**；旧 Source 保留。事务发现引用 Source 已被新 ID 替换 → needs_review（场景 s-recheck-source-replaced）。
3. 原文内容哈希用于事务外前置快照与证据；**不在活事务内 await 读 Blob/算摘要**（IndexedDB 活事务中 await 非 IDB 异步会提前结束事务）。
4. 普通恢复继续全量新 Source ID；合法撤销只恢复原快照，不借机替换原文。
5. 任意开发工具直接篡改浏览器数据库不属于应用并发保护的承诺。

## 4 采用事务协议（5B-2 实施规范）

### 4.1 准备阶段（事务外）

prepare_application：读当前空间 → 不可变快照（snapshot/deepRaw，db.js:25-37）→ 冻结 draft_id/revision、用户确认（绑定 revision+字段+旧新值）、影响清单、分段顺序、临时key→正式ID映射（客户端 crypto.randomUUID，不复用模型 UUID）、application_id、input_signature（SHA-256，固定顺序基线字段）。所有哈希/异步计算在事务外完成。

信封结构＝提案 ApplicationEnvelope：有缺口必须 gap_acknowledged=true，有既有过载日必须 overbook_acknowledged=true（models.py:1352-1364 强制）；id_map 双向唯一；写集 PreparedWriteSet 不含任何替换字段（首版 D11）。

### 4.2 协调预写（独立小事务）

正式写入前：pending 信封落 assistant_ops ＋ 草案标 applying。这一步只写协调状态，不创建正式 Task/Plan；落盘失败即不提交业务事务。**同一 draft revision 不得存在两份生效信封**（两标签并发时第二份在协调事务内被拒）。

### 4.3 业务提交（单一 IndexedDB 事务）

沿用 transformFocusAtomic（db.js:210-260）模式：plan 函数同步读最新→比较→返回 puts/deletes，事务内只做同步事实比较与 IDB 操作。

store 范围：

| store | 模式 | 用途 |
| --- | --- | --- |
| docs | readwrite | Note 字段确认、Task/Action/PlanItem 写入 |
| sources | **readonly** | 核对存在/归属/元数据（§3） |
| assistant_drafts | readwrite | 草案 applied＋applied_summary |
| assistant_ops | readwrite | 回执落盘、pending→committed |
| focus_runtime | **readonly** | 执行保护核对（未结束会话/历史投入） |
| assistant_threads | readwrite（仅当需更新结果引用） | 线程消息追加采用结果 |

事务内顺序核对（场景表 ADOPTION_RECHECK 已冻结，s-recheck-* 样本）：

1. 同 application_id 已有回执 → 核对 input_signature：匹配返回原结果（零写入）；不匹配拒绝（零写入）。
2. 草案仍属同空间、同 revision、未被其它 application 采用；已被采用 → 冲突＋可核实原回执入口，不重复创建。
3. 读取**全部**最新相关对象、被引用来源、候选字段、完整规划窗口占用与执行记录——必须发现新插入的同日安排，不能只查用户选中 Task 的 updated_at。
4. 重新验证来源确认、任务状态、引用、当日容量与预计变更；跨午夜或关键事实改变 → needs_review，展示全部相关差异，禁止自动改方案后继续提交。
5. 全部通过 → 一次写入：Note 字段确认、Task（created/updated 由本地服务产生）、Action（done=false）、新 PlanItem、草案 applied＋applied_summary、ApplicationReceipt、ops committed。任一步失败整体回滚（零业务写入）。

新 PlanItem 硬形状（PreparedPlanItemCreate 使非法状态不可表达）：state=planned、actual_minutes=null、focus_session_id=null、task_ref_state=active、**无 action_id 字段**（保持 0.4.0 语义，样本 f-planitem-no-action-id / f-planitem-actual-not-null）。同日新 order 在既有最大 order 之后按草案顺序分配，不重排现有条目；超安全整数拒绝，不静默溢出。

尚未排下的已知 Action 创建但保持未完成（D08）；明确排除的步骤不创建（D07）。成功结果逐类列真实数量，不把“建议100项”当“保存100项”。

### 4.4 失败分类与 result_unknown

| 类别 | 判定 | 处理 |
| --- | --- | --- |
| 输入/事实拒绝 | 核对 1–4 未过 | 零业务写入；草案 needs_review＋全差异 |
| 事务中止 | onabort/onerror | 零业务写入；保留同一信封，显式重试前重新核对 |
| 可能已提交但读取失败 | 事务结果未知 | 草案 result_unknown（“保存结果待核实”，**不是**“没有写入”）；查询原 application_id |

查询原回执须在相同事务范围协调后读取（另一页可能仍在提交，暂时查不到≠绝对未执行）。查到回执→恢复原结果；确认未提交→保留**同一信封**，用户显式重试前重新核对；**绝不生成新 ID 再写一批**。新需求/重新确认后的新版本才签新意图。

assistant_ops 分 pending/committed；首版不自动清理台账。applied 草案不可再次采用，丢失回执不重新放行。用户清空空间/恢复到新空间是不同边界（恢复不导入 ops，见§5）。

### 4.5 5B-5 替换协议预留（首版不执行）

只允许：今天及以后、用户显式选入替换集、state=planned、活引用、无任何 Focus 引用、未锁定。届时采用「旧安排 cancelled＋新安排新 ID」同事务变更，不硬删、不把 moved 伪装成迁移链；partial/done/有投入记录继续走既有显式流程。首版 PlanningInput.replacement_ids schema maxItems=0（f-plan-replacement-nonempty），代码无该分支。
