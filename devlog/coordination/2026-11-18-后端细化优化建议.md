## 第二轮：让公开调用有明确边界

1. **统一调用总时限。** 当前 profile 默认 timeout_s=90、retries=1，多 profile 按序降级；总耗时会随次数累加。HTTPX 的连接/读取等阶段超时也不等于整条业务请求的总时限。增加贯穿尝试、退避和降级的总预算，在每次尝试前检查剩余预算，并保证实际请求能在预算内结束。前端等待时限、反向代理时限和后端预算一起设定；预算值按部署与实际延迟确认，不靠简单缩短单次 timeout 代替。
2. **限制并发与费用。** 公开分析入口设置运行中请求上限、有界等待、访客调用频次及总体费用边界。达到限制时快速降级，保留仅保存与固定示例。单进程信号量只能限制单进程，多 worker/多实例部署需通过网关或共享控制覆盖整体；不为此自动扩张成完整账户系统。
3. **谨慎处理重复调用。** 浏览器重复点击首先在前端阻止；后端可先合并同一进程中、同一客户端操作标识的在途重复请求，明确隔离、有效期和冲突规则。不要用 source_id 单独充当唯一请求键：同一资料可修改参照后重新分析。跨用户缓存与长期结果缓存暂不做。断线或超时不能自动推定上游未执行、未计费。
4. **明确健康状态。** 当前 ModelProvider.ready 只说明路由配置能装载，不证明厂家此刻可访问。区分服务存活、配置就绪及最近调用状态；定期/人工探测需限频，健康检查本身不触发付费识别。前端不能把配置就绪等同实时模型可用；更改响应结构时遵循契约流程。
5. **请求关联与排错。** 每个请求生成并透传 request_id，记录总耗时、尝试耗时、降级原因、错误码及限流结果。元数据日志采用允许字段，异常日志只保留分类和安全诊断，不带原文、图片、密钥或完整上游异常。优先请求头传递关联标识，避免无必要改变响应契约。
6. **配置与资源管理。** 启动时校验 profile 名称唯一、协议合法、timeout/max_tokens/retries 的类型及合理范围；避免异常配置在用户调用时才报错。按生命周期复用适配器 HTTP 客户端并关闭资源；当前同步路由可以保留，是否改异步由并发测试决定。

验收至少覆盖：模型慢响应、限流、首选厂家失败、全部失败、重复点击、预算耗尽以及超限请求；以本地受控假厂家为主，先不增加真实模型费用。

## 第三轮：提高分析质量的可测性

- 建立可公开提交的虚构/脱敏语义样例集：普通通知、活动开始与提交截止混合、改期旧节点、没有年份、旧截图相对日期、跨年、时区混合、低质量图片、非任务资料。
- 每个样例单独标明预期字段、节点角色、截止、是否应留空与引用依据，防止只验证 JSON 合法而语义错误。
- 文字资料可以检查引用是否确实出现在输入中；概括字段允许聚合支撑片段，需要定义相应规则。图片引用当前仍是模型候选，不能因为返回 quote 就声称已完成独立 OCR 核验。
- 分开报告离线解析回归与真实模型端到端结果。历史原始输出重放不能证明新提示词的输出质量；现有 golden 的通过条件主要是结构与不变量，需补明确语义期望。
- 输出识别遗漏、错误截止、应留空却生成具体值、角色混淆与引用不匹配等错误清单；竞赛材料记录样本版本、提示词/契约版本、模型标识及实际执行日期。

## 暂缓事项与架构边界

继续保持无状态分析代理与本地优先：任务、事项、专注、规则规划及备份恢复按既定分工实现。暂不增加跨便签自动改期、AI 归组、AI 规划、云端用户数据库、复杂队列或微服务拆分。core.py 可以随修补提取小型纯函数，但大规模重构不作为前端推进的前置条件。

建议执行顺序：第一轮中的入口校验、依赖和文档修补先完成；完整 HTTP 测试定位同步推进；第二轮在公开接入前验收；第三轮与真实前端核对界面联调逐步补充。新增响应字段、错误码或语义变化都需同步源模型、生成物、前端接收和交接资料。
