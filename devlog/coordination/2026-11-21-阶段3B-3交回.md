## 1 实际改动

### 1.1 本轮（B3-4）发现并修复的真实缺陷：PlanItem 活引用闭合（X20）

**证据先行**：先写红探针 `x-legacy.cjs` X20-B，删除带计划条目的任务后断言 `plan_item.task_ref_state`。首跑 **17/19**，两条计划条目仍 `active` → 与契约 0.4.0 冲突：
- `contract/models.py:800`：`state=planned` 且 `task_ref_state=deleted` 直接拒绝（「未执行计划不得继续指向已删任务」）。
- `contract/generate.py:246-264`：deleted-ref 计划条目要求任务**不存在**；active-ref 要求任务存在且同空间。

即：删任务时 **planned 条目必须随任务移除**，**已执行条目（done/partial/moved/cancelled）保留为历史并置 `task_ref_state='deleted'`**。原前端删除事务只断开 focus_session 引用，漏了 plan_item，留下悬空活引用。

**最小修复（现有领域，非计划功能扩展）**：
- `frontend/src/domains/matter.js`：新增 `planRefDelete(latest, taskIds)` 辅助——planned→`deletes`+`removed`；已执行且非 deleted→`puts{task_ref_state:'deleted'}`+`detached`。`deleteTaskPlan` / `cascadeDeleteNotePlan` 把计划补丁并入同一事务的 puts/deletes，并在 `info` 捕获 `planRemoved`/`planDetached`。`undoDeletePlan` 恢复 planned 本体（任务须已恢复，否则整体拒绝）、逐条回补 detached 引用（缺失/已变化/任务仍缺→refused，不覆盖），返回 `info.planRefs{applied,refused}`。
- `frontend/src/stores/app.js`：`deleteTask`/`deleteNote` 的 `lastDeleted` 快照新增 `planRemoved`/`planDetached`；`undoDelete` 读取 `planRefs`，有 refused 时明确提示「部分计划条目的任务引用未回补……保持断开状态」，不笼统报全成功。
- `frontend/src/tests/action.test.js`：+7 例（planned 移除/done 断开/info 捕获、无 plan_item 零写入、联删计划闭合、撤销恢复顺序与分钟不变、撤销 ID 占用拒绝、撤销引用已变化 refused、deleteAction 不动 plan_item）。

**零回归保证**：产品前端当前从不创建 plan_item（仅种子夹具可达），`planRefDelete` 在无 plan_item 时 puts/deletes/removed/detached 全空 → 对现有数据是 no-op。修复后 `x-legacy` **19/19** 绿，`x-undo`/`x-scope`/`x-protect` 重跑全绿（见 §3）。**不新增计划状态、不重排、不重算、不新增计划 UI**，符合开工单 §5「已有 PlanItem 按 0.4.0 与既定删除/撤销策略处理，检验活引用闭合与历史保留」。

## 4 失败注入方法

- **DB 事务失败**：临时 Context + 虚构种子数据，`page.evaluate` 补丁 `IDBObjectStore.prototype.put`，当 `window.__failFocus`（或 `__failDocs`）为真且 `transaction.objectStoreNames` 含 `focus_runtime`（或 `docs`）时抛 `DOMException('AbortError')`，使整笔事务回滚。用于 X15（删除/撤销写入失败回滚）、X21-B（切空间保存失败留原页）、U08（离开前保存失败）。
- **可撤销与无残留**：每段注入结束 `setFail(false)`，并断言 `window.__failFocus===false`（X21-B 显式检查「失败注入已清除」）。区分「提交未发生」（事务 abort，对象/引用全回滚）与「已提交但回调迟到」（信封/草稿序号协议拒绝旧请求，X10）。
- **不清用户库/不改系统时钟/不停用户后端**：全部在隔离浏览器 Context 的虚构 `jxl-product` 库内；时间用 Playwright 受控时钟（见 §5），不改 OS 时钟；用户 8000 进程未触碰。

## 5 真实时间 vs 模拟时间证据区别

- **受控时钟（模拟）**：`clock.install` 自动走针 + `setSystemTime` 跳变 + `advance(ms)`（1s `runFor` 分块 + 25ms 真实 sleep）。用于推进租约到期（30s）、长间隙（60s）、明显跳变（5min）、跨北京时间午夜、墙钟回拨/前跳。**这些是受控时钟推进，非实际等待，更非已实测 OS 休眠。**
- **模拟休眠/后台**：以「停止调度 + 受控时钟推进 + 恢复可见」模拟长后台/休眠间隙（x-anomaly X07），探针注明方法；**不声称已实测真实操作系统休眠**。
- **真实关闭页面**：x-anomaly X06 含一组真实 `page.close()` 后重开（同 context 新 page 共享同源 IDB），验证至少恢复最后落库正文/累计/上下文。
- **真实多页竞争**：同一浏览器 Context 两个以上 Page 共享同源 IndexedDB，竞争操作尽量同时触发，断言胜者数量/失败码/owner/epoch/正文/累计（x-multi X01–X05）。
- **真实操作真实落库**：开始/编辑/暂停/继续/结束/删除/撤销均经真实 UI 入口 + 真实 IDB 断言；断网用 `setOffline`。
