## 必须在公网冻结前处理

### P0：模型端点没有访问和成本控制

当前 README 明确写着“无鉴权”，API 也没有请求频率、并发数、匿名额度或单来源配额。只要模型模式公开，任何人都可以反复提交图片并消耗上游额度。比赛页面可以保持无登录，但模型 API 至少应放在网关后面，或增加匿名 demo 限额、并发信号量和每日预算。

### P0：上游响应没有字节级上限

适配器把所有 `iter_bytes()` 结果放进 `chunks`，再一次性 `b"".join(chunks)`；`max_output_chars` 只在 JSON 已经读完后才检查。恶意或异常上游返回大 body 时，内存会先被占用。应增加 `JXL_MAX_MODEL_RESPONSE_BYTES`，读取过程中累计字节数，超过上限立即关闭响应并映射为可重试错误。

### P0：依赖没有锁定，当前环境已经出现兼容性漂移

`backend/pyproject.toml` 只有下限约束（例如 `fastapi>=0.136`），没有 lock/constraints；包版本仍是 `0.1.0`，而契约和 API 已是 `0.3.0`。当前工作区实际是 FastAPI 0.136.1 + Starlette 1.0.0，`TestClient` 在进入应用生命周期时会挂起；历史干净环境证据使用的是 FastAPI 0.163.2 + Starlette 1.10.0，292 项通过。应固定经过验证的版本组合，提交 constraints/lock，并在 CI 中用全新环境重跑完整测试。

### P1：时间语义文档仍有冲突

代码和 README 已说明产品默认北京时间，但 `backend/app/model/core.py` 的 `canonical_datetime` 注释仍写“让前端按用户本地时区解析”，`handoff/HANDOFF.md` 第 193 行也保留了“按用户本地时区解析”。这会导致前端实现回退到设备时区。应统一改为：`tz_known=false` 只表示原文未声明时区；业务计算按北京时间，展示层不得自行按设备时区改写。

### P1：请求体限流会产生两份大内存副本

`BodyLimitMiddleware` 先把 chunks 存在列表，再 `b"".join` 成完整 body。8 MB 上限在多并发下会放大内存峰值。后续应改为受限缓冲或交给反向代理做 body limit，并为读取请求体增加超时。

### P1：日志缺少跨请求关联字段

目前日志有 `source_id`、provider 和耗时，但没有服务端 `request_id`，模型重试、供应商切换和 503 很难在日志中串起来。建议生成不可预测的 request id，响应头和结构化日志同时记录；`source_id` 只作为业务幂等键。

### P1：工作树有生成物

`backend/jiexialai_backend.egg-info/` 是未跟踪的构建生成物。提交或打包前应加入忽略规则并清理，避免把本机安装状态带进比赛材料。

## 当前验收边界
