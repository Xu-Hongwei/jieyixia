## 3 协议分层与唯一来源

四层（开工单§3）：HTTP（AssistantProposeRequest/Response）→ 模型建议（AssistantModelProposal）→ 本地草案与排程（AssistantDraft、PlanningInput/Result）→ 应用信封/回执（ApplicationEnvelope/Receipt）。模型输出永远不是数据库命令。

隔离与生成规则：

- 唯一手写来源：`contract/proposals/assistant-v1/models.py`。schema.json、typedefs.d.ts、limits.json 全部由同目录 `generate.py` 生成，`--check` 逐字节比对；不得手改生成物。
- 限额唯一清单：models.py 的 `LIMITS`（28项）→ limits.json，含 value/unit/scope/future_config。selftest 程序化交叉校验 limits.json==LIMITS 且字段 max_length 元数据与限额一致；不允许第二套手写常量。
- 不加入正式 ALL_MODELS；生产前后端（frontend/src、backend、contract/models.py）零 import 提案，门禁以机器检索证明。
- 版本路线**仅为提案**：业务契约 0.5.0、DB v4、备份 v2、assistant_protocol_version="1.0"。当前正式版本保持 0.4.0 / v3 / v1 不变（基线证据见 private-evidence/stage5b-0/base-versions.txt）。
- 临时引用判别类型 `{kind:"draft",key}` / `{kind:"existing",id}`；key 仅在单一草案 revision 内有效，正式 ID 由客户端采用时生成，不复用模型自造 UUID。
- schema 管结构（白名单/枚举/有界数组/真实日历），语义校验管引用、依赖、守恒（selftest.py 的 check_model_semantics / check_planning_semantics / check_planning_pair）。

## 4 草案状态流转（冻结表）

状态集合：editing / generating / needs_clarification / ready / needs_review / applying / applied / result_unknown / discarded。以下边集已在 selftest.py `DRAFT_TRANSITIONS` 冻结并以场景样本校验（设计验证）：

- `editing → generating | discarded`。
- `generating → needs_clarification | ready | needs_review | discarded`。
- `needs_clarification → generating | editing | discarded`（回答后修订，revision+1）。
- `ready → applying | editing | generating | discarded`（继续修改或重新生成，revision+1）。
- `needs_review → editing | generating | discarded`。
- `applying → applied | needs_review | result_unknown`。
- `result_unknown → applied | applying | needs_review | discarded`（核实原 application_id 后；applying 为显式重试原信封）。
- **终态**：applied、discarded。applied 永不回 ready；丢失回执不重新放行。

刷新映射（`REFRESH_MAP`）：generating→needs_review（中断待显式重试）；applying→result_unknown（先核实原信封）；result_unknown→result_unknown。

恢复映射（`RESTORE_MAP`，备份恢复到新空间）：所有未应用态（含原 ready/generating/applying/result_unknown）→needs_review，清除可执行信封/旧事实基线/旧采用授权，内容完整保留；applied→applied（历史只读）；discarded→discarded。原 applying 不能据备份断言未提交。

并发与晚到响应：修改范围/需求/建议/排程均递增 revision；采用只接受当前 revision；晚到响应必须 thread/turn/client_seq/workspace/revision 全匹配才接纳。确认事件绑定 revision+对象+字段+旧新值，改值使旧确认失效。

ready 资格（全部满足）：关键 Task 事实已确认；采用范围内新 Action 估时为正；工作项剩余估时已知（或已明确排除）；引用全部有效；无硬约束违规；缺口/既有过载已取得独立确认；既有安排重叠的工作量口径已确认（D12）。

## 6 排程规则摘要与伪代码（daily-v1）

容量公式（唯一口径，DaySummary 校验器强制）：

```
allocatable = floor(budget_minutes × (100 − buffer_pct) / 100)
free        = max(0, allocatable − committed_minutes)
overbooked  = max(0, committed_minutes − allocatable)
```

buffer_pct 为 0–50 整数，默认15；DaySummary.buffer_minutes 必须恰等于某整数 pct 的 floor 结果，防止派生值不一致。占用按唯一 PlanItem ID 计一次：planned/partial/done 按原日期原 planned_minutes 保守计入；cancelled/moved 不占用；done 不腾空；Focus 分钟不二次相加；提前执行不移日期。断引用 partial/done 历史仍占用；planned+deleted 等不可信占用阻断核对，不按0。过载日 free=0、不新增，采用需确认旧过载。

算法伪代码（5B-1 实现依据；5B-0 只交付规范化输入+手算金标+本伪代码）：

```
1 校验：真实日期/空间归属/引用/正整数或null/依赖无环/硬约束；非法输入拒绝，不归为“无容量”
2 每项定界：earliest = max(start_date, earliest_date)
           latest   = 日期截止→截止当天；精确时刻截止→北京时间日期−1天；
                    无截止→窗口末；逾期且已确认补做→窗口末（保留原截止事实+警告）
3 逾期未经确认 → unscheduled(overdue_requires_consent)，不参与排程
4 循环：取前置已全部排完的就绪项，按 (有效截止升序, priority, 稳定key) 排序，无截止最后
5 对每项从 earliest 扫到 latest：
    不可拆：整段放入首个 free≥remaining 的日；放不下 → unscheduled(not_splittable)
    可拆：逐日分配，非最终段 ≥ min_segment_minutes，最终余量段可更小，所有段正分钟
    截止界内耗尽 → unscheduled(deadline_window)；无截止窗口耗尽 → unscheduled(no_capacity)
    精确时刻截止当天在窗口内且 free>0 但需时段核对 → unscheduled(needs_deadline_day_window)
6 前置仍有未排量 → 后继零段 + unscheduled(dependency_blocked)；同日后继必须 order 严格在后
7 无隐藏回溯/随机重排；未找到完整方案 ≠ 数学无解
8 输出守恒：每项 remaining = Σ段分钟 + 未排分钟；excluded 单列；
  complete=true 仅当全部已知估时、零未排、零阻断、零冲突
```

未排原因语义（冻结解释，见§7）与守恒由 selftest.check_planning_pair 独立重算校验。**金标是手算期望值，校验属“规范样本校验”，不是排程器功能通过。** 20份金标：g1–g8 对应开工单§5.3八算例（逐分钟手写字面量），g9–g17 覆盖稳定排序/重跑一致/闰日跨月/跨年/断引用历史/取消moved释放/未选任务占用/超窗口/逾期补做与未确认/截止当天时段核对。

## 7 冻结解释与开工单内部差异

开工单未写死或存在表述差异之处，按以下解释冻结；均不扩大首版范围：

1. **精确时刻截止的写法（R1 修正）**：开工单算例6写 `2026-11-26T09:00+08:00`（无秒）。正式 0.4.0 **Task.Deadline 用 DATETIME_RE**（contract/models.py:316），允许无秒/naive/小数秒；严格 DEADLINE_VALUE_RE（必须带秒）只用于 AnalyzeResponse.deadline 与 TimeNode.value，不是 Task.Deadline 的规则。提案分两层：既有事实快照（ExistingDeadline/PlanningTaskFact）用 `_check_existing_deadline_value`，与正式 Deadline 同口径（无秒/naive/小数秒合法；naive 按北京时间解释；保留原值与原精度，不改写）；模型新候选（DeadlineCandidate）另用严格规范输出规则（datetime 必须带秒），不与旧事实共用不兼容约束。金标用 `2026-11-26T09:00:00+08:00`（两种规则都接受）；兼容正例 f-compat-deadline-* / f-compat-planfact-*，非法日期/偏移负例同组。语义不变：默认最迟排 11-25。原文此处曾误称「0.4.0 规范 datetime 必须带秒」，已按审查 R1 更正。
2. **未排原因边界**（开工单只列枚举未定义边界）：`deadline_window`=有截止项在截止界内容量耗尽；`no_capacity`=无截止项窗口容量耗尽；`needs_deadline_day_window`=精确时刻截止、截止当天在窗口内且当日 free>0，但按天规则无法保证上午截止前完成，需用户核对当天时段；`not_splittable`=不可拆整段放不下；`outside_horizon`=最早日晚于窗口末；`overdue_requires_consent`=逾期未确认补做；`dependency_blocked`=前置未全部排完。各原因的前置条件由 selftest 反向校验。
3. **重复占用引用**：“重复引用不双计”实现为输入边界唯一性拒绝（f-plan-dup-occupancy），组装器在构造输入前按 PlanItem ID 去重；不在计算阶段静默去重掩盖脏输入。
4. **20版本与1MiB双上限**：哪个先到都提示基于当前内容新建草案，原记录保留；revision_history ≤19 条（含当前共20），整体序列化 ≤1MiB。不静默删历史。
5. **逾期补做后的最迟日**：用户明确补做后 latest 取窗口末（否则过去截止日永远排不进当前窗口）；原 Task 截止事实不变，必须带 overdue_scheduled 警告，不声称按时完成。
6. **PlanningWorkItem.estimate_origin**：开工单§4.3把 estimate_origin 定义在 WorkItemProposal；规范化排程输入镜像保留该字段，使保存草案中的估时来源（user/model）可追溯，排程计算本身不消费它。
7. **replacement_ids 拒绝层次**：schema maxItems=0 是机器信号（前端 checkJs 可见），字段约束先于语义消息触发；负向样本预期按实际拒绝原因（too_long）记录，语义校验器保留同义中文消息作第二道防线。
8. **预算未指定**：PlanningContext 日预算允许 null（澄清用），PlanningInput 日预算必须 0–1440 整数（排程前必须已确认）；null 不得进入排程，也不得默认0。

## 9 限额清单与调用预算

28项限额唯一来源见 `limits.json`（由 LIMITS 生成），每项含 future_config 接入映射：backend propose 校验/BodyLimit 按路径/输出上限/专用 profile（max_tokens=8192，不改 analyze 默认）/attempt_gate 共享每日额度（5B-3）；前端约束卡/选择器/domains/planning（5B-1/4）。**更低的已配置上限优先；单接口不得放宽全局保护。**

一次完整用户操作（3张新图+补充要求→规划）的调用清单：

| 调用 | 次数上限 | 预算 | 额度 |
| --- | --- | --- | --- |
| analyze（每张新图各一次） | ≤3 | 各自现有独立预算（默认120s/次） | 每次实际厂家尝试计入共享每日额度；沿用现有 ModelRouter 逐 profile fallback（registry.py:151–153）：retries 是单 profile 上限，一次 analyze 的配置尝试上界=各可用 profile (1+retries) 之和，实际还受时间预算/共享额度/提前成功限制 |
| propose | 1次请求 | 整体120s，全部厂家尝试合计≤2（含重试/结构修复/fallback） | 同上共享每日额度 |

「2次propose尝试」是未来一次 propose 的整体上限，不是全流程模型调用上限；analyze 不新设整体尝试上限，沿用现有 profile/fallback、时间预算与共享每日额度。`3×2+2=8` 只是「每次 analyze 仅有一个 retries=1 profile」的特定算例，不是普适最坏上限：多 profile 降级时全流程可超过 8（s-call-budget-multi-profile：3次 analyze 各两个 retries=1 profile，配置上界各4合计12，实际7次＋propose 2次=9次）。首版不宣称 request_id 保证付费恰好一次；取消不保证免除已发生费用。样本 s-call-budget-ok/over/multi-profile/attempts-over-config 冻结该口径。（R5 修正：原文曾把单 profile retries=1 误当整个 analyze 的上限；本批只改文档与设计样本，未改正式后端重试策略。）
