## 3.5 时间格式不统一的成因审查

| 形状 | 成因 | 性质 |
| --- | --- | --- |
| `YYYY-MM-DD` | 原文只写日期；PRD F07 禁止补 23:59 | 设计（精度是语义） |
| `...T18:00:00`（无 tz） | 原文没写时区；不编造 | 设计 |
| `...T18:00:00+08:00` | 原文/模型给了时区 | 正常 |
| `...T18:00:00+00:00` | 昨日 bug 历史遗留存于 IndexedDB | 脏数据，新管道不再产生 |
| 相对词丢时刻 | 真缺口 | 已修 |

结论：统一应发生在结构层（precision: date|datetime、tz: string|null），字符串差异是语义的正确表达。v0.3 评审议题。

## 8 追加：时间格式固定化（用户澄清「我说的是时间格式」）

用户 concern：格式要固定，前后端交接不能「后天识别不了」；不要靠关键词猜。

### 8.1 现状澄清

- **格式强制**早已是机器手段：契约 `DEADLINE_VALUE_RE` pattern 硬校验（越界 422）+ `canonical_datetime` 规范化 + 版本化 schema/typedefs。不是关键词猜格式。
- 但固定的是「一组合法形状」（date / 带 tz datetime / naive datetime），前端仍需判断是哪种 → 交接隐患真实存在。

### 8.2 v0.2.1 additive：结构元数据消歧（已实施）

Field 新增可选 `precision: date|datetime` 与 `tz_known: bool|null`。值保持语义真实形状（不伪造），前端按元数据确定性渲染，零猜测。纯加字段不破坏 v0.2。

- 后端 `_build_field` 计算并填充；`timezone_unspecified` warning 改由 `tz_known=False` 触发。
- fixtures 01/02/03 的 deadline 字段补元数据（mock 与真返回同形状）。
- lab 便签区显示 precision 徽章 + 「时区未知」徽章。
- schema.json / typedefs.d.ts 重新生成；selftest 24 负向全拒；**119 测试全绿**（+1 元数据测试）。
- 真 API 复验：`deadline = {value: 2026-11-27T17:00:00, precision: datetime, tz_known: false, status: unresolved, derived: true}`。

### 8.3 诚实边界

- 固定格式 ≠ 单一字符串形状；形状差异是语义（精度/时区是否已知），由元数据消歧而非抹平。
- **自然语言→时间的换算目前仍是确定性正则 resolver**（可测但脆，遇「月底/三天后/国庆前」失效）。用户先前「不要关键词」指向的 model-first 结构化抽取**尚未实施**，列为 v0.3 议题；本轮聚焦格式固定。
